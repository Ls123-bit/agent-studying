# 图结构查询引擎（Graph Structure Query Engine）— 源码剖析与面试讲解

> **一句话定位**：文档解析后的章节结构（树形层级 + 步骤项）存放在 **Neo4j 图数据库**中（MySQL 作为降级备份），图结构查询引擎负责回答 *"这个文档有哪些章节？"*、*"某章节下面有什么内容？"*、*"第 N 步是什么？"* 这类**结构性问题**，并把查询结果直接渲染成自然语言回答，**不经过大模型生成**，从根本上避免了幻觉。

## 1. 整体架构与核心类

| 功能 | 核心类 | 所在模块/路径 | 一句话说明 |
|---|---|---|---|
| 执行器（GRAPH_ONLY） | `GraphOnlyExecutor` | `chatagent/rag/executor/` | 纯结构图直接回答，不取正文证据 |
| 执行器（GRAPH_THEN_EVIDENCE） | `GraphThenEvidenceExecutor` | `chatagent/rag/executor/` | 先图定位章节/编号项，再校验证据 |
| **图查询引擎** | `StructureGraphQueryEngine` | `chatagent/rag/service/` | 查询章节的兄弟节点、子节点、编号项，汇总为 `GraphQueryResult` |
| **图结果渲染** | `GraphAnswerRenderer` | `chatagent/rag/service/` | 把图查询结果转成自然语言回答 |
| 执行器注册表 | `ConversationExecutorRegistry` | `chatagent/rag/executor/` | 按 `ExecutionMode` 路由到对应执行器（策略模式） |
| **复合图服务** | `CompositeDocumentStructureGraphService` | `chatagent/manage/service/impl/` | `@Primary`，Neo4j + MySQL 双引擎，按文档可用性动态委托、互为备份 |
| Neo4j 实现 | `Neo4jDocumentStructureGraphService` | 同上 | `@ConditionalOnBean(documentManageNeo4jDriver)`，原生 Cypher 查询 |
| MySQL 实现 | `MysqlDocumentStructureGraphService` | 同上 | 基于结构节点表全量加载 + 内存打分/过滤 |
| 数据访问接口 | `DocumentStructureGraphService` | `chatagent/manage/service/` | 13 个图查询方法的统一抽象 |

**分层关系**：

```
执行器层 (GraphOnlyExecutor / GraphThenEvidenceExecutor)
    │ 调用
查询引擎层 (StructureGraphQueryEngine)  ──渲染──►  渲染层 (GraphAnswerRenderer)
    │ 调用
数据访问层 (DocumentStructureGraphService 接口)
    │ 委托路由 (@Primary Composite)
    ├──► Neo4jDocumentStructureGraphService   (首选，Cypher)
    └──► MysqlDocumentStructureGraphService   (降级，SQL + 内存打分)
```

## 2. 核心数据模型

所有模型类位于 `org.javaup.ai.manage.model.graph` 包（Lombok `@Data @Builder`）。

### 2.1 `GraphSection` — 章节节点视图

| 字段 | 类型 | 说明 |
|---|---|---|
| `nodeId` | `Long` | 章节节点唯一 ID（图中的主键） |
| `documentId` | `Long` | 所属文档 ID |
| `parseTaskId` | `Long` | 来源解析任务 ID |
| `nodeNo` | `Integer` | 排序号 |
| `depth` | `Integer` | 树深度 |
| `parentNodeId` | `Long` | 父节点 ID |
| `prevSiblingNodeId` / `nextSiblingNodeId` | `Long` | 前/后兄弟节点 ID |
| `nodeCode` | `String` | 章节编号（如 "3.2"） |
| `title` / `anchorText` | `String` | 标题 / 锚文本 |
| `sectionPath` / `canonicalPath` | `String` | 章节路径 / 规范化路径 |
| `contentText` | `String` | 章节正文 |

方法：`String displayTitle()` — 优先返回 `sectionPath`，其次 `nodeCode + title`，兜底 `title`。

### 2.2 `GraphItem` — 步骤/列表项节点视图

关键字段：`nodeId(Long)`、`documentId(Long)`、`nodeNo(Integer)`、`nodeType(String)`、`sectionNodeId(Long)`（归属章节）、`prev/nextSiblingNodeId(Long)`、`title/anchorText/sectionPath/canonicalPath/contentText(String)`、**`itemIndex(Integer)`（步骤编号）**。
方法：`String displayText()` — `contentText → anchorText → title` 逐级兜底。

### 2.3 `GraphQueryResult` — 引擎汇总结果（渲染层的唯一输入）

| 字段 | 类型 | 说明 |
|---|---|---|
| `targetSection` | `GraphSection` | 目标章节 |
| `parentSection` | `GraphSection` | 父章节 |
| `previousSibling` / `nextSibling` | `GraphSection` | 前/后兄弟章节 |
| `targetItem` | `GraphItem` | 命中的编号项 |
| `children` | `List<GraphSection>`（`@Builder.Default` = 空列表） | 直接子章节 |
| `matchedItems` | `List<GraphItem>`（默认空） | 关键词命中的步骤项 |
| `allItems` | `List<GraphItem>`（默认空） | 子树内全部步骤项 |

### 2.4 引擎的三个专用包装返回

| 类 | 字段 | 用途 |
|---|---|---|
| `GraphSectionWithChildren` | `section: GraphSection`、`children: List<GraphSection>` | "章节 + 直接子章节" |
| `GraphSectionWithSiblings` | `section`、`parent`、`previousSibling`、`nextSibling`（均 `GraphSection`） | "章节 + 父 + 前后兄弟" |
| `GraphItemWithContext` | `section: GraphSection`、`item: GraphItem`、`siblingItems: List<GraphItem>` | "编号项 + 所在章节 + 同级步骤列表" |

| `findSectionByTitle(Long, String)` | `Long, String` | `GraphSection` |
| `findSectionByCanonicalPath(Long, String)` | `Long, String` | `GraphSection` |
| `findBestSection(Long, String, String)` | `Long, String, String` | `GraphSection` |
| `listSections(Long)` | `Long` | `List<GraphSection>` |
| `listChildren(Long, Long)` | `Long, Long` | `List<GraphSection>` |
| `parentSection(Long, Long)` | `Long, Long` | `GraphSection` |
| `previousSibling(Long, Long)` | `Long, Long` | `GraphSection` |
| `nextSibling(Long, Long)` | `Long, Long` | `GraphSection` |

| `listItems(Long, Long)` | `Long, Long` | `List<GraphItem>` |
| `searchItemsInSection(Long, Long, String)` | `Long, Long, String` | `List<GraphItem>` |

**`CompositeDocumentStructureGraphService`**（`@Service @Primary`）：实现上述全部接口方法，每个方法体都是一行 `return delegate(documentId).xxx(...)`。

| 方法 | 参数 | 返回值 | 说明 |
|---|---|---|---|
| `private DocumentStructureGraphService delegate(Long documentId)` | `Long` | `DocumentStructureGraphService` | **路由核心**：`ObjectProvider.getIfAvailable()` 取 Neo4j bean；bean 存在且 `isGraphAvailable(documentId)`（Cypher 检查 `Document` 节点是否存在，异常安全返 false）→ Neo4j；否则 → MySQL |

**两个实现的差异**（面试加分点）：

| | `Neo4jDocumentStructureGraphService` | `MysqlDocumentStructureGraphService` |
|---|---|---|
| 装配条件 | `@ConditionalOnBean(name = "documentManageNeo4jDriver")` | 无条件注册 |
| 查询方式 | 原生驱动 `Session.run(Cypher)`，`MATCH (s:Section {documentId, nodeId})` | `DocumentStructureNodeService` 全量加载到内存 Map |
| `findBestSection` | Cypher 匹配 `normalizedTitle/normalizedPath` | **内存打分**：标题/路径含 topic +8、锚文本 +6、正文 +2；facet 命中标题/路径 +5、正文 +1；取最高分 |
| 兜底定位 | — | 全表 stream filter 精确匹配 |

## 4. 方法调用关系与执行顺序

### 4.1 GRAPH_ONLY 流程（例："这个文档有哪些章节？"、"3.2 节的上一节是什么？"）

> 前置：上游规划阶段（LLM）已产出 `ConversationExecutionPlan`，内含 `DocumentNavigationDecision`（导航动作 `navigationAction`、结构锚点 `structureAnchor.structureNodeId`、执行模式 `executionMode=GRAPH_ONLY`）。

| 步骤 | 动作 | 说明 |
|---|---|---|
| ① | `ConversationExecutorRegistry.get(GRAPH_ONLY)` | 从 `EnumMap` 中按模式取出 `GraphOnlyExecutor`（策略模式，构造时收集所有 `ConversationExecutor` bean 注册） |
| ② | `GraphOnlyExecutor.execute(taskInfo)` | 校验 `plan / decision / structureAnchor.structureNodeId`，任一为空 → 直接返回 `noEvidenceReply` 兜底话术 |
| ③ | 发布"思考中"事件 + `traceRecorder().startStage(GRAPH_QUERY, ...)` | 开始追踪图查询阶段 |
| ④ | **分支判断** `decision.getNavigationAction()` |  |
| ④-a | `== SECTION_ADJACENCY_LOOKUP` → `structureGraphQueryEngine.findSectionWithSiblings(documentId, sectionNodeId)` | 引擎内部顺序：`findSectionById` → `parentSection` → `previousSibling` → `nextSibling`（4 次图查询）→ Builder 组装 `GraphSectionWithSiblings` |
| ④-b | 其他动作 → `findSectionWithChildren(documentId, sectionNodeId)` | 引擎内部顺序：`findSectionById` → `listChildren` → 组装 `GraphSectionWithChildren` |
| ⑤ | 执行器把包装结果**平铺**成 `GraphQueryResult`（Builder） | 统一渲染层输入格式 |
| ⑥ | `graphAnswerRenderer.renderGraphAnswer(GRAPH_ONLY, decision, graphResult)` | 渲染内部顺序：空校验 → `renderGraphOnly` → `asksAdjacency(问题)` 为真或动作是邻接查询 → `renderAdjacency()`；否则 `asksChildren` 或 children 非空 → `renderChildren()`；再兜底返回 `displayTitle()` |
| ⑦ | `traceRecorder().completeStage(graphStage, ...)` 记录目标章节/父/子数量/答案 |  |
| ⑧ | `Flux.fromIterable(List.of(answer))` | 空答案时降级为 `noEvidenceReply`，流式返回前端 |

### 4.2 GRAPH_THEN_EVIDENCE 流程（例："安装章节的第 3 步是什么？"）

| 步骤 | 动作 | 说明 |
|---|---|---|
| ① | Registry 取出 `GraphThenEvidenceExecutor`，`execute(taskInfo)` | 同样先做锚点空校验 |
| ② | 私有 `buildGraphResult(plan, decision)` | 从 `itemAnchor` 取 `itemIndex`；`extractItemKeyword(originalQuestion, decision)` 从"哪一步/哪一项"后截取关键词并清洗（去掉"要求/需要/的是/？"等停用词） |
| ③ | `structureGraphQueryEngine.buildGraphResult(documentId, sectionNodeId, itemIndex, keyword)` | **引擎汇总方法**，内部顺序见 4.3 |
| ④ | `hasGraphEvidence(graphResult, decision)` 证据校验 | 失败 → `completeStage`（"证据不满足约束"）→ 返回 `noEvidenceReply`；成功 → 继续 |
| ⑤ | `renderGraphAnswer(GRAPH_THEN_EVIDENCE, decision, graphResult)` | 渲染内部顺序：`renderGraphThenEvidence` → ① `targetItem` 非空 → "第 N 步是：…"；② `matchedItems` 非空 → 列出所有命中步骤；③ 章节有正文 → 输出正文；④ 兜底 `displayTitle()` |
| ⑥ | `completeStage` + `Flux.fromIterable(List.of(answer))` | 返回 |

### 4.3 `buildGraphResult` 引擎内部执行顺序（最核心，面试必讲）

```
1. findSectionById(documentId, targetSectionNodeId)          → 目标章节（可为 null）
2. listChildren(documentId, section.getNodeId())             → 直接子章节列表
3. listItemsInSectionTree(...)          [私有递归]           → 子树内全部步骤项（按 nodeNo 排序）
4. findItemInSectionTree(..., itemIndex) [私有递归]           → 定位目标编号项（当前层查不到就 DFS 下钻子树）
5. searchItemsInSection(...) → searchItemsInSectionTree(...) [私有递归]  → 关键词命中项（keyword 非空才查）
6. 归属修正：
   6a. targetItem 有 sectionNodeId → findSectionById(所属章节) → resolvedSection 替换为 item 真正所属的章节
   6b. 否则 matchedItems 恰好 1 条 → 该 item 归属章节作为 resolvedSection，且 targetItem = matchedItems[0]
7. resolvedSection 非空时补齐：parentSection / previousSibling / nextSibling（3 次图查询）
8. Builder 组装 GraphQueryResult + log.info 汇总日志 → 返回
```

> **注意步骤 6 的设计意图**：提问"第 3 步是什么"时锚点章节可能是父章节，而第 3 步实际挂在某个子章节下，归属修正让最终回答能带出**正确的章节上下文**。

### 4.4 复合服务委托顺序（`CompositeDocumentStructureGraphService.delegate`）

```
每个接口方法被调用
  → delegate(documentId)
      → ObjectProvider<Neo4jDocumentStructureGraphService>.getIfAvailable()   // bean 可能不存在，避免注入报错
      → neo4j != null && neo4j.isGraphAvailable(documentId)   // Cypher: MATCH (d:Document {documentId}) RETURN count(d)>0，try-with-resources + 异常吞掉返 false
          ├─ true  → 返回 Neo4j 实现（打印"结构图服务选择 Neo4j"）
          └─ false → 返回 MySQL 实现（打印"结构图服务选择 MySQL fallback"）
  → 转发同名方法
```

## 6. 面试讲解话术

### 6.1 30 秒电梯版

> "我负责的文档问答里有一类**结构性问题**，比如'这个文档有哪些章节''3.2 节下面有什么''第 3 步是什么'。文档解析时章节树已经写入 Neo4j，我设计了一个**图结构查询引擎**来回答这类问题：执行器根据规划阶段的导航决策路由到 `StructureGraphQueryEngine`，引擎调图数据库查出目标章节、父子兄弟关系和编号项，汇总成 `GraphQueryResult`；再由 `GraphAnswerRenderer` **模板化渲染**成自然语言直接返回——全程不经过大模型生成，所以零幻觉。底层是 **Neo4j + MySQL 双引擎**，`CompositeDocumentStructureGraphService` 用 `ObjectProvider` 做探活委托，Neo4j 不可用自动降级 MySQL，互为备份。"

### 6.2 三分钟完整版（按"背景 → 架构 → 流程 → 亮点"）

**背景**：Agent 问答有两条取证路径：向量检索（RAG）适合语义问题，但"章节之间关系"这种结构问题向量检索答不准。所以解析阶段把章节树（`Section` 节点 + 父子/兄弟关系 + `Item` 步骤项）写入 Neo4j，运行时用图查询直接回答。

**架构（三层）**：
1. **执行器层**：`GraphOnlyExecutor`（纯结构问题，图查完直接答）和 `GraphThenEvidenceExecutor`（先图定位、还要取正文/编号项做证据校验）。两者实现 `ConversationExecutor` 接口，由 `ConversationExecutorRegistry` 按 `ExecutionMode` 策略路由。
2. **引擎 + 渲染层**：`StructureGraphQueryEngine` 提供 7 个查询入口（含两个重载），核心是 `buildGraphResult` 汇总方法，内部用**递归 DFS** 在章节子树里找编号项/搜关键词；`GraphAnswerRenderer` 按执行模式和问题关键词分四个渲染分支，把结构化结果拼成中文自然语言。
3. **数据访问层**：接口 `DocumentStructureGraphService` 有 13 个方法，`CompositeDocumentStructureGraphService` 标 `@Primary`，每个方法委托给 `delegate(documentId)` 动态选出的 Neo4j 或 MySQL 实现。

**流程**（以"安装章节的第 3 步是什么"为例）：
规划阶段 LLM 产出 `DocumentNavigationDecision`（锚点章节 ID、itemIndex=3、模式 GRAPH_THEN_EVIDENCE）→ Registry 路由到 `GraphThenEvidenceExecutor.execute` → 私有 `buildGraphResult` 从原问题提取关键词 → 调引擎 `buildGraphResult`：查目标章节 → `listChildren` → 递归收集子树 items → 递归找第 3 步（当前层没有就下钻子章节）→ **归属修正**（把上下文章节替换成第 3 步真正挂载的子章节）→ 补父/兄弟 → `hasGraphEvidence` 校验证据，失败返回兜底话术 → `renderGraphAnswer` 走 `renderGraphThenEvidence` 分支输出"第 3 步是：xxx" → 包成 `Flux<String>` 流式返回，全程 `traceRecorder` 记录阶段事件。

**亮点**：① 双引擎互备 + `ObjectProvider` 解决 Neo4j bean 可能不存在的装配问题；② 图查结果模板渲染，规避 LLM 幻觉；③ 递归 DFS + 归属修正保证跨层级提问也能答准；④ 全链路日志 + trace 阶段埋点，可观测。

## 7. 高频追问 Q&A

**Q1：为什么已经有向量检索（RAG），还要做图查询引擎？**
> 向量检索按语义相似度召回片段，丢失了**层级和顺序**信息。"有哪些章节""上一节是什么""第几步"这类问题的答案在结构里而不在语义里。图数据库原生存了 `parent/child/prev/next` 关系，一次 Cypher 就能精确回答，且结果确定性 100%。

**Q2：Neo4j 和 MySQL 怎么做到互为备份？**
> 三个配合点：① MySQL 实现无条件注册，Neo4j 实现用 `@ConditionalOnBean(documentManageNeo4jDriver)` —— 没配 Neo4j 驱动时 bean 干脆不创建；② 复合服务注入 Neo4j 用的是 `ObjectProvider`（`getIfAvailable()`），避免 bean 缺失时启动报错；③ 每次调用先 `isGraphAvailable(documentId)` 用 Cypher 探活该文档的图数据是否已写入（异常吞掉返 false），**按文档粒度**选择引擎——有的文档已导入图就用 Neo4j，否则回退 MySQL。

**Q3：为什么查完图还要专门一个 Renderer，不直接把结构丢给大模型总结？**
> ① 结构性问题的答案就是确定的文本，模板拼装零延迟零成本零幻觉；② 渲染器里做了**意图分流**（邻接问题/子章节问题/编号项问题），比 LLM 总结更稳定可控；③ 关注点分离——引擎只管"查什么"，渲染器只管"怎么说"，改话术不用动查询逻辑。

**Q4：`buildGraphResult` 为什么要做"归属修正"？**
> 用户问"第 3 步是什么"时，LLM 锚点定位到的可能是父章节，而第 3 步实际挂在更深的子章节下。递归 `findItemInSectionTree` 找到 item 后，用 `item.getSectionNodeId()` 反查真正所属章节，把 `resolvedSection` 替换掉，这样回答里的章节上下文才是准确的。关键词恰好唯一命中时同理修正。

**Q5：`findItemInSectionTree` 的递归会不会很慢？图会不会很深？**
> 单文档章节树一般深度 3~5 层、节点几十到几百个，DFS 代价可忽略。且每层只做两次图查询（`findItemByIndex` + `listChildren`），Neo4j 上 `documentId+nodeId` 是精确匹配。MySQL 版本则是一次全量加载到内存 Map 后纯内存遍历，无 N+1 问题。

**Q6：执行器返回 `Flux<String>` 是为什么？**
> 整个 Chat 服务是 WebFlux 响应式流式架构。图查询虽然同步完成，但统一用 `Flux.fromIterable(List.of(answer))` 包装，和其他执行器（如 RAG/ReAct 的逐 token 流）保持同一接口签名，前端按同一套 SSE 协议消费。

**Q7：查不到怎么兜底？**
> 三层兜底：① 执行器入口校验 `structureAnchor.structureNodeId` 为空 → 直接返回 `plan.noEvidenceReply`；② `GraphThenEvidenceExecutor` 有 `hasGraphEvidence` 证据校验（要求有 targetItem/matchedItems 或章节正文），不满足 → `noEvidenceReply`，并在 trace 里记"证据不满足约束"；③ 渲染层各级空值兜底（无兄弟 → "未找到相邻章节"，答案为空 → 兜底话术）。

**Q8：MySQL 版 `findBestSection` 的打分逻辑说说看？**
> 遍历全部章节，对每节累计得分：topic 命中标题/路径 +8，命中锚文本 +6，命中正文 +2；facet（维度词）命中标题/路径 +5、命中正文 +1。取最高分且 >0 才返回。本质是一个轻量级规则打分器，替代 Neo4j 版用规范化标题精确匹配的策略。

**Q9：导航决策 `DocumentNavigationDecision` 是谁产出的？**
> 上游规划阶段由 LLM 结构化输出（导航动作 `navigationAction`、结构锚点 `structureNodeId`、编号锚点 `itemAnchor`、检索问题 `retrievalPlan`、模式 `executionMode`），本引擎只消费不生产——这也是"规划-执行"分离的设计。

**Q10：如果让你改进，你会改什么？**
> ① 递归树遍历可改为 Cypher 一次 `MATCH (s)-[:HAS*]->(i)` 变长路径查询，减少往返；② `findBestSection` 的关键词打分可引入拼音/同义词；③ 双引擎可用本地缓存（Caffeine）缓存 `isGraphAvailable` 探活结果，减少每次调用的探活 Cypher；④ 渲染话术可国际化配置化。

## 8. 设计亮点与可改进点

### 亮点（面试主动抛出）

| # | 亮点 | 体现位置 |
|---|---|---|
| 1 | **策略 + 注册表模式**路由执行器 | `ConversationExecutorRegistry`（`EnumMap<ExecutionMode, Executor>`，构造器自动收集所有 bean） |
| 2 | **组合/委托模式**实现双引擎互备 | `CompositeDocumentStructureGraphService` 全方法一行委托 + `@Primary` 对上层透明 |
| 3 | **`ObjectProvider` 延迟可选注入** | Neo4j bean 不存在时不炸启动，运行时 `getIfAvailable()` 探测 |
| 4 | **文档级探活降级** | `isGraphAvailable` 逐文档检查图数据是否就绪（而非全局开关），异常安全 |
| 5 | **递归 DFS + 去重排序** | 三个 `*InSectionTree` 私有方法统一的下钻模式，`nodeNo` 排序保证输出顺序稳定 |
| 6 | **归属修正**（resolvedSection） | `buildGraphResult` 第 6 步，回答的章节上下文始终是 item 真正所属章节 |
| 7 | **模板渲染替代 LLM 生成** | `GraphAnswerRenderer` 确定性输出，结构性问题零幻觉 |
| 8 | **全链路可观测** | 每个方法 `log.info` 结构化字段 + `traceRecorder.startStage/completeStage` 阶段埋点 |
| 9 | **Builder + `@Builder.Default`** | `GraphQueryResult` 等模型集合字段默认空列表，避免 NPE |

### 可改进点（展示思考深度）

1. 递归树遍历产生多次数据库往返，可改为 Neo4j 变长路径一次查完子树；
2. `Composite` 每次调用都执行 `isGraphAvailable` 探活 Cypher，可加短 TTL 缓存；
3. `findSectionWithChildren(Long, String)` 重载里 `findBestSection` 查不到时用 `null` 继续查，行为可再明确（返回空对象或抛业务异常）；
4. 渲染话术硬编码中文，可抽到配置/资源文件支持多语言。
