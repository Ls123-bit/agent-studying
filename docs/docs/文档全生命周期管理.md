# 文档全生命周期管理（面试讲述版）

> 模块位置：`nexus-agent-business/nexus-agent-business-chat`，包路径 `org.javaup.ai.manage`
> 一句话定义：**从文档上传到最终可被检索，中间经历了解析、分块、向量化、索引构建等一系列步骤**的完整异步化流水线。

---

## 一、30 秒总览（面试开场白）

这套文档全生命周期管理解决的是 RAG 场景下"一份原始文件如何变成可被 AI 精准检索的知识"的问题。整个链路分为**两条线**：

- **同步交互线（HTTP）**：负责上传文件、查询推荐策略、确认策略、触发索引构建、查询进度——用户只做"轻决策"；
- **异步处理线（Kafka）**：负责耗时重的解析、分块、向量化、索引构建——用两条 Kafka 主题（parse-topic / index-topic）驱动，消费者执行真正的流水线。

数据最终落在 **6 个存储**：MinIO（原始文件+解析文本）、MySQL（主数据+任务+日志）、PGVector（向量）、Elasticsearch（导航索引+关键词索引）、Neo4j（结构图）。全流程用一个 `SuperAgentDocumentTask` 任务表 + `DocumentTaskLog` 日志表做状态追踪，每个阶段可观测、可恢复。

**为什么这样设计？** 解析一份 100 页的 PDF 可能要几十秒，调 LLM 切块、调 Embedding 模型更慢。如果同步做，HTTP 必然超时。所以用 Kafka 把"用户请求"和"重处理"解耦，前端通过轮询任务状态接口获知进度——这是典型的**生产者-消费者 + 状态机**模式。

## 二、八大核心类与职责（对应架构图表格）

| 功能 | 核心类 | 关键方法 | 职责说明 |
|------|--------|----------|----------|
| 文档上传 | `DocumentManageServiceImpl` | `upload()` | 接收文件，存 MinIO，建任务，发 Kafka 解析消息 |
| 多格式解析 | `TikaDocumentParserService` | `parse()` | 用 Apache Tika 解析 PDF/Word/HTML 等，TXT/MD 直接按 UTF-8 读 |
| 分块策略推荐 | `DocumentStrategyServiceImpl` | `recommend()`（实际方法名 `recommendStrategy`） | 根据文档特征（结构/长度/质量）推荐父块+子块两级分块策略 |
| 异步处理管线 | `DocumentAsyncProcessServiceImpl` | `process()`（实际方法名 `handleParseRoute` / `handleIndexBuild`） | Kafka 驱动的两个消费者入口，串起整条异步流水线 |
| 向量化入库 | `DefaultDocumentVectorGateway` | `store()`（实际方法名 `vectorize`） | 文本块分批 Embedding 后 upsert 进 PGVector |
| 结构树构建 | `DocumentStructureNodeServiceImpl` | `replaceDocumentNodes()` | 把解析出的层级结构（标题/段落/列表）落库为结构树 |
| Neo4j 图写入 | `Neo4jDocumentStructureGraphService`（读）/ `Neo4jDocumentStructureGraphProjectionService`（写） | `projectToGraph()` 等 | 把文档结构投影为 `Document-Section-Item` 图，支持章节级导航 |
| ES 导航索引 | `ElasticsearchDocumentNavigationIndexService` | `reindexDocumentNodes()` / `searchSections()` | 构建章节级别的搜索索引，支撑"定位到第几章第几节" |

> 面试提示：图片中的 `recommend()`、`process()`、`store()` 是能力简称，源码中的真实方法名分别是 `recommendStrategy()`、`handleParseRoute()/handleIndexBuild()`、`vectorize()`，讲述时用真实方法名更专业。

## 三、完整执行顺序（五幕剧）

### 第一幕：上传（同步 HTTP）

```
POST /manage/document/upload (multipart)
```

1. `DocumentManageController.upload()` 接收 `MultipartFile` + `DocumentUploadDto`；
2. `DocumentManageServiceImpl.upload()` 依次执行：
   - 校验：文件非空 → 文件名非空 → `DocumentFileTypeEnum.fromFileName()` 识别类型（不支持的类型直接抛业务异常）；
   - `getFileBytes(file)` 读出 `byte[]`；
   - 雪花 ID 生成 `documentId`；
   - **`storageService.uploadOriginalFile()` 存 MinIO**，返回 `StoredObjectInfo`（bucket/objectName/url）；
   - 组装 `SuperAgentDocument`（parseStatus=`PARSING`，strategyStatus=`WAIT_RECOMMEND`，indexStatus=`WAIT_BUILD`）和 `SuperAgentDocumentTask`（taskType=`PARSE_ROUTE`，stage=`FILE_UPLOAD`）；
   - **`transactionTemplate.execute()` 编程式事务**内一次性落库：document + task + 首条任务日志；
   - **事务提交后** `kafkaProducer.sendParseRoute(DocumentParseRouteMessage)` 发 Kafka；
3. 立即返回 `DocumentUploadVo(documentId, taskId, 三个状态)`——**上传接口不等待解析**。

> 面试考点：为什么先落库再发消息、且发消息放在事务外？—— 若在事务内发消息，消费者可能先于事务提交读到"脏数据"（查不到 document），所以采用"事务提交后再投递"的顺序保证一致性。

### 第二幕：异步解析 + 策略推荐（Kafka parse-topic）

```
DocumentKafkaConsumer.consumeParseRoute(String payload)
  └─► DocumentAsyncProcessServiceImpl.handleParseRoute(documentId, taskId)
```

`handleParseRoute()` 内部按序执行（每步都写任务日志）：

1. 任务状态 `NEW → RUNNING`，阶段 → `CONTENT_PARSE`；文档 parseStatus → `PARSING`；
2. `storageService.downloadObject(objectName)` 从 MinIO 下载原始文件 `byte[]`；
3. **`parserService.parse()`（TikaDocumentParserService）**：
   - `extractRawText()`：PDF/DOC/DOCX/HTML 走 `Tika.parseToString()`，TXT/MD 直接 UTF-8 解码（Tika 失败时文本类文件兜底降级）；
   - `cleanupText()` 清洗（统一换行、去控制符、压缩空白）；
   - `structureNodeExtractor.extract()` 抽取结构节点候选；
   - 统计标题数、段落数、最大段落长度、估算 token 数；
   - `evaluateStructureLevel()` 评估结构强度（高/中/低/未知）、`evaluateContentQuality()` 评估内容质量（乱码率+长度→高/中/低）；
   - 产出 `DocumentAnalysisResult`；
4. `storageService.uploadParsedText()` 把纯文本回存 MinIO，得到 `parseTextPath`；
5. **`structureNodeService.replaceDocumentNodes()` 结构树构建**：先删旧节点，再把 `DocumentStructureNodeCandidate` 列表转成 `SuperAgentDocumentStructureNode` 落库（两遍扫描：第一遍分配雪花 ID 建 `nodeNo→id` 映射，第二遍填父子/兄弟指针）；
6. `syncNavigationArtifacts()`（私有方法）同步两个导航产物：
   - `navigationIndexService.reindexDocumentNodes()` → **ES 导航索引**（先 deleteByQuery 清旧，再 Bulk 写入，`Refresh.WaitFor`）；
   - `graphProjectionService.projectToGraph()` → **Neo4j 图写入**（DETACH DELETE 旧图 → CREATE Document/Section/Item 节点 → MERGE HAS_SECTION/HAS_CHILD/NEXT_SIBLING/HAS_ITEM 关系）；
7. `documentProfileService.generateProfile()` 生成文档画像；
8. **`strategyService.recommendStrategy()` 分块策略推荐**（DocumentStrategyServiceImpl）：
   - 四个判定函数：`shouldUseStructure()`（文件类型合适 且 结构≥中 或 标题≥2）、`shouldUseRecursive()`（文本超长）、`shouldUseSemantic()`（够长+段落≥3+质量≥中）、`shouldUseLlm()`（低质量+够长+配置开关）；
   - 父块流水线：有结构→`STRUCTURE`，否则→`RECURSIVE`（兜底）；
   - 子块流水线：质量差→`LLM`；边界清晰→`SEMANTIC`；超长/需兜底→追加 `RECURSIVE`；
   - 产出 `DocumentStrategyPlanDraft`（快照 `PARENT:1;CHILD:3,2` 形式 + 推荐理由）；
9. 生成 `SuperAgentDocumentStrategyPlan`（planStatus=`WAIT_CONFIRM`）+ 两个流水线的 `SuperAgentDocumentStrategyStep` 落库；
10. 文档状态更新：parseStatus=`PARSE_SUCCESS`，strategyStatus=`RECOMMENDED`，回填 charCount/tokenCount/structureLevel 等；
11. `finishTaskSuccess()` 任务置 `SUCCESS`，记录耗时。

失败分支：catch 后 parseStatus=`PARSE_FAILED` + 记录 errorMsg + 任务置 `FAILED` + ERROR 日志。

> 前端此间轮询 `POST /manage/document/strategy/plan/query` 获取推荐结果。

### 第三幕：用户确认策略（同步 HTTP）

```
POST /manage/document/strategy/confirm
```

`DocumentManageServiceImpl.confirmStrategy(dto)`：

1. 前置校验：parseStatus 必须 `PARSE_SUCCESS`；请求的 basePlanId 必须等于文档当前方案；
2. `strategyService.normalizeSteps()` 把用户提交的父/子流水线归一化（去重、校验合法枚举、保留原有步骤的 USER_KEEP、新增步骤标 USER_ADD）；
3. **对比决策**：归一化后与基础方案一致 → 原方案直接置 `CONFIRMED`；有变化 → 旧方案置 `DISCARDED`，新建方案（planVersion+1，来源 `USER_ADJUST`）并插入新步骤；
4. document.strategyStatus → `CONFIRMED`，任务阶段推进到 `STRATEGY_CONFIRM`，写 USER_CONFIRM 日志；
5. 返回 `DocumentStrategyConfirmVo`（含最终两级流水线）。

> 面试考点：方案版本化（planVersion 递增 + 新方案插表而非原地更新）保留了完整的策略调整审计链。

### 第四幕：触发索引构建（同步受理 + 异步执行）

**受理端** `POST /manage/document/index/build` → `DocumentManageServiceImpl.buildIndex(dto)`：

1. 前置校验：`PARSE_SUCCESS` **且** `CONFIRMED`（状态机闸门）；planId 一致性校验；
2. 防重复：查是否存在 `NEW/RUNNING` 状态的 BUILD_INDEX 任务，有则拒绝；
3. 创建 BUILD_INDEX 任务（携带 strategySnapshot），indexStatus → `BUILDING`；
4. `kafkaProducer.sendIndexBuild(DocumentIndexBuildMessage(documentId, taskId, planId))`；
5. 立即返回 `DocumentIndexBuildVo`。

**执行端** Kafka index-topic → `DocumentKafkaConsumer.consumeIndexBuild()` → `DocumentAsyncProcessServiceImpl.handleIndexBuild(documentId, taskId, planId)`：

1. 任务 RUNNING，阶段 → `CHUNK_EXECUTE`；step 全部置 `EXECUTING`；
2. `storageService.downloadText(parseTextPath)` 取回解析纯文本；
3. **`strategyService.buildParentBlocks(document, plan, steps, parsedText)` 分块流水线执行**（核心）：
   - `sortPipelineSteps()` 拆出父块步骤和子块步骤；
   - `structureNodeService.listDocumentNodes()` 取结构树；
   - `buildParentSeedList()`：有 STRUCTURE 步骤→按结构节点做种子，否则全文作为一个种子；
   - `executePipeline(..., PARENT)`：按步骤顺序对种子依次执行 `applyStructureChunking → applyRecursiveChunking → applySemanticChunking → applyLlmChunking`（switch 分发），每步后 `cleanupChunkList()` 去空去重；
   - 对每个父块种子：`buildChildSeedList()` + `executePipeline(..., CHILD)` 生成子块；子块为空则用父块自身兜底；
   - 组装 `ParentBlockCandidate(sectionPath, structureNodeId, nodeType, canonicalPath, itemIndex, text, sourceType, childChunks)` 列表，`cleanupParentBlockList()` 去重；
   - 细节：递归分块按"段落→行→句子→固定窗口"四级降序尝试，带 overlap；语义分块用 **Jaccard 相似度**做句间边界判定；LLM 切块走 PromptTemplate 调 ChatModel 返回 JSON 数组，失败自动降级语义切块；
4. `CHUNK_POST_PROCESS`：过滤空父块/空子块；
5. `buildParentChildEntities()`（私有方法）把候选转成 DB 实体：全局递增 `chunkNo`、父块记录 `startChunkNo/endChunkNo/childCount`、chunk 初始 vectorStatus=`WAIT_VECTOR`；逐条 insert `SuperAgentDocumentParentBlock` + `SuperAgentDocumentChunk`；
6. 阶段 → `VECTORIZE`；
7. **`vectorGateway.vectorize(chunkList)`（DefaultDocumentVectorGateway）**：
   - 过滤空文本块；`EMBEDDING_BATCH_SIZE_LIMIT = 10` 分批；
   - 每批 `embeddingModel.embed(List<String>)` 得 `List<float[]>`，校验数量一致；
   - `batchUpsert()`：JdbcTemplate `batchUpdate` 执行 `INSERT ... ON CONFLICT (id) DO UPDATE`（metadata 用 `CAST(? AS jsonb)`，向量用 `CAST(? AS vector)` 手拼 `[1.0,2.0]` 字面量）写入 PGVector 表；
   - `markSuccess()`：chunk 回写 vectorId/vectorStoreType=`PG_VECTOR`/vectorStatus=`VECTOR_SUCCESS`；
8. （可选）`keywordSearchGateway.indexChunks()` 写 ES 关键词索引；逐条 `chunkMapper.updateById()` 回写状态；
9. plan.planStatus → `EXECUTED`；document.indexStatus → `BUILD_SUCCESS`，`lastIndexTaskId = taskId`；任务 SUCCESS。

失败分支：indexStatus=`BUILD_FAILED`、相关 chunk 批量置 `VECTOR_FAILED`、step 置 `EXECUTE_FAILED`、任务 FAILED。

### 第五幕：查询与删除（同步 HTTP）

- 查询族：`queryDocumentPage` / `queryDocumentDetail` / `queryStrategyPlan` / `queryTaskLogs` / `queryDocumentChunks` / `queryDocumentChunkDetail` —— 全部读 MySQL（chunk 关联 parentBlock 组装 VO）；
- 删除 `deleteDocument(dto)`（`@Transactional`）按依赖顺序清理：
  **有进行中任务则拒绝删除** → MinIO 原文件+解析文本 → PGVector 向量 → ES 关键词索引 → ES 导航索引 → 知识路由索引 → Neo4j 图 → 依次删 9 张 MySQL 表（profile→topic关系→parentBlock→chunk→structureNode→taskLog→step→task→plan→document）。

```

  |
  +- sortPipelineSteps(steps, PARENT) / (steps, CHILD)
  +- structureNodeService.listDocumentNodes(docId, lastParseTaskId): List<StructureNode>
  |
  +- buildParentSeedList(parsedText, parentSteps, structureNodes)
  |     |
  |     +- [有STRUCTURE步骤且结构树非空] buildStructureParentSeeds(nodes)
  |     |     (SECTION 且内容承载 → ChunkCandidate 种子)
  |     +- [否则] 全文包成 1 个种子
  |     └─► executePipeline(seeds, remainingSteps, PARENT)
  |              |
  |              |  for step in orderedSteps:   (switch strategyType)
  |              |    ├─ STRUCTURE -> applyStructureChunking()   [标题栈+sectionPath]
  |              |    ├─ RECURSIVE  -> applyRecursiveChunking()  [段落→行→句→窗口,带overlap]
  |              |    ├─ SEMANTIC   -> applySemanticChunking()   [Jaccard<阈值断句成块]
  |              |    └─ LLM        -> applyLlmChunking()        [ChatModel出JSON; 失败降级semanticSplit]
  |              |    每步后: cleanupChunkList() 去空/去重
  |              └─► List<ChunkCandidate> 父块
  |
  +- for 每个父块种子 parentSeed:
  |     +- buildChildSeedList(parentSeed, childSteps, structureNodes)
  |     |     └─► executePipeline(childSeeds, childSteps, CHILD)  (同上四种策略)
  |     +- finalChildren 为空 ? 用父块自身兜底
  |     └─► new ParentBlockCandidate(sectionPath, structureNodeId, nodeType,
  |                                   canonicalPath, itemIndex, text, sourceType, finalChildren)
  └─► cleanupParentBlockList() 去重
      => List<ParentBlockCandidate>
```

## 六、状态机（面试讲"可观测性"必备）

```
document.parseStatus:    PARSING ──► PARSE_SUCCESS / PARSE_FAILED
document.strategyStatus: WAIT_RECOMMEND ──► RECOMMENDED ──► CONFIRMED
document.indexStatus:    WAIT_BUILD ──► BUILDING ──► BUILD_SUCCESS / BUILD_FAILED
task.taskStatus:         NEW ──► RUNNING ──► SUCCESS / FAILED
task.currentStage:       FILE_UPLOAD ──► CONTENT_PARSE ──► STRATEGY_ROUTE ──► STRATEGY_CONFIRM
                         ──► CHUNK_EXECUTE ──► CHUNK_POST_PROCESS ──► VECTORIZE ──► STORE_COMPLETE
plan.planStatus:         WAIT_CONFIRM ──► CONFIRMED ──► EXECUTED （调整后旧版置 DISCARDED）
step.executeStatus:      WAIT_EXECUTE ──► EXECUTING ──► EXECUTE_SUCCESS / EXECUTE_FAILED
chunk.vectorStatus:      WAIT_VECTOR ──► VECTORIZING ──► VECTOR_SUCCESS / VECTOR_FAILED
```

闸门规则：`confirmStrategy` 要求 `PARSE_SUCCESS`；`buildIndex` 要求 `PARSE_SUCCESS + CONFIRMED` 同时成立——状态机天然防止"未解析完就建索引"这类乱序操作。

## 七、面试讲述脚本

### 7.1 两分钟版本

> "我负责的文档全生命周期管理，覆盖一份知识文档从上传到可检索的完整链路，我把它的执行顺序总结为五步：**上传 → 解析+推荐 → 确认 → 构建索引 → 查询/删除**。
>
> 上传是同步接口：校验文件类型后，原始文件存 MinIO，同时在编程式事务里把文档记录、PARSE_ROUTE 任务和首条日志落库，事务提交后向 Kafka 的 parse-topic 投递消息，接口立刻返回 documentId 和 taskId。
>
> 消费端 handleParseRoute 里完成四件事：从 MinIO 拉文件用 Apache Tika 做多格式解析并清洗；抽取标题/段落/列表的结构树落库，同时同步两份导航产物——ES 章节索引和 Neo4j 结构图；基于解析出的结构强度、内容质量等特征，用规则引擎推荐父块+子块两级分块策略并落库为 WAIT_CONFIRM 的方案。
>
> 用户在前端可以查看推荐理由、调整策略后确认——确认接口会做方案版本化：方案没变直接 CONFIRMED，变了就废弃旧版、版本号+1 建新版。
>
> 用户触发构建索引后，接口只做状态校验和防重，再投一条消息到 index-topic。消费端 handleIndexBuild 按确认的策略执行分块流水线——结构切块、递归切块、语义切块、LLM 切块四种策略可按步骤编排，父块保留大语义单元用于回答，子块细粒度用于召回。切出的 Parent-Child 结构落 MySQL，然后子块以 10 条一批调 Embedding 模型向量化，通过 ON CONFLICT 幂等 upsert 进 PGVector，同时可选写 ES 关键词索引。
>
> 整条链路靠任务表+阶段枚举+日志表做全流程追踪，每个阶段的失败都有独立的失败状态和错误记录，删除时按依赖顺序清理 6 个存储。"

### 7.2 高频追问与参考回答

**Q1：为什么用 Kafka 而不是线程池/HTTP 回调？**
> 三个原因：①削峰——批量导入文档时解析/Embedding 是重 IO+重算力操作，MQ 天然缓冲；②可靠性——消息持久化，服务重启后消息仍可消费，线程池任务会丢；③有序性——发送时用 documentId 作为 message key，同一文档的消息进同一分区保证有序；④解耦——上游只管投递，消费速率可以独立扩缩容（改 consumer 并发）。

**Q2：上传接口如何保证"落库成功且消息必达"？**
> 顺序是"先事务落库、事务提交后再发消息"。如果反过来（事务内发消息），消费者可能先于提交读到不存在的文档。发消息失败则抛异常让用户重试，此时文档状态停在 PARSING，不会出现"有文件但没任务"的中间态。消息发送用 `send(...).get()` 同步确认 broker 应答。

**Q3：为什么分块要设计 Parent-Child 两级？**
> 这是 RAG 的经典优化（small-to-big retrieval）：向量检索的召回精度要求 chunk 小而准，但只召回小片段会缺乏上下文，LLM 回答质量差。所以子块（细粒度）用于 Embedding+召回，命中后通过 parentBlockId 回溯父块（大语义单元，如完整章节）喂给大模型。父块记录了 startChunkNo/endChunkNo/childCount，可以整段还原。

**Q4：分块策略是怎么"推荐"的？**
> 纯规则引擎（非 LLM）：解析阶段产出文档画像——结构级别（标题数≥5 高/≥2 中）、内容质量（乱码率+长度）、段落数、最大段落长度、token 估算。推荐逻辑：父块流水线——结构明显用 STRUCTURE（保章节边界），否则 RECURSIVE 兜底；子块流水线——质量低加 LLM 增强，边界清晰用 SEMANTIC 优化召回，超长追加 RECURSIVE 控长兜底。每个步骤带角色标记（PRIMARY/OPTIMIZE/ENHANCE/FALLBACK）和推荐理由，前端可解释。

**Q5：四种切块策略的实现要点？**
> STRUCTURE：维护标题栈，`DocumentLineClassifier` 判定标题行及其层级，拼 sectionPath（"第1章 > 第1.1节"），按标题切；RECURSIVE：按"空行段落→换行→句子→固定滑窗"四级降序，段落内贪心合并到 maxChars，块间加 overlap 防语义断裂；SEMANTIC：分句后逐句计算与当前块的 Jaccard 相似度，长度达标且相似度低于阈值即断块——主题漂移处切开；LLM：Prompt 模板让大模型输出 JSON 数组形式的语义块，超长先递归预切，LLM 失败自动降级 SEMANTIC，保证流水线不中断。

**Q6：向量写入 PGVector 的细节？**
> 10 条一批调 `EmbeddingModel.embed()`（Spring AI 抽象，底层 OpenAI 兼容接口），返回 `List<float[]>` 并校验数量一致。写入用 JdbcTemplate batchUpdate，SQL 是 `INSERT ... ON CONFLICT (id) DO UPDATE` 幂等 upsert，向量列用 `CAST(? AS vector)`，先手拼 `[0.1,0.2]` 字面量；元数据（documentId/sectionPath/structureNodeId 等 14 个字段）序列化成 jsonb 存入，供检索时过滤。每批成功后立即把 chunk 的 vectorStatus 回写为 SUCCESS——批间可观测。

**Q7：为什么结构树要同时写 ES 和 Neo4j？各干什么用？**
> 同一份结构树的三种消费形态：MySQL 关系行给分块时用（structureNodeId 关联 chunk）；ES 导航索引给"问题→章节"的模糊检索（matchPhrase + boost 权重，回答"这个问题出自哪一节"）；Neo4j 图给精确的结构导航（HAS_CHILD/NEXT_SIBLING/HAS_ITEM 关系，回答"这个章节的下一节/第 3 个列表项是什么"）。ES 挂了 searchSections 返回空列表自动降级；Neo4j 用 @ConditionalOnBean 按需装配——都是可选增强，不阻塞主链路。

**Q8：如何处理失败？有重试吗？**
> 两个消费者方法整体 try-catch：解析失败→parseStatus=PARSE_FAILED+错误信息落库；构建失败→indexStatus=BUILD_FAILED+已入库 chunk 批量置 VECTOR_FAILED+step 置 EXECUTE_FAILED。Kafka 监听器本身 catch 异常不打回消息（避免毒丸消息无限重试），用户可在前端看到失败原因后重新触发构建（buildIndex 有防重校验，RUNNING 中不允许重复触发）。这属于"人工触发重试"的最终一致设计。

**Q9：删除文档要注意什么？**
> ①前置校验有进行中任务则拒绝（防止删了文档任务还在写）；②删除顺序按依赖反向清理 6 个存储：MinIO→PGVector→ES 关键词→ES 导航→知识路由→Neo4j，最后删 9 张 MySQL 表，整体在 @Transactional 里保证 DB 原子性；外部存储删除放在事务内属可接受妥协（外部系统无法参与分布式事务，失败靠重试删除兜底）。

**Q10：token 数是怎么估算的？为什么不用分词器？**
> 用启发式：英文按空白分词数 + 中文按字符数 + 其余字符除以 4。解析阶段要快速给百万级文档画像，分词器成本高且此处只需量级正确的估算值（用于推荐阈值判断和展示），精度要求不高。

## 八、可复用的"亮点句"

1. **"同步做轻决策、异步做重处理"** —— HTTP 只做状态流转和校验，耗时操作全部 Kafka 异步化。
2. **"一套任务表+阶段枚举+日志表，整条流水线每一步可观测、可追溯"** —— task.currentStage 精确到 8 个阶段，每步 saveLog 带 detailJson。
3. **"策略即数据"** —— 分块策略不是写死的代码路径，而是 plan+step 两张表里的可版本化数据，用户可调整、可审计（DISCARDED 旧方案保留）。
4. **"四种切块策略可编排成流水线"** —— executePipeline 用 switch 按步骤序贯执行，策略间自动降级（LLM→SEMANTIC，STRUCTURE 空结果→RECURSIVE）。
5. **"存储各司其职"** —— MinIO 存原件、PGVector 管向量召回、ES 管章节导航与关键词、Neo4j 管结构推理、MySQL 管元数据与状态机。
6. **"可选组件用 ObjectProvider + Conditional 装配"** —— ES/Neo4j/LLM 缺失时主链路自动降级，不硬依赖。
