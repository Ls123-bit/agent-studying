# 对话入口与生命周期管理的执行流程（面试讲述版）

> 对应模块：`nexus-agent-business/nexus-agent-business-chat`
> 基础包：`org.javaup.ai.chatagent`
> 本文对应资料中的"对话入口与生命周期管理"表格：SSE 流式对话入口 / 对话主流程编排 / 会话租约（防并发）/ JVM 任务注册 / 停止生成。

---

## 一、一句话总览（开场白）

> "一个对话请求进来后，系统分三层接住它：**Controller 层**用 `Flux<String>` 返回一条 SSE 流；**Service 层**先用 **Redis 分布式租约**（Lua 脚本实现）跨实例防止同一会话重复请求，再在 **JVM 内的 ConcurrentHashMap 注册表**做单机级任务去重；任务注册成功后创建一个**单播 Sink** 绑定给客户端，真正的大模型生成是在客户端**订阅之后**才被激活的；结束后无论**完成、失败、用户点停止**，都走同一条带 CAS 防重入的收尾路径：关流 → 落库 → 释放租约 → 从注册表摘除任务。"

## 三、主流程调用关系与执行顺序（完整时序）

```

 │
 ▼ ①入口
BusinessChatController.stream(ChatRequestDto) : Flux<String>
 │
 ▼ ②总调度（Flux.defer 包装 → 订阅时才执行）
BusinessChatService.openConversationStream(ChatRequestDto) : Flux<String>
 │
 ▼
openDeferredConversationStream(ChatRequestDto) : Flux<String>
 │
 ├─▶ buildLaunchPlan(ChatRequestDto) : StreamLaunchPlan
 │      · normalizeQuestion / normalizeConversationId(为空则生成UUID)

 │

 │    claimConversationLease(StreamLaunchPlan) : boolean

 │      ✗ 失败 ──▶ rejectionFlux("该会话当前正在执行中...") : Flux<String> 直接返回
 │
 ├─▶ ④引导启动
 │    bootstrapConversation(StreamLaunchPlan) : BootstrapResult
 │      ├─▶ conversationArchiveStore.startExchange(...) : ConversationExchangeView   ← 落库开启本轮对话(exchange)
 │      ├─▶ createTaskInfo(StreamLaunchPlan, ConversationExchangeView) : TaskInfo
 │      │      · Sinks.many().unicast().onBackpressureBuffer()  ← 单播sink，客户端通道
 │      │      · buildSessionConfig(conversationId) : RunnableConfig（threadId=conversationId）
 │      │      · 往 runnableConfig.context() 塞入 sink/thinkingSteps/references/usedTools/traceId/question/日期...
 │      │      · new ConversationTraceRecorder(...)  ← 阶段链路追踪
 │      ├─▶ ⑤JVM任务注册（单机去重）
 │      │    chatRuntimeRegistry.register(TaskInfo) : boolean

 │      │      ✗ false ──▶ failBootstrappedExchange(落库FAILED) + releaseLeaseQuietly(释放Redis租约)
 │      │                    └─▶ BootstrapResult.rejected("该会话当前正在执行中...")
 │      └─▶ ✔ true ──▶ BootstrapResult.ready( bindClientChannel(TaskInfo) )
 │
 ▼ ⑥绑定客户端通道
bindClientChannel(TaskInfo) : Flux<String>
      = taskInfo.sink().asFlux()
          .doOnSubscribe(ignored → activateGeneration(taskInfo))   ← 订阅即激活生成
          .doOnCancel(() → stopTask(taskInfo, "客户端已取消请求"))  ← 断连自动停止
 │
 ▼ ⑦客户端真正订阅 SSE 流后（延迟到这一步才跑）

 ├─▶ startLeaseRenewal(TaskInfo) : Disposable

 │              Lua: get(key)==token → pexpire 返回1（只有持有人能续期）
 │            ✗ 续期失败 ──▶ 停止续期 + stopTask(taskInfo, "会话租约已失效，已停止生成")
 ├─▶ buildConversationExecution(TaskInfo) : Flux<String>  .subscribe()
 │      Flux.defer:
 │        ├─ safeEmit(thinking事件"正在分析问题上下文")
 │        ├─ Mono.fromCallable(→ prepareExecutionPlan(TaskInfo))  [boundedElastic 线程池]
 │        │    └─▶ chatPreparationOrchestrator.prepare(TaskInfo) : ConversationExecutionPlan
 │        │        taskInfo.setExecutionPlan / setDebugTrace
 │        └─ conversationExecutorRegistry.get(plan.getMode()) : ConversationExecutor
 │             └─▶ executor.execute(TaskInfo) : Flux<String>   ← 移交下游Agent/检索执行器
 │      .publishOn(boundedElastic)
 │      .doOnNext(chunk → emitModelChunk(TaskInfo, chunk))
 │      │     · answerBuffer.append(chunk)；CAS 记录首响应耗时 firstResponseTimeMs
 │      │     · safeEmit(streamEventWriter.text(chunk, metadata)) → 写入 sink → SSE 推给前端
 │      .doOnError(error → finishWithFailure(TaskInfo, error))
 │      .doOnComplete(() → finishSuccessfully(TaskInfo))
 ▼
⑧三种终态收尾（互相用 CAS 互斥，只会走一个）
 ├─ 正常完成: finishSuccessfully(TaskInfo)
 ├─ 执行失败: finishWithFailure(TaskInfo, Throwable)
 └─ 主动停止: stopTask(TaskInfo, reason)        ← 见第五节
     共同尾部：
       safeComplete(sink) 关闭SSE
       conversationArchiveStore.completeExchange(..., COMPLETED/FAILED/STOPPED, ...) 落库
       safeRefreshConversationSummary 异步刷新会话摘要
       cleanup(TaskInfo):
         dispose 租约续期任务 → dispose 生成流 → releaseLeaseQuietly(释放Redis租约)
         → chatRuntimeRegistry.remove(conversationId, taskInfo)   ← 条件删除，防止误删新任务
```

**执行顺序口诀（面试背这个）**：
**入口 → 延迟编排 → 参数归一化成 LaunchPlan → Redis 抢租约 → 落库开轮次 → 建 TaskInfo → JVM 注册表去重 → 绑定 Sink 返回 Flux → 客户端订阅激活 → 启动租约续期定时器 → 订阅执行计划 → 交给执行器 → 逐 chunk 推流 → 三选一终态收尾（关流/落库/释放租约/摘除注册）**。

### 4.5 两个防并发组件

**ChatRuntimeRegistry**（`@Component`，纯 JVM 内存）：

| 方法 | 参数 | 返回 | 实现 |
|---|---|---|---|
| `register` | `TaskInfo` | `boolean` | `ConcurrentMap.putIfAbsent(conversationId, taskInfo)==null`（原子） |
| `get` | `String conversationId` | `Optional<TaskInfo>` | `Optional.ofNullable(map.get)` |
| `remove` | `String conversationId` | `void` | 无条件删 |

**RedisLeaseManager**（基于 Redisson `RScript` eval Lua）：

| 方法 | 参数 | 返回 | Lua 语义 |
|---|---|---|---|
| `acquire` | `String key, String ownerToken, Duration ttl` | `boolean` | `exists==0 → psetex(key,ttl,token) 返回1`（不存在才能抢，原子） |

## 五、停止生成（stopConversation）执行顺序

```
前端 POST /api/chat/session/stop {conversationId}
 → Controller.stop(ConversationIdentityDto) : ApiResponse<ConversationStopVo>
 → BusinessChatService.stopConversation(conversationId)              ← 重载①，reason="用户已停止生成"
 → stopConversation(conversationId, reason)                          ← 重载②
    ├─ chatRuntimeRegistry.get(conversationId) : Optional<TaskInfo>
    │    empty → return ConversationStopVo(id, false, "没有找到正在执行的会话")
    └─ stopTask(taskInfo, reason) : ConversationStopVo
         ① taskInfo.finalized().compareAndSet(false,true) 抢终态标记
         │    失败 → return (id, false, "会话已经结束")          ← CAS 防止重复停止/与收尾竞态
         ② chatRuntimeRegistry.get 再核对：当前注册的不是同一个 taskInfo
         │    → return (id, false, "会话已由新的执行接管")        ← 防止停止"新任务"
         ③ businessChatReactAgent.interrupt(runnableConfig)      ← 中断 Agent 图执行（吞异常）
         ④ taskInfo.disposable.dispose()                          ← 取消响应式生成流
         ⑤ safeEmit(status事件 "⏹ 用户已停止生成") → safeComplete(sink) 关SSE
         ⑥ conversationArchiveStore.completeExchange(..., ChatTurnStatus.STOPPED, reason, 首响应耗时, 总耗时)
         ⑦ finally: safeRefreshConversationSummary(异步刷摘要) + cleanup(taskInfo)
              cleanup = dispose续期定时器 → dispose生成流 → releaseLeaseQuietly(释放Redis租约)
                        → chatRuntimeRegistry.remove(conversationId, taskInfo)  ← 条件删除
         → return ConversationStopVo(id, true, "已停止会话生成")
```

**三种结束路径对比（面试加分点）**：

| | finishSuccessfully | finishWithFailure | stopTask |
|---|---|---|---|
| 触发者 | Flux doOnComplete | Flux doOnError | 用户点停止 / doOnCancel / 租约失效 / reset |
| 终态标记 | CAS finalized | CAS finalized | CAS finalized |
| 推给前端 | references+recommendations 事件 | error 事件 | status("⏹ 原因") 事件 |
| 落库状态 | `ChatTurnStatus.COMPLETED` | `ChatTurnStatus.FAILED` | `ChatTurnStatus.STOPPED` |
| 额外动作 | 生成推荐追问（CLARIFICATION 模式直接用澄清选项） | buildErrorMessage（深挖 WebClientResponseException 的响应体） | interrupt Agent + dispose |
| 尾部 | 完全相同：关流 → 落库 → 刷摘要 → cleanup | 同左 | 同左 |

## 六、面试重点：为什么是"Redis 租约 + JVM 注册表"双层防并发？

**标准回答**：
1. **只留 Redis 行不行？** Redis 锁能挡住**跨实例**的重复请求，但从"抢到 Redis 锁"到"JVM 注册任务"之间存在窗口；而且同一实例内多个线程几乎同时到达时，先释放锁/后注册的时序交错仍可能放进两个任务。JVM 层 `ConcurrentHashMap.putIfAbsent` 是**单机内真正原子的**去重，两层各管一段，形成纵深防御。
2. **为什么租约 TTL 30s、续期 10s？** TTL 太短会误失效，太长则进程假死后其他实例要等很久才能接管。30s TTL + 10s 一次续期，意味着进程死掉后**最多 30s 租约自动过期**，系统自愈；续期 Lua 校验 ownerToken，**只有持有人能续期**，避免接管者续了旧锁。
3. **为什么 release/renew 都要比对 token？** 经典分布式锁安全问题：A 因 GC 停顿锁过期 → B 抢到锁 → A 恢复后直接 del 会误删 B 的锁。token 比对 + Lua 原子执行（get 和 del/pexpire 在一个脚本里，Redis 单线程不会穿插）杜绝误删。
4. **为什么 remove 有两个重载？** 收尾时任务可能已被"新一轮执行"替换注册。`remove(key, value)` 条件删除保证**只摘除自己那个 TaskInfo**，不会把接管的任务摘掉——和 stopTask 里"会话已由新的执行接管"的检查是同一套防御思想。
5. **finalized 的 AtomicBoolean CAS 干什么用？** 同一个 TaskInfo 可能同时收到 doOnComplete、doOnError、stopTask、doOnCancel 多路结束信号，`compareAndSet(false,true)` 保证**只有一个路径**做收尾（落库、关流、释放资源），其余直接返回——防止重复落库、重复关流。

**其他高频追问**：
- **为什么 `Flux.defer` 包 openConversationStream？** buildLaunchPlan/抢租约/落库都是副作用，defer 让它们推迟到**客户端真正订阅时**才执行，符合响应式规范，也保证每次订阅独立执行。
- **为什么用 unicast sink？** 一次对话只服务一个客户端连接，unicast 语义正好 1:1；`onBackpressureBuffer` 缓冲前端消费不过来的事件。
- **生成逻辑为什么挂在 doOnSubscribe 而不是直接返回时启动？** 如果客户端永远不订阅，任务、租约、落库就白做了；`doOnSubscribe → activateGeneration` 让"订阅即激活"，而 `doOnCancel → stopTask` 保证客户端断连时自动停止生成并释放资源（这是生命周期闭环的一部分）。
- **客户端直接关浏览器会怎样？** SSE 连接取消 → `doOnCancel` 触发 `stopTask(taskInfo, "客户端已取消请求")` → 走完整停止收尾（含落库 STOPPED、释放租约、摘除注册）。
- **TaskInfo 里为什么有 StringBuffer / synchronizedList / ConcurrentHashMap.newKeySet / AtomicLong？** 推流在响应式线程上，收尾可能在另一个线程（stop 是 HTTP 线程），answerBuffer、thinkingSteps、references、usedTools、firstResponseTimeMs 都是被跨线程读写的共享状态，收尾时用 `snapshotXxx` 在 synchronized 块里做一致性快照再落库。

## 七、面试讲述脚本

### 30 秒版（概述）
> "对话入口是一个返回 `Flux<String>` 的 SSE 接口。Service 层先用 Redis Lua 租约做跨实例防并发——同一会话 30 秒 TTL 的运行锁；抢锁成功后落库开启一轮 exchange，把 sink、追踪器、答案缓冲等组装成 TaskInfo，再用 JVM 内 ConcurrentHashMap 的 putIfAbsent 做单机任务去重。注册成功把 sink.asFlux 返回给客户端，订阅时才激活真正的模型生成，每 10 秒给租约续期，续期失败自动停止。结束路径有完成、失败、停止三种，用 CAS 保证只有一路收尾：关流、落库、释放租约、条件删除注册表条目。"

### 2 分钟版（按"进入→运行→退出"讲）
> **进入阶段**：前端 POST `/api/chat/stream`，Controller 校验 `ChatRequestDto` 后直接把 `openConversationStream` 返回的 `Flux<String>` 以 `text/event-stream` 吐出去。Service 用 `Flux.defer` 把启动副作用推迟到订阅时：先做参数归一化组装 `StreamLaunchPlan`——conversationId 为空就生成 UUID，chatMode 必填，文档模式下 selectedDocumentId 必须是可检索文档；同时生成租约 key `chat:running:{conversationId}` 和随机 ownerToken。
> 然后抢 **Redis 租约**：`acquire` 的 Lua 脚本是"不存在才 psetex"，抢不到直接回一条 error 事件的 Flux 拒绝。抢到后 `bootstrapConversation`：`startExchange` 落库开启本轮对话，组装 `TaskInfo`——里面最重要的是 unicast Sink（客户端通道）、RunnableConfig（threadId=会话id，context 里塞 sink/traceId/思考步骤/引用集合）、TraceRecorder（阶段追踪）。接着往 **ChatRuntimeRegistry** 注册，`putIfAbsent` 返回非空说明本机已有同会话任务在跑，就落库 FAILED、释放租约、返回拒绝。都通过后 `BootstrapResult.ready(bindClientChannel(taskInfo))`——把 `sink.asFlux()` 挂上 `doOnSubscribe` 和 `doOnCancel` 两个钩子返回。
> **运行阶段**：客户端订阅 SSE 时 `doOnSubscribe` 触发 `activateGeneration`：先启动每 10 秒一次的**租约续期定时器**（renew 的 Lua 校验 token，续期失败说明实例可能被判定失联，自动 stopTask 兜底），再订阅 `buildConversationExecution`：boundedElastic 上跑 `prepareExecutionPlan`（意图改写、历史压缩、检索规划，产出 ExecutionPlan），按 mode 从 ExecutorRegistry 取执行器执行，`doOnNext` 把每个模型 chunk 追加进 answerBuffer 并经 StreamEventWriter 序列化成 JSON 事件写进 sink 推给前端，同时记录首响应耗时。
> **退出阶段**：三路终态——正常完成、异常失败、主动停止——用 TaskInfo 里的 `AtomicBoolean finalized` CAS 抢占，只允许一路收尾：补发引用/推荐或 error/status 事件、completeSink 关流、`completeExchange` 按 COMPLETED/FAILED/STOPPED 落库、异步刷新会话摘要，最后 cleanup：dispose 两个 Disposable、**带 token 释放** Redis 租约、`remove(key, value)` **条件删除**注册表条目。用户点"停止"走 `/session/stop`：registry 找到 TaskInfo，CAS 抢终态后 interrupt ReactAgent、dispose 生成流、发"⏹ 已停止"、落库 STOPPED、走同一个 cleanup。整个设计的核心就是**双层防并发 + 单路收尾 + 全路径资源释放**。

### 讲述时的画图建议
在白板上画三条泳道：`Controller/客户端`、`BusinessChatService`、`Redis+Registry+DB`，按"进入（抢锁→落库→注册→返回Flux）→ 运行（订阅激活→续期→推流）→ 退出（三路终态→cleanup）"三段箭头讲，每个箭头标上方法名。

## 九、一句话总结每张表的要点（对应资料表格）

| 资料表格项 | 对应实现 | 记忆锚点 |
|---|---|---|
| SSE流式对话入口 | `BusinessChatController.stream()` → `Flux<String>`，produces text/event-stream | "Controller 只做转发，零业务逻辑" |

| 停止生成 | `stopConversation` → `stopTask`（CAS → interrupt → dispose → 落库STOPPED → cleanup） | "抢终态、断Agent、关流、落库、释放，一步不漏" |
