## 一、RPC 化的工具调用层（harness engineering 的外壳）

你清单里的核心认知是：**agent 的工具调用不是本地函数调用，而是一次网络请求，要按 RPC 的标准做认证、超时、重试、限流、幂等**。项目对这个认知的体现程度如下。

### 1.1 重试 ✅ 已实现（参数属实，但「不区分错误类型」是硬伤）

- 配置位置：`nexus-agent-business/nexus-agent-business-chat/.../chatagent/config/ChatAgentConfiguration.java:87-94`，通过框架的 `ToolRetryInterceptor` 声明：
  - `toolName("tavily_search")`、`maxRetries(2)`（即最多执行 3 次）、`initialDelay(200ms)`、`maxDelay(1200ms)`、`jitter(true)`、`onFailure(RETURN_MESSAGE)`。
- 退避算法（框架源码 `ToolRetryInterceptor`）：`delay = 200ms × 2.0^retryNumber`，封顶 1200ms，抖动因子 `0.75 + random×0.5`（±25% 随机抖动）。
- **关键缺陷（面试必须知道）**：框架 Builder 默认 `retryOn = e -> true`，项目没有调用 `retryOn(...)` 定制，所以 **429 限流、400 参数错误、500、超时全部无差别重试**。429 被 200~400ms 后立刻重试，反而加重对方限流——这正是你清单里「重试会不会触发限流」的标准反面案例。正确做法是：只对 5xx/超时/网络错误重试，429 读 `Retry-After` 头退避，4xx 直接不重试。
- 另一个坑：重试拦截器只绑定了 `tavily_search` 这一个工具名，未来新增工具默认没有重试。

### 1.2 熔断 ❌ 未实现

全项目 grep `CircuitBreaker / Resilience4j / Sentinel / 熔断` 零命中（含 pom 依赖）。**没有「连续失败 N 次后暂停调用、半开探测恢复」的机制。** 最接近的东西是调用次数 Hook 和会话租约，但那些是截止和互斥，不是熔断。面试时如果被问「工具持续挂了怎么办」，诚实的答案是：靠重试耗尽后兜底文案 + 次数 Hook 截止，没有熔断器，这是我清楚该项目缺的一块（可顺势讲 Resilience4j 的 CLOSED/OPEN/HALF_OPEN 三态方案）。

### 1.3 超时 ⚠️ 部分实现（外呼有，LLM 主链路没有）

| 层 | 数值 | 位置 |
| :--- | :--- | :--- |
| Tavily 工具级 | connect 3000ms / read 6000ms | `TavilySearchProperties.java:22-23`，经 `RestClientFactorySupport.java:18-26` 生效 |
| RAG 任务级：单检索通道 | 5000ms（`orTimeout`） | `ChatRagProperties.java:50` → `RagRetrievalEngine.java:88,128` |
| RAG 任务级：单子问题 | 12000ms（`orTimeout`） | `ChatRagProperties.java:52` |
| 推荐追问生成 | 3000ms（`orTimeout`） | `RecommendationService.java:68` |
| ES | connect 3000 / socket 5000 | `application.yaml:347-349` |
| Redis / Neo4j | 3000ms / 5s query-timeout | `application.yaml:19 / 357` |
| **LLM 模型主调用** | **无任何显式超时** | `application.yaml:38-63` 无 timeout 配置 |

**结论**：你清单里「超时每层都要有」只做了一半——工具外呼和检索编排有超时，但 ReAct 主循环里的 LLM 调用没有超时保护，只能靠 `ModelCallLimitHook`（8 次）兜底。面试时可以主动指出这一点并给出修法（给 OpenAI 兼容 client 配 connect/read timeout）。

### 1.4 限流 ⚠️ 只有「次数硬截止」，没有 QPS 限流，且会话级累计失效

- 无 Guava RateLimiter / Bucket4j / 任何令牌桶漏桶算法（全项目零命中）——**「别把对方 API 打挂」的速率限制不存在**。
- 存在的是调用次数 Hook（`ChatAgentConfiguration.java:70-82`，参数来自 `application.yaml:95-104`）：
  - `ToolCallLimitHook`：tavily_search 单轮 run 上限 **6** 次、thread 上限 **30** 次，超限 `ExitBehavior.END`（注入提示消息并优雅结束，不是抛异常）。
  - `ModelCallLimitHook`：单轮 **8** 次、thread 上限 **40** 次。
- **重大发现（README 宣传不实）**：「会话级累计 30/40 次」**实际不生效**。计数器写在 `RunnableConfig.context()` 里，而框架明确注释 context 是 run 级、不持久化；业务侧 `BusinessChatService.java:1151-1156` 每轮新建 RunnableConfig，从不恢复历史 context → thread 计数每轮从 0 重计。**真实生效的只有单轮 6/8 的限制。** 面试时绝不能说「会话累计 30/40」，说了会被框架源码追问穿；正确讲法是「单轮硬截止 + 我知道 thread 级计数因 context 不持久化而失效，修法是把计数挪到 Redis 按会话累计」。

### 1.5 幂等 ❌ 未实现（工具调用层面）

- 项目自研了幂等/防重框架 `nexus-agent-redisson-framework/.../super-agent-repeat-execute-limit-framework`（`@RepeatExecuteLimit` 注解 + 切面），但 **business 业务模块 0 处使用**。
- 唯一工具 Tavily 搜索是只读的，客观风险低；但一旦加写操作工具（下单、发消息），没有调用前检查/去重/唯一约束——你清单里「工具调用没做幂等，照样三次下单」的 bug 该项目今天就会发生。
- 注意区分：会话租约 `RedisLeaseManager` 防的是「同一会话并发跑两轮」，是互斥，不是工具幂等。

### 1.6 认证鉴权 / API key 管理 ✅ 已实现（符合你清单的「不写死、不打日志」）

- 所有 key 走环境变量注入，无硬编码：LLM `${ALI_BAI_LIAN_API_KEY}`（`application.yaml:46,59`）、Tavily `${TAVILY_API_KEY}`（yaml:232）、Rerank 带回退链 `${RERANK_API_KEY:${spring.ai.openai.api-key}}`（yaml:214）。全项目 grep `sk-`/`tvly-` 零命中。
- 运行时校验：`TavilySearchTool.java:62-64` key 为空抛 `IllegalStateException`（会被兜底链接住）。
- key 只放 Authorization header（`TavilySearchTool.java:86`），日志不打印 key；模型调用日志只打 messages 摘要。
- 小瑕疵：无加密存储（配置解析后是明文内存值）；`application.yaml:361-362` 把 `org.springframework.ai` 设为 DEBUG，生产日志暴露面偏大；弱默认凭据（admin 密码 `REDACTED-ADMIN-PASSWORD`、MinIO `minioadmin`）。

### 1.7 降级兜底 ✅ 已实现（多层，是项目的真亮点）

失败后的处理链条完整，符合你清单「工具不可调用就降级给兜底回复，不让异常直接抛给用户」：

1. **重试层**：`ToolRetryInterceptor` 耗尽后 `RETURN_MESSAGE`——把「工具失败」作为工具结果回传给模型，模型会向用户解释而不是 500。
2. **兜底层**：`ToolErrorInterceptor`（配置于 `ChatAgentConfiguration.java:95`）catch 所有异常，返回 `"Tool failed: " + message` 文案，不抛给用户。
3. **入参兜底**：`TavilyToolInputFallbackInterceptor.java:42-67`——LLM 生成的工具入参为空/格式错误时，用用户原始问题改写入参；无法构造时返回 error 响应而不是让调用炸掉。
4. **Rerank 四层兜底**：`HttpDocumentRerankPostProcessor.java`——开关关闭直通(53-55)、key 缺失回退原始排序(56-59)、响应格式错误回退(81-84)、异常/超时捕获回退(102-106)。**rerank 挂了不会导致检索挂**。
5. **存储级降级**：ES 关闭时关键词检索降级为 PG 内 LIKE 加权打分（`DocumentKnowledgeServiceImpl.java:212-307`）；Neo4j 关闭时回退 MySQL 结构表（`CompositeDocumentStructureGraphService`）。
6. **无证据短路**：`RagChatExecutor.java:127-131`——证据为空时不调 LLM，直接返回兜底话术「当前没有检索到足够证据」（防幻觉的最直接手段），另有 3 个短路点（GraphOnly/GraphThenEvidence/锚点缺失）。
7. **路由低置信降级为澄清**：置信度 <0.55 时走 `ClarificationExecutor` 反问用户，而不是硬检索（`ChatPreparationOrchestrator.java:200-222`）。

### 1.8 RPC 体现与 MCP ⚠️/❌

- 「工具调用 = 网络请求」的体现：唯一工具 `TavilySearchTool.java`（322 行）走 HTTP REST（connect 3s/read 6s + 重试 + 兜底 + 次数限制 + 入参校验 + key 校验），是教科书式的「给网络调用套工程壳」。
- **MCP 未集成到核心项目**：business 模块 grep `mcp` 零命中；MCP 代码只存在于演示模块 `ai-example/ai-example-mcp/`（且是 MCP **server** 端示例）。README 宣传的「MCP 动态发现 + 多工具编排」在核心链路里不存在——实际是 `FunctionToolCallback` 静态注册（`ChatAgentConfiguration.java:42-49`）。

## 二、并发控制 ✅（项目最扎实、最能打的部分）

你清单里「在不确定的执行流里管好正在发生的事」——这部分项目做得最好，面试优先讲。

### 2.1 集群级：Redis 租约互斥（比 setnx 教程深一层）

`super-agent-service-lease-framework/.../lease/RedisLeaseManager.java`：

- 三段 **Lua 脚本**实现 CAS 语义：ACQUIRE（19-24 行，`exists==0` 才 `PSETEX`，原子互斥）、RENEW（26-31 行，`GET==ownerToken` 才续期）、RELEASE（33-37 行，**token 匹配才 DEL，防误删别人的锁**）。
- 业务使用（`BusinessChatService.java`）：租约 key `chat:running:{conversationId}`（:80,1217-1220），**TTL=30s（:81），每 10s 续期一次（:82，`Flux.interval` 定时器 :1172-1182）**。
- 获取失败：直接返回拒绝消息「该会话当前正在执行中」（:115-118）——不排队不重试，快速失败。
- **续期失败的处理是精髓**（`renewLeaseOrStop` :1184-1204）：续期失败 = 锁被抢/Redis 不可用 → 本实例主动 `stopTask` 终止生成。这防止了「两个实例同时生成同一条消息」的脑裂。
- finally 统一清理（`cleanup()` :769-787）：dispose 定时器、静默释放租约、条件删除注册表——**成功失败都走，不留孤儿锁**（你清单里的「优雅降级，不留孤儿锁」）。

### 2.2 JVM 级：进程内注册表（双层防护）

`ChatRuntimeRegistry.java`：`ConcurrentHashMap<String, TaskInfo>`，`register` 用 `putIfAbsent` 防同进程重入（:19-21），`remove(key, expectedTaskInfo)` 条件删除防误删新任务（:32-37）。与 Redis 租约形成「集群级 + 进程级」双层防护，同时支撑 `/session/stop` 定位运行中任务。

### 2.3 并行工具与线程池清单

- ReactAgent 并行工具：`ChatAgentConfiguration.java:67-68` —— `parallelToolExecution(true)` + `maxParallelTools(4)`。
- 三个业务线程池（`ChatRagExecutorConfiguration.java`，工厂 :38-55：固定池、core=max、守护线程、**CallerRunsPolicy** 拒绝策略）：
  - 检索池 **8 线程/队列 256**（:21-25）——子问题×双通道并行检索（`CompletableFuture.supplyAsync`，`RagRetrievalEngine.java:56,84-86`）；
  - 记忆摘要池 **2/32**（:27-31）——摘要异步写库；
  - 后处理池 **2/64**（:33-36）——推荐追问生成。

### 2.4 流式输出为什么不会卡死（你清单里那个「收 token 同步查库」的坑，项目明确规避了）

这是最值得面试展开的题：

- SSE 实现：Servlet MVC 下 Controller 返回 `Flux<String>` + `produces="text/event-stream"`（`BusinessChatController.java:42-45`），由 Spring 的 ReactiveTypeHandler 桥接成 SSE。
- 发射器：`Sinks.many().unicast().onBackpressureBuffer()`（`BusinessChatService.java:180`），所有发射经 `SinkEmitHelper.java:19-45`（`synchronized(sink)` + 状态检查，CANCELLED/TERMINATED 静默忽略——防止停止后还往死 sink 里发）。
- **token 回调里没有任何 IO**：`ReactAgentExecutor.java:63-64` 模型流 `publishOn(Schedulers.boundedElastic)`，`extractTextChunk`（:89-115）纯内存操作；`BusinessChatService.java:282-299` 的 `doOnNext(emitModelChunk)`（:545-555）只做 StringBuffer 追加 + sink 发射。
- **DB 读写全部挪到阶段边界或异步**：编排准备（历史/改写/检索）用 `Mono.fromCallable().subscribeOn(boundedElastic)`（:286-288）；每阶段的 trace 写库在阶段开始/结束时各一次（不是每 token）；最终回答落库 `completeExchange` 只在成功/失败/停止时一次性写（:622-635,694-707）；摘要刷新完全异步（专用池 + JVM 内 `refreshingConversationIds` 防重，`PersistentConversationMemoryService.java:163-181`）。
- 面试话术：「把『每 token 一次 DB/网络操作』的阻塞写法，改造成『流上只做内存变换 + 阶段边界批量落库 + 专用有界线程池隔离』，连接池就不会被流式回调打满」。

### 2.5 停止生成 / 中断 ✅

两条路径：显式 `POST /api/chat/session/stop`（`BusinessChatController.java:52-55`）+ 客户端断连触发 `doOnCancel`（`BusinessChatService.java:253`）。都进 `stopTask`（:376-462）：`finalized` CAS 防重 → 框架级 `interrupt(runnableConfig)`（:390）→ dispose 执行流 → 发停止事件并 complete sink → 落库 STOPPED 状态 → cleanup 释放租约。

### 2.6 诚实的风险点

- HikariCP 主池 **maximum-pool-size=10**（`application.yaml:25-28`），PGVector 独立池 5（yaml:319-324）。多会话并发时，检索池 8 线程 + trace 写库 + 摘要池 + Kafka 消费者共享 10 个连接，**存在排队打满风险**（Hikari 默认等 30s），无连接隔离配置。面试可主动讲「我会按池隔离 + 监控 active connections」。

## 三、状态管理 ⚠️（持久化做了，断点恢复没做）

### 3.1 Checkpoint 持久化 ✅

- `ChatAgentConfiguration.java:33-39`：`MysqlSaver.builder().dataSource(...).createOption(CREATE_IF_NOT_EXISTS)`，挂到 ReactAgent（:65）。
- 表结构（`sql/Mysql/create_table_mysql.sql`）：`GRAPH_THREAD`（:89-95）+ `GRAPH_CHECKPOINT`（:97-107，`state_data JSON` 存 Graph 状态含消息列表）。
- 恢复方式：`RunnableConfig.threadId = conversationId`（`BusinessChatService.java:182,1151-1156`）——同会话下一轮自动从 MySQL 加载最近 checkpoint 续接上下文。**这就是「状态如何存」的答案：图执行状态以 JSON checkpoint 存 MySQL，业务态以结构化表存。**

### 3.2 业务状态落库 ✅

编排中间产物和终态分开存：`nexus_agent_chat_exchange`（轮次+调试快照 JSON，sql:19-42）、`nexus_agent_chat_exchange_trace_stage`（阶段轨迹，sql:61-87）、`nexus_agent_chat_memory_summary`（摘要，sql:44-59）、`nexus_agent_chat_retrieval_result` / `channel_execution`（检索观测）。运行中的执行计划只存内存 TaskInfo，终态落库。

### 3.3 状态恢复（断点续跑）❌ 未实现

- 有的：重启后历史会话/轮次从表里读回，对话上下文靠 checkpoint 续接。
- 没有的：**任务级断点恢复**。进程被杀时，进行中的轮次在 DB 里永远停在 RUNNING 态，不会标记失败也不会续跑；内存 TaskInfo 全丢，stop 接口只会说「没有找到正在执行的会话」。自愈手段只有 Redis 租约 30s TTL 自然过期 + 下次请求重新抢锁。全项目无 resume/启动重扫逻辑。你清单里「状态恢复——让他出了问题可以接住」这条，项目只做到「能接住同一会话的下一轮」，没做到「能接住被打断的这一轮」。

### 3.4 Kafka 异步流水线 ⚠️（队列有，可靠性配置没有）

- 用途：文档上传后异步解析（parse topic）+ 确认策略后异步切块/向量化/建索引（index topic）（`DocumentManageKafkaConfiguration.java:26-35`）。
- 发送端 `kafkaTemplate.send(...).get()` 同步等 ack；消费端异常 catch 后仅 log.error **吞掉**（`DocumentKafkaConsumer.java:41-44,55-57`），未配置 DefaultErrorHandler/RetryTemplate/**死信队列**；任务表有 `retry_count` 列但代码从不递增——**失败即终态，无自动重试**。
- 分步任务日志做得好：`nexus_agent_document_task_log` 表（sql:219-243）记录 8 个 stage × 6 种 event，`DocumentAsyncProcessServiceImpl` 各阶段更新任务状态——「出了问题能定位到哪一步」这点成立，「出了问题能自动恢复」不成立。

## 六、Loop engineering：agent 自主循环「该跑该停」✅ 基本体现

你清单里「现在的 agent 要自主跑多步 loop，会自己跑的循环」——项目对应实现：

1. **自主多步循环**：`ReactAgentExecutor.java:63` 的 `reactAgent.stream(...)` 是框架级 ReAct 循环（模型→工具→模型…），工具 `tavily_search` 由 LLM 自主决定调几次。
2. **「该停」——三重保险**：
   - 次数 Hook：`ModelCallLimitHook`（run 8）+ `ToolCallLimitHook`（run 6），超限 `ExitBehavior.END` 优雅结束（注入提示而不是硬崩）——这就是防死循环/防烧额度的工程兜底，对应你清单「可能一个会话把 api 额度跑光，只能靠工程兜底」。（注意 thread 级 30/40 失效，见 §1.4。）
   - 用户主动停止 / 断连取消：`stopTask` 链路（§2.5）。
   - 工具失败不会终止循环：兜底文案回传给模型，由模型决定下一步（失败被「消化」进循环而不是炸出循环）。
3. **「跑过的能找回」**：checkpoint 每轮落 MySQL（§3.1）+ 每阶段 trace（§5.1）。
4. **「壳」的缺口**：harness 的壳里少了熔断（§1.2）、任务级恢复（§3.3）、QPS 限流（§1.4）、幂等（§1.5）。

## 八、面试建议

### 8.1 优先讲的亮点（按含金量排序）

1. **流式链路的异步改造**（§2.4）——正好是你清单里那个「收 token 同步查库 → 连接池打满 → 服务僵死」的标准病例，项目给出了标准答案：token 回调零 IO + boundedElastic 调度 + 阶段边界批量落库 + 专用线程池隔离（8/2/2，CallerRunsPolicy）。
2. **Redis 租约互斥的完整生命周期**（§2.1）——Lua CAS、token 防误删、30s TTL + 10s 续期、**续期失败主动自杀防脑裂**、finally 不留孤儿锁。比「setnx + finally del」的教程答法深两档。
3. **多层降级兜底链**（§1.7）——重试→兜底文案→入参兜底→rerank 四层兜底→存储降级→无证据短路→低置信澄清。核心思想一句话：「每一层失败都有下一层接着，最后才轮到用户看到错误」。
4. **上下文工程的具体策略**（§4.1/4.2）——能报出数字（4 轮保留/6 轮一批/2200/1400 字符、5200 总预算），说明是真做过的。「截断保尾部、摘要保头部、LLM 摘要失败回退规则压缩」是有取舍的策略。
5. **trace 的响应式适配**（§5.1）——为什么不用 ThreadLocal（响应式链线程切换）而用 TaskInfo/方法参数传递，这是能和面试官讨论的点。

### 8.2 三个雷区（README 宣传与代码不符，别照着 README 说）

1. **「会话级累计 30/40 次」实际失效**（§1.4）——计数器存 run 级 context 不持久化。追问必穿。可反手变成加分：「我发现这个缺陷，修法是计数挪 Redis 按会话累计」。
2. **「MCP 工具协议集成」核心链路没有**（§1.8）——只有演示模块。被问就答「静态注册 FunctionToolCallback，MCP 在示例模块」。
3. **「重试区分错误类型」没有做**（§1.1）——429 也盲重试。主动说「当前 retryOn 全放行，正确做法是 429 读 Retry-After、4xx 不重试」。

### 8.3 「缺的 13 项」怎么答（§7）

被问到某项没实现时，用「承认 + 方案」的句式，例如熔断：「项目没接熔断器，我的方案是 Resilience4j 按 toolName 维度配 CircleBreaker，连续 5 次失败开路 30s，半开放 1 个探测请求，工具异常率作为健康指标暴露到 metrics」。这比假装实现了更加分。
