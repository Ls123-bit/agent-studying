# 全链路可观测

> 对应文档描述：从请求进来到回答生成，每一步都有埋点记录，方便排查问题和性能优化。
> 核心类：`ConversationTraceRecorder`（`startStage()/completeStage()`，记录每个阶段的耗时和状态）、`RetrievalObserveStore`（`listResults()`，记录每次检索的详细结果）、`StageBenchmarkService`（`listAll()`，各阶段的性能基准数据）。

---

## 一、模块定位（一句话说清这个业务）

一次 AI 对话要经过"记忆装载 → 意图/路由 → 问题改写 → 图谱查询 / RAG 检索 → 证据预算 → 回答生成 → 推荐 → 收尾"约十来个阶段，任何一步慢了或错了都直接影响体验。这个模块做的事是：**给每轮对话发一个 `traceId`，把每个阶段的开始/完成/失败（含耗时、摘要、快照 JSON）写进数据库，把检索的每条候选结果（各通道排名、RRF 得分、rerank 得分、闸门是否通过）和每个检索通道的执行明细也逐条落库，再对外提供查询接口，让前端能像"时间线 + 检索明细表"一样回放整轮对话**。另有一个 `StageBenchmarkService` 维护各阶段的 P50/P90/P99 性能基准（写入路径当前预留、未接线，查询接口已就绪）。

设计总纲是三句话：

1. **一轮一 Recorder**：`BusinessChatService` 每收到一轮提问就 `new ConversationTraceRecorder(...)`，绑定 `conversationId + exchangeId + traceId`，贯穿整轮。
2. **埋点零侵入主流程**：所有埋点都是" Recorder 为 null 就跳过、写入失败只 warn"，可观测永远不能拖垮业务。
3. **写读分离**：写入走 Recorder → 两个 MyBatis-Plus Store 落三张表；查询走 Controller → BusinessChatService 门面 → Store 的 `list*()` 方法。

## 二、核心组件与数据表

| 组件 | 位置 | 角色 |
|---|---|---|
| `ConversationTraceRecorder` | `chatagent/service` | **非单例**，每轮对话 `new` 一个；阶段埋点的唯一门面，内部持有两个 Store |
| `ConversationTraceStageStore`（接口）/ `MybatisConversationTraceStageStore` | `chatagent/service` | 阶段记录存取，表 `nexus_agent_chat_exchange_trace_stage` |
| `RetrievalObserveStore`（接口）/ `MybatisRetrievalObserveStore` | `chatagent/service` | 检索观测存取，表 `nexus_agent_chat_retrieval_result` + `nexus_agent_chat_channel_execution` |
| `StageBenchmarkService` | `chatagent/service` | `@Service` 单例；阶段性能基准，表 `nexus_agent_chat_stage_benchmark` |
| `ObservedChatModelService` | `chatagent/service` | LLM 调用包装器，每次调用模型后 `addModelUsageTrace()` 回填 token/耗时 |
| `ConversationTraceStageCode` | `model/trace` | 枚举，11 个阶段码，自带 `order` 字段 |
| `ConversationTraceStageState` | `model/trace` | 枚举，RUNNING(1)/COMPLETED(2)/FAILED(3)/SKIPPED(4) |

**11 个阶段码（按 `order` 排序即时间线展示顺序）：**

| 枚举 | order | 含义 | 埋点位置（已确认） |
|---|---|---|---|
| `MEMORY` | 10 | 会话记忆 | `ChatPreparationOrchestrator` 装载记忆时 |
| `INTENT` | 20 | 意图分析 | 已定义，当前代码无埋点（预留） |
| `REWRITE` | 30 | 问题改写 | `ChatPreparationOrchestrator`（RETRIEVAL 模式） |
| `ROUTE` | 40 | 路由判定 | `ChatPreparationOrchestrator` ×3（开放式 Agent / 自动文档 / 检索判定）+ `ClarificationExecutor`（澄清） |
| `GRAPH_QUERY` | 45 | 结构图查询 | `GraphOnlyExecutor` / `GraphThenEvidenceExecutor` |
| `RAG_RETRIEVE` | 50 | RAG 检索 | `RagChatExecutor`（双通道混合检索） |
| `EVIDENCE_BUDGET` | 60 | 证据评估与预算控制 | `RagChatExecutor`（Prompt 组装） |
| `ANSWER_GENERATE` | 70 | 回答生成 | `RagChatExecutor`（LLM 流式生成） |
| `REACT_AGENT` | 75 | ReAct Agent | `ReactAgentExecutor` |
| `RECOMMENDATION` | 80 | 推荐问题 | `BusinessChatService`（回答完成后） |
| `FINALIZE` | 90 | 收尾归档 | `BusinessChatService` ×3（停止/完成/失败三种收尾） |

## 三、方法清单：参数类型与返回值类型

### 3.1 ConversationTraceRecorder（每轮一个实例）

| 方法 | 参数类型 | 返回值类型 | 职责 |
|---|---|---|---|
| 构造器 | `ConversationTraceStageStore, RetrievalObserveStore, String conversationId, long exchangeId, String traceId` | — | 绑定本轮对话三元组；`modelUsageTraces` 用 `Collections.synchronizedList` 保证并发安全 |
| `startStage(...)` | `ConversationTraceStageCode stageCode, String executionMode, String summaryText, Object snapshot` | `StageHandle`（record：`long stageId, long startTimeMs, ConversationTraceStageCode stageCode`） | 立即落库一条 RUNNING 阶段记录，返回"阶段句柄" |

| `addModelUsageTrace(trace)` | `ChatModelUsageTrace` | `void` | 追加一次 LLM 调用用量（线程安全） |
| `snapshotModelUsageTraces()` | 无 | `List<ChatModelUsageTrace>` | 防御性拷贝（`new ArrayList<>(...)`） |
| `limitStats()` | 无 | `ChatLimitStats` | 可变的限额统计对象（引用直出） |
| `recordRetrievalResults(results)` | `List<RetrievalResultView>` | `void` | 批量存检索结果快照；**catch RuntimeException 只 log.warn**，观测失败不影响主流程 |
| `recordChannelExecutions(executions)` | `List<ChannelExecutionView>` | `void` | 批量存检索通道执行明细；同样吞异常只 warn |
| `conversationId() / exchangeId() / traceId()` | 无 | `String / long / String` | 三元组访问器 |

## 四、执行顺序（写入侧时间线 + 查询侧）

### 4.1 写入侧：一轮对话从创建 Recorder 到归档

```
用户提问进入 BusinessChatService
 ① new ConversationTraceRecorder(stageStore, retrievalStore, conversationId, exchangeId, traceId)
    traceId = UUID（去掉横线）；Recorder 塞进 TaskInfo，随执行上下文贯穿全链路
 ② ChatPreparationOrchestrator.prepare():
      MEMORY   startStage → 装载记忆/摘要 → completeStage
      ROUTE    startStage → 三种路由分支各自埋 → completeStage
      REWRITE  startStage → ChatQueryRewriteService.rewrite(内含 LLM 调用) → complete / fail
 ③ 执行器按路由结果分派（每个执行器各自埋点）:
      RagChatExecutor:        RAG_RETRIEVE → 检索引擎内部两次批量落库
                              (recordChannelExecutions / recordRetrievalResults)
                              → EVIDENCE_BUDGET(Prompt 组装) → ANSWER_GENERATE(LLM 流式)
      GraphOnlyExecutor / GraphThenEvidenceExecutor: GRAPH_QUERY
      ReactAgentExecutor:     REACT_AGENT
      ClarificationExecutor:  ROUTE(澄清场景) + 直接返回
 ④ 每次 LLM 调用（无论哪个阶段）:
      ObservedChatModelService.callText/streamText → traceRecorder.addModelUsageTrace(usage)
 ⑤ 回答流结束后 BusinessChatService 收尾:
      RECOMMENDATION startStage → 生成推荐追问 → completeStage
      snapshotModelUsageTraces() → 写入 debugTrace；limitStats.setModelCallsUsed(...)
      FINALIZE startStage → 归档(完成/停止/失败三种收尾路径) → completeStage
```

### 4.2 查询侧：前端回放一轮对话

```
前端先调 /exchange/detail        → listStageViews  → 得到按 order 排序的阶段时间线
         再调 /exchange/retrieval/results    → 每条候选的得分与闸门明细
         再调 /exchange/channel/executions   → 每个通道的执行耗时
         （运营页可调 /stage/benchmarks      → 各阶段 P50/P90/P99 基准）
```

时间线的关键点：**startStage 在阶段动作"之前"落库，complete/fail 在"之后"凭 StageHandle 关闭**，所以即使进程崩溃，库里也会留下 RUNNING 状态的"僵尸阶段"——这本身就是一种故障信号。

## 六、设计亮点（面试加分点）

1. **句柄模式（StageHandle）**：`startStage` 返回 `(stageId, startTimeMs, stageCode)` 三元组 record，结束方法凭句柄关闭并算耗时。耗时的起点在业务代码开始前就钉死，不会把"构造埋点参数"的时间算进阶段耗时。
2. **观测永不下线、也永不拖垮业务**：三层防护——
   - 调用方侧统一写法 `traceRecorder == null ? null : startStage(...)`（可观测是可选依赖，关闭后主流程零影响）；
   - Recorder 侧 `completeStage/failStage` 对 null 句柄直接 return；
   - 批量落库侧 catch RuntimeException 只 `log.warn`（检索观测挂了不影响回答）。
3. **failStage(Throwable) 重载是排障设计**：自动把 `exceptionClass / errorMessage / stackTrace` 合并进 snapshot JSON，开发者查一条阶段记录就能看到完整堆栈，不用再翻应用日志定位是哪次失败。
4. **线程安全考虑到了流式场景**：`modelUsageTraces` 用 `Collections.synchronizedList`，因为 ANSWER_GENERATE 是 `Flux<String>` 流式回调，LLM 用量可能在多个线程回调中追加。
5. **检索观测做到了"逐候选"粒度**：不只记录"检索到 20 条"，而是每条候选的通道内排名、RRF 融合排名、最终排名、三段得分、闸门是否通过、是否被提升——检索质量回归可以直接拿这批数据做对比。
6. **阶段码带 order 字段**：`MEMORY(10) → FINALIZE(90)` 的序号留了空隙（如 45、75），方便后续插新阶段而不重排；`INTENT` 与 `SKIPPED` 状态已定义但当前埋点未使用，属于预留扩展位。
7. **性能基准的简单务实**：滚动窗口只留最近 200 个样本（防表无限膨胀），每次写入排序重算全部分位数（样本量小，O(n log n) 足够），避免了维护复杂流式分位数结构的成本——这是"数据量级决定算法选型"的好例子。
8. **查询侧三层清晰**：Controller（参数校验）→ BusinessChatService 门面（组装 Detail 视图）→ Store（MyBatis-Plus 查询），写入和读取共用同一个 Store 接口，没有重复的数据访问层。

## 七、面试讲述脚本

### 7.1 30 秒电梯版

> 每轮对话进来时，`BusinessChatService` 会 new 一个 `ConversationTraceRecorder`，绑定 conversationId、exchangeId 和一个 UUID traceId。准备、检索、生成、推荐、收尾这些阶段都通过 `startStage()` 落一条 RUNNING 记录拿到 StageHandle 句柄，结束时 `completeStage()/failStage()` 凭句柄回写状态和耗时。Recorder 内部持有两个 Store：阶段表存时间线，`RetrievalObserveStore` 把每条检索候选的 RRF/rerank 得分和闸门结果、每个通道的执行耗时逐条落库。所有埋点写入失败只打 warn，绝不影响主流程。前端通过 `/api/chat/exchange/detail` 等四个接口回放整轮时间线和检索明细。另有一个 `StageBenchmarkService` 用滚动 200 样本窗口维护各阶段 P50/P90/P99 基准，查询接口已就绪，写入路径目前预留。

### 7.2 3 分钟完整版（按"问题 → 方案 → 细节 → 价值"讲）

> **问题**：Agent 对话链路很长——记忆、改写、路由、检索、预算、生成，每步都可能慢或错，而且是流式响应。出了问题用户只说"回答慢/回答差"，没有埋点就是黑盒；检索质量调优也需要逐条对比候选得分。
>
> **方案**：全链路可观测分三块。第一块是**阶段时间线**：每轮对话一个 `ConversationTraceRecorder`，11 个阶段码枚举（带 order 排序字段），每个阶段 start 时落 RUNNING 记录返回 StageHandle，结束凭句柄回写 COMPLETED/FAILED 加耗时；失败重载方法会自动把异常类名和堆栈合并进快照 JSON。第二块是**检索观测**：`RetrievalObserveStore` 两张表，`retrieval_result` 存每条候选的通道排名、RRF 分、rerank 分、闸门通过情况，`channel_execution` 存每个检索通道的执行耗时和状态。第三块是**性能基准**：`StageBenchmarkService` 按"阶段+执行模式"聚合，JSON 数组滚动保留最近 200 个耗时样本，每次写入排序重算 P50/P90/P99。
>
> **实现细节**（加分段）：
> 1. Recorder 是每轮 new 的轻量对象，不是单例——因为 conversationId/exchangeId/traceId 是轮次维度的；而两个 Store 和 BenchmarkService 是 Spring 单例。LLM 用量列表用 synchronizedList，因为流式回答的用量回调可能并发到达。
> 2. 防护做了三层：调用方 `traceRecorder == null ? null : startStage(...)`，Recorder 对 null 句柄直接 return，批量落库 catch RuntimeException 只 warn——观测是可选依赖，永远不拖垮主流程。
> 3. 每次 LLM 调用由 `ObservedChatModelService` 包装，回填 `ChatModelUsageTrace`（模型、token、耗时），收尾时 snapshot 进 debugTrace，同时更新限额统计的已调用次数。
> 4. 查询侧四个 HTTP 接口：对话详情（含阶段时间线）、检索结果明细、通道执行明细、性能基准，Controller → Service 门面 → Store 三层，读写共用同一套 Store。
>
> **价值**：排障从"翻日志"变成"查一条阶段记录看快照 JSON"（含堆栈）；性能优化有真实分位数数据支撑；检索调优有逐候选得分对比；而且这套埋点可以整体关闭，对主流程零侵入。

## 八、面试追问 Q&A

**Q1：为什么 Recorder 不做成 Spring 单例？**
A：它携带轮次维度会话三元组（conversationId/exchangeId/traceId），天然是请求作用域对象，做成单例反而要引入 ThreadLocal 或参数透传，复杂化。轻量对象每轮 new 的成本可忽略；真正重的资源（数据库连接、Mapper）在单例 Store 里。

**Q2：埋点用的 `System.currentTimeMillis()` 算耗时可靠吗？**
A：够用但有已知局限——它受 NTP 校时影响可能出现负值或跳变。更严谨可用 `System.nanoTime()` 单调时钟。这里阶段耗时是秒级到十秒级，毫秒级校时扰动占比极小，取舍为简单可靠。若被追问"怎么改进"，答：句柄里存 nanoTime，落库时换算。

**Q3：观测数据写库会不会拖慢主流程？**
A：三道防线：埋点对象为 null 直接跳过；finishStage 是单条 UPDATE（有索引主键）；检索批量落库 catch RuntimeException 只 warn。极端情况下即使数据库抖动，最坏影响是一次 warn 日志，回答流程照常。若要求更强，可升级为异步写（队列 + 批量刷盘），代价是崩溃时丢尾部记录。

**Q4：进程崩溃时阶段记录停在 RUNNING 怎么办？**
A：这是有意保留的信号——RUNNING 超过阈值的记录就是"崩溃/中断现场"，可以定期扫描超时 RUNNING 记录标记为 FAILED 或 SKIPPED（枚举里已预留 SKIPPED 状态）。

**Q5：为什么阶段码和状态都用枚举而不是字符串常量？**
A：阶段码枚举带 `code/label/order` 三字段：label 给前端展示中文名，order 决定时间线排序且留了序号空隙（45、75）方便插入新阶段不重排。枚举在编译期防拼写错误，落库存 code 字符串，查询视图再转回中文。

**Q6：StageBenchmark 为什么每次写入都全量重算分位数，而不是增量更新？**
A：样本窗口只有 200 个，排序 200 个元素是微秒级，全量重算保证 P50/P90/P99 永远精确；增量近似算法（如 t-digest）在这个数据量级属于过度设计。滚动窗口同时防了表膨胀——每阶段一行、JSON 数组定长截断。

**Q7：recordRetrievalResults 为什么吞异常而不抛？**
A：检索观测是"锦上添花"数据，写入失败意味着主流程已经在检索或更上游出了问题，再抛异常只会把一个可降级的故障放大成请求失败。观测组件的铁律：自己的故障不能成为业务的故障。

**Q8：如果要加一个新阶段（比如"安全审查"），要改哪些地方？**
A：三步：① `ConversationTraceStageCode` 加枚举（选个空隙序号）；② 在对应业务位置 `startStage/completeStage` 埋点；③ 前端时间线无需改动（按 order 排序、label 自带）。表结构不用动——这就是枚举带 order 字段 + snapshot 用 JSON 柔性结构换来的扩展性。
