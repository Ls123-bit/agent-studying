# SuperAgent(nexus-agent)网络请求部分分析

> 分析对象:`D:\Desktop\SuperAgent\superagent`
> 项目形态:Spring Boot 3.5.6 / Java 17 多模块 Maven 后端(`nexus-agent-*`)+ Vue 3 / Vite 前端(`vue/`)。
> 本文回答一个问题:**这个项目的网络请求是怎么发的、怎么收的**。

```
      │ LLM/Embedding│ │ (RestClient) │ │ (RestClient) │ └──────────┘ └──────────────┘

      ┌──────────────────────────────────────────────────────┐
      │ 基础设施连接(非 HTTP 或专用协议):MySQL(JDBC)、      │
      │ PostgreSQL/pgvector(JDBC)、Redis(Redisson/RESP)、   │
      │ Kafka(自有协议)、Neo4j(Bolt 二进制协议)             │
      └──────────────────────────────────────────────────────┘
```

关键结论:

1. **入站**:后端是 Spring MVC(Tomcat)单体服务,统一监听 **9082** 端口;对话走 **SSE 流式**,其余接口全部是 **POST + JSON**。
2. **出站 HTTP**:业务代码统一用 **Spring 的 `RestClient`**(同步、基于 JDK `HttpURLConnection`),LLM 调用交给 **Spring AI OpenAI starter** 自动装配;没有引入 OkHttp / Feign / WebClient 作为业务客户端。
3. **前端**:完全不依赖 axios,统一封装在 `vue/src/api/api.js` 的 **原生 `fetch`** 上,SSE 也是手写解析器,没有用 `EventSource`。

## 二、后端入站:HTTP 接口与 SSE 流式响应

### 2.1 端口与协议栈

`nexus-agent-business-chat/src/main/resources/application.yaml`:

```yaml
server:
  port: 9082
  servlet:
    encoding:
      charset: UTF-8
      enabled: true
      force: true
```

- 使用 `spring-boot-starter-web`(传统 Servlet 栈 + Tomcat),**不是** WebFlux。
- 但因为引了 `spring-ai-starter-model-openai` 和 `spring-ai-alibaba-agent-framework`,Reactor 在 classpath 上,所以 MVC 控制器可以直接返回 `Flux<T>`,Spring MVC 会自动按流式响应写出。

### 2.2 控制器形态:`BusinessChatController`

`controller/BusinessChatController.java` 全部接口都在 `/api/chat` 下,除流式接口外全部返回统一包裹 `ApiResponse<T>`(`{code, message, data}`,`code === "0"` 表示成功),并且**清一色 POST + JSON body**(连分页、详情查询都不用 GET + path 参数,前端注释明确说是为了避免两套交互风格):

```java
// 唯一的流式接口:对话
@PostMapping(value = "/stream", produces = "text/event-stream;charset=UTF-8")
public Flux<String> stream(@Valid @RequestBody ChatRequestDto dto) {
    return businessChatService.openConversationStream(dto);
}

// 其余接口的统一形态
@PostMapping("/session/list")
public ApiResponse<ConversationSessionListVo> sessions(@RequestBody ...) {
    return ApiResponse.ok(businessChatService.listSessions(dto));
}
```

接口清单:

| 路径 | 作用 | 返回 |
|---|---|---|
| `POST /api/chat/stream` | 对话主链路,SSE 流 | `text/event-stream` 的 `Flux<String>` |
| `POST /api/chat/session/list` / `detail` / `reset` / `stop` | 会话分页/详情/重置/停止 | JSON |
| `POST /api/chat/exchange/detail`、`/exchange/retrieval/results`、`/exchange/channel/executions` | 问答明细与检索观测 | JSON |
| `POST /api/chat/session/summary/rebuild` | 手动重建长期摘要 | JSON |
| `POST /api/chat/stage/benchmarks`、`/document/options` | 阶段基准/知识文档选项 | JSON |

另有管理端 `AdminAuthController`(`POST /admin/auth/login|logout`、`GET /admin/auth/me`)和文档管理接口(见第 2.5 节)。

### 2.3 SSE 流式的产生方式(Reactor Sinks)

这是本项目最核心的一条网络链路。`service/BusinessChatService.java` 的实现模式:

```java
public Flux<String> openConversationStream(ChatRequestDto request) {
    return Flux.defer(() -> openDeferredConversationStream(request));  // 订阅时才启动
}
```

每个对话任务创建一个**单播 Sinks**作为事件总线,所有阶段(改写、检索、ReAct、工具、摘要)都往里推事件:

```java
Sinks.Many<String> sink = Sinks.many().unicast().onBackpressureBuffer();
runnableConfig.context().put(ChatContextKeys.EVENT_SINK, sink);  // 交给 Agent 图的上下文
// ...
private Flux<String> bindClientChannel(TaskInfo taskInfo) {
    return taskInfo.sink().asFlux()
        .doOnSubscribe(ignored -> activateGeneration(taskInfo))  // 客户端订阅时才真正开跑
        .doOnCancel(() -> stopTask(taskInfo, "客户端已取消请求")); // 浏览器断开即停止生成
}
```

事件内容由 `support/StreamEventWriter` 统一序列化成 JSON 字符串,事件类型有:`text`(正文增量)、`thinking`(思考步骤)、`status`、`error`、`reference`(搜索引用)、`recommend`(推荐追问)。

配合机制:

- **并发防护**:同一 `conversationId` 用 Redis 租约(`chat:running:` 前缀,TTL 30s)防重复对话;获取失败直接返回一条 `error` 事件的拒绝 Flux。
- **租约续期**:`Flux.interval(10s)` 每 10 秒续租,流结束即取消。
- **单次运行限流**:`ModelCallLimitHook`(run 8 次 / thread 40 次)与 `ToolCallLimitHook`(run 6 次 / thread 30 次)从源头限制模型与外呼次数。

### 2.4 鉴权与跨域

- 管理端 JWT:登录后发 Bearer Token,`AdminAuthInterceptor` 拦截校验;预览模式(`PreviewModeInterceptor`)可将线上环境降级为只读。
- **没有任何 `@CrossOrigin` / `CorsRegistry` / `CorsFilter` 配置**——后端不做 CORS。跨域问题完全靠前端的开发代理和同源部署解决(见第 4.4 节)。

### 2.5 文档管理接口(入站另一半)

`/manage/**` 提供文档上传( multipart:`file` + JSON `meta` 两段)、策略确认、索引构建、chunk 查询等;上传后真正的"解析→切块→向量化→入库"通过 **Kafka 异步**完成(`DocumentKafkaProducer` → `DocumentKafkaConsumer`,topic 见 `app.manage.kafka.*`),不是 HTTP 回调。

## 三、后端出站:作为 HTTP 客户端发起的请求

### 3.1 统一的 RestClient 工厂:`RestClientFactorySupport`

`support/RestClientFactorySupport.java` 是本项目所有手写 HTTP 客户端的唯一工厂:

```java
public static RestClient create(String baseUrl, int connectTimeoutMs, int readTimeoutMs) {
    SimpleClientHttpRequestFactory requestFactory = new SimpleClientHttpRequestFactory();
    if (connectTimeoutMs > 0) requestFactory.setConnectTimeout(connectTimeoutMs);
    if (readTimeoutMs > 0) requestFactory.setReadTimeout(readTimeoutMs);
    RestClient.Builder builder = RestClient.builder().requestFactory(requestFactory);
    if (StringUtils.hasText(baseUrl)) builder.baseUrl(baseUrl);
    return builder.build();
}
```

要点:
- 底层是 `SimpleClientHttpRequestFactory` → **JDK `HttpURLConnection`**,不依赖 Apache HttpClient / OkHttp。
- 连接与读超时全部**从配置注入**,按"调用方"分别设置。
- `baseUrl` 可传 null(Rerank 就是每请求传完整 URL)。

### 3.2 Tavily 联网搜索工具(ReAct Agent 的外呼)

`tool/TavilySearchTool.java`,在构造器里用工厂建好 `RestClient`,作为 Agent 工具被 LLM 触发:

```java
this.restClient = RestClientFactorySupport.create(
    properties.getBaseUrl(),            // https://api.tavily.com
    properties.getConnectTimeoutMs(),
    properties.getReadTimeoutMs());

TavilySearchApiResponse response = restClient.post()
    .uri(properties.getSearchPath())    // /search
    .header("Authorization", "Bearer " + properties.getApiKey())
    .body(new TavilySearchApiRequest(   // query/topic/search_depth/max_results/include_answer/include_raw_content
        effectiveQuery, topic, properties.getSearchDepth(), ...))
    .retrieve()
    .body(TavilySearchApiResponse.class);   // Jackson 反序列化为 record
```

围绕这次外呼的可靠性设计(都在 `ChatAgentConfiguration`):

- **重试**:`ToolRetryInterceptor`(toolName=`tavily_search`,maxRetries=2,initialDelay 200ms,maxDelay 1200ms,带 jitter)。
- **错误兜底**:`ToolErrorInterceptor` + `TavilyToolInputFallbackInterceptor`(修正模型给工具传的非法入参)。
- **限流**:`ToolCallLimitHook` 限制单 run 6 次 / 单 thread 30 次。
- **观测**:调用过程写入 `ChatToolTrace`(状态 RUNNING/COMPLETED/FAILED、耗时、引用数),同时向 SSE 推送 `thinking` 事件(如"🔍 正在联网搜索: …")。

### 3.3 外部 Rerank HTTP 调用(RAG 精排)

`rag/service/HttpDocumentRerankPostProcessor.java` 实现 Spring AI 的 `DocumentPostProcessor`,在检索后处理阶段同步调用外部精排接口:

```java
restClient = RestClientFactorySupport.create(null, connectTimeoutMs, readTimeoutMs); // 不设 baseUrl

Map<String, Object> response = restClient.post()
    .uri(rerankProperties.getUrl())     // 默认 https://api.siliconflow.cn/v1/rerank
    .contentType(MediaType.APPLICATION_JSON)
    .header("Authorization", "Bearer " + rerankProperties.getApiKey())
    .body(Map.of("model", ..., "query", query.text(), "documents", texts, "top_n", topN, "return_documents", false))
    .retrieve()
    .body(Map.class);
```

调用失败(异常/空结果/未配 key)时**降级为原始排序**,并把 `rerankScore`、`rerankDurationMs` 等写回 Document metadata 供观测。当前 `application.yaml` 中 `app.chat.rag.rerank.enabled: false`,该通道默认关闭。

### 3.4 LLM 调用:Spring AI OpenAI 兼容协议(自动装配,不手写 HTTP)

配置(`application.yaml` → `spring.ai.openai.*`):

```yaml
spring:
  ai:
    openai:
      base-url: https://dashscope.aliyuncs.com/compatible-mode/   # 阿里云百炼的 OpenAI 兼容入口
      api-key: ${OPENAI_API_KEY:...}
      chat:
        options: { model: qwen-plus-latest, temperature: 0.5, maxTokens: 5000 }
      embedding:
        base-url: https://dashscope.aliyuncs.com/compatible-mode/ # 向量模型单独一份,便于以后拆网关
        api-key: ...
        options: { model: text-embedding-v4 }
```

- 依赖 `spring-ai-starter-model-openai`,由 starter 自动装配 `OpenAiChatModel` 与 `OpenAiEmbeddingModel`;**项目里没有一行手写的模型 HTTP 代码**。Spring AI 内部:同步调用走 `RestClient`,流式调用走 `WebClient`(所以代码里能捕获到 `WebClientResponseException`)。
- 同一份密钥/地址同时服务:对话回答、问题改写、推荐追问生成、记忆摘要压缩、embedding 向量化——只是各阶段传不同的 options(例如 rewrite 阶段低温 0.2,并通过 `extraBody` 透传 `thinking: false` 给 DashScope)。
- **供应商兼容层** `support/DashScopeCompatibilityInterceptor`(agent 框架的 `ModelInterceptor`):在每次模型调用外做适配与日志——关闭 `parallelToolCalls`、移除 DashScope 不认的 `streamOptions`、把 DashScope 流式碎片化的 tool_call 按 id 合并,并对请求/响应/流片段做全量结构化日志。
- **Agent 编排**:上层的 ReactAgent(`spring-ai-alibaba-agent-framework`)负责 ReAct 循环、工具执行(checkpoint 持久化在 MySQL),模型调用都经过上述拦截器。

### 3.5 基础设施客户端(带超时配置的专有 SDK)

| 目标 | 客户端 | 传输层 | 关键配置 | 代码入口 |
|---|---|---|---|---|
| Elasticsearch 127.0.0.1:9200 | 官方 `elasticsearch-java` + `RestClientTransport` | 低层 `org.elasticsearch.client.RestClient`(Apache HttpClient) | Basic 认证;connect 3000ms / socket 5000ms | `manage/config/DocumentManageElasticsearchConfiguration.java` |
| MinIO 127.0.0.1:9000 | 官方 `MinioClient`(S3 API) | HTTP | endpoint/accessKey/secretKey;启动时自动建 bucket | `manage/config/DocumentManageMinioConfiguration.java` |
| Neo4j bolt://127.0.0.1:7687 | 官方 `neo4j-java-driver` | **Bolt 二进制 TCP 协议(非 HTTP)** | basic 认证,query-timeout 5s | `manage/config/DocumentManageNeo4jConfiguration.java` |
| Kafka 127.0.0.1:9092 | `spring-kafka` | Kafka 私有协议 | 生产者/消费者序列化、auto-offset-reset | `manage/mq/DocumentKafka*` |
| MySQL 3307 / PG(pgvector) 5433 / Redis 6379 | JDBC / Redisson | 专有协议 | Hikari 池参数等 | `application.yaml` |

其中 ES 客户端的三层组装值得注意(`@ConditionalOnProperty` 控制 enabled):

```java
RestClient.builder(hosts)                       // 低层 REST 客户端
    .setRequestConfigCallback(rb -> rb.setConnectTimeout(3000).setSocketTimeout(5000))
    .setHttpClientConfigCallback(hb -> hb.setDefaultCredentialsProvider(credentialsProvider));
new RestClientTransport(restClient, new JacksonJsonpMapper(objectMapper));  // 传输层
new ElasticsearchClient(transport);             // 类型化 API
```

ES 上跑三类索引:关键词检索(`*-document-keyword`)、结构导航(`*-document-navigation`)、知识路由(`*-knowledge-route`)。

### 3.6 出站请求的共性约定

1. **超时显式化**:每类外呼都有独立的 connect/read 超时配置,没有全局兜底。
2. **密钥可注入**:API key 一律 `${ENV:default}` 形式,支持环境变量覆盖(注:仓库里 `application.yaml` 的默认值内嵌了真实 key,属于安全隐患,建议只留环境变量)。
3. **失败即降级**:Rerank 失败回退原始排序;搜索失败抛回给 Agent 由 `ToolErrorInterceptor` 转成对模型的错误消息;LLM 失败向上冒泡为 SSE `error` 事件。
4. **全链路观测**:外部调用统一计时并写入 trace(`ChatToolTrace`、`rerankDurationMs`、`SuperAgentChatStageBenchmark` 等)。

## 四、前端(Vue 3)的网络请求

### 4.1 唯一入口:`vue/src/api/api.js`(原生 fetch)

项目没有 axios/fetch 封装库,所有请求集中在这一个模块,按能力分四个私有函数:

| 函数 | 用途 | 特点 |
|---|---|---|
| `requestJson` | GET/普通 JSON | 30s 超时,原样返回 JSON |
| `requestApiEnvelope` | 业务 POST | 解析 `{code,message,data}` 包裹,`code!=='0'` 抛 `APIError` |
| `requestMultipartApiEnvelope` | 文件上传 | `FormData`(file + JSON Blob 的 meta),不带 Content-Type 让浏览器自动设 boundary |
| `requestBlob` | 文件下载 | 解析 `content-disposition` 文件名(先 `filename*=UTF-8''` 再普通 `filename`) |

公共行为:

```js
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || ''   // 空则走同源
const REQUEST_TIMEOUT = 30000                                  // AbortController 30 秒
headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${localStorage的admin token}` }
// 401 → 清 token,若在 /admin 页面则跳 /admin/login
```

API 按域分组导出:`chatApi`(对话/会话/观测)、`adminAuthApi`(登录登出)、`manageApi`(文档管理,全部字段过 `stringifyManageValue` 把数值转字符串再提交)。

### 4.2 SSE:手写流解析(不用 EventSource)

因为需要 **POST + JSON body + Authorization 头**,浏览器原生 `EventSource`(只支持 GET、不能带自定义头)不可用,所以前端用 `fetch` + `ReadableStream` 自己解析 SSE:

```js
openStream(payload, handlers = {}) {
  const response = await fetch(buildApiUrl('/api/chat/stream'), {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Accept: 'text/event-stream', ...buildAuthHeaders() },
    body: JSON.stringify(payload),
    signal: controller.signal          // “停止生成”按钮就是 controller.abort()
  })
  await consumeEventStream(response.body, handlers)
}
```

解析器 `consumeEventStream` 的流程:

1. `stream.getReader()` 循环 `read()`,用 `TextDecoder('utf-8')` 以 `{stream: true}` 增量解码,手工维护 buffer;
2. 以空行(`/\r?\n\r?\n/`)切分 SSE 事件块,块内取所有 `data:` 行拼接(处理多行 data);
3. 每个载荷 `JSON.parse` 后交给 `handlers.onEvent`,忽略 `[DONE]` 哨兵;解析失败抛带原文的 `APIError`。

事件类型与后端 `StreamEventWriter` 一一对应:`text / thinking / status / error / reference / recommend`。

注意:该 POST 流**没有 30s 超时**(只受 AbortController 手动控制),符合长流式对话的预期。

## 五、ai-example 教学模块的额外姿势(非主链路)

`ai-example/` 是配套教学示例,网络姿势与主项目不同,可作对照:

- **OkHttp 直连大模型**:`ai-example-one` 的 `LLMClient` / `LLMStreamClient` / `ConversationClient` 用 OkHttp 手工调 SiliconFlow `/v1/chat/completions`,自配 connect/read/write/call 四级超时,自己解析 SSE 达成"打字机"效果——展示"没有框架时怎么做"。
- **MCP 客户端传输层**:`ai-example-mcp/ai-example-spring-ai-office-mcp-client` 演示两种 MCP 传输:
  - `HttpClientSseClientTransport`(SSE 长连接,`/sse` 端点);
  - `HttpClientStreamableHttpTransport`(Streamable HTTP,新规范)。
  底层都是 JDK HttpClient,由 Spring AI MCP 封装。
- `ai-example-rag`、`ai-example-spring-ai(-alibaba)` 则演示如何用 Spring AI 的模型/RAG 抽象发请求(与主项目同思路)。
