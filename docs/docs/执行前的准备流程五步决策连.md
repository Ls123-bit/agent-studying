# 执行前的准备流程（五步决策链）

> 项目：superagent-understanding（企业级 AI Agent 知识问答系统）
> 核心模块：`nexus-agent-business/nexus-agent-business-chat`
> 核心思想：**请求进来之后不是直接丢给大模型，而是先经过一系列准备工作，决定"该怎么回答这个问题"，再把决策结果组装成一份执行计划（ExecutionPlan），交给对应的执行器。**

---

## 一、总览：这条链在解决什么问题

用户的一个提问可能属于完全不同的回答路径：

- 闲聊/天气/新闻 → 应该走开放式 ReAct Agent，不需要检索知识库；
- "第3章包含哪些小节" → 只查文档结构图就能回答，根本不用向量检索；
- "3.2 节的第 2 步是什么" → 先用结构图定位章节，再取正文证据；
- "为什么这个方案更优" → 典型的检索问答（RAG）；
- "帮我对比一下 A 和 B" → 问得太模糊，连该查哪份文档都不确定 → 应该先反问用户澄清。

如果所有请求都无脑走"向量检索 + 大模型"，会导致：检索浪费、答案错误、体验差。**五步决策链就是一个"请求预审流水线"**，在真正调用大模型之前完成 5 次决策：

| 步骤 | 功能 | 核心类 | 关键方法 | 返回的决策产物 |
|---|---|---|---|---|
| 总入口 | 准备流程总编排 | `ChatPreparationOrchestrator` | `prepare()` | `ConversationExecutionPlan` |
| 第 1 步 | 会话记忆加载 | `ConversationMemoryService` | `loadMemoryContext()` | `ConversationMemoryContext` |
| 第 2 步 | 问题改写与拆分 | `ChatQueryRewriteService` | `rewrite()` | `RagRewriteResult` |
| 第 3 步 | 知识路由（三层漏斗） | `KnowledgeRouteServiceImpl` | `route()` | `KnowledgeRouteDecision` |
| 第 4 步 | 文档问题路由 | `DocumentQuestionRouter` | `route()` | `DocumentNavigationDecision` |
| 第 5 步 | 执行计划装配 | `BusinessChatService` | `prepareExecutionPlan()` | `ConversationExecutionPlan` |

## 二、调用关系与执行顺序

### 2.1 前置链路：请求如何走到五步决策链（BusinessChatService 内部）

```
openConversationStream(ChatRequestDto)                    对外入口，返回 Flux<String>（SSE 流）
  └─ openDeferredConversationStream(request)
       ├─ buildLaunchPlan(request)            → StreamLaunchPlan   解析参数/解析文档/取当前日期
       ├─ claimConversationLease(launchPlan)  → boolean            Redis 租约，同一会话防并发
       └─ bootstrapConversation(launchPlan)   → BootstrapResult
            ├─ conversationArchiveStore.startExchange(...)         落库开启一轮问答交换
            ├─ createTaskInfo(launchPlan, exchangeView) → TaskInfo 打包本次请求全部上下文
            ├─ chatRuntimeRegistry.register(taskInfo)              注册运行时（二次防并发）
            └─ bindClientChannel(taskInfo) → Flux<String>
                 └─ 客户端订阅时触发 activateGeneration(taskInfo)
                      └─ buildConversationExecution(taskInfo)
                           └─ Mono.fromCallable(() -> prepareExecutionPlan(taskInfo))
                                  .subscribeOn(Schedulers.boundedElastic())   ← 关键：切到弹性线程池阻塞执行
```

**两个必须能讲清楚的点：**
1. **响应式与阻塞代码的隔离**：整条链路是 Reactor 流（`Flux<String>` 向前端推 SSE），但五步决策链是同步阻塞代码（要查库、调 LLM），所以用 `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())` 把它隔离到弹性线程池，不阻塞事件循环。
2. **两层防并发**：先抢 Redis 租约（跨实例），再在内存 `chatRuntimeRegistry` 注册（进程内），任一失败都直接返回"该会话正在执行中"。

### 2.2 五步决策链主流程（ChatPreparationOrchestrator.prepare 内部）

`prepare(TaskInfo)` 按顺序执行，**其中有两处"短路分支"**：

```
prepare(taskInfo)
 │
 ├── 第1步 会话记忆加载
 │     summarizeHistory(conversationId, traceRecorder)
 │       └─ conversationMemoryService.loadMemoryContext(conversationId, traceRecorder)
 │     随后在本类内做三次加工：
 │       ├─ buildHistoryPlanningContext(memoryContext)   → 规划用结构化上下文
 │       ├─ buildPlanningHistory(...)                    → 给改写/路由用的 historySummary 文本（带字符预算裁剪）
 │       └─ buildAnswerHistoryContext(...)               → 给最终回答用的近期问答上下文
 │           └─ answerHistoryContextAssembler.assemble(question, answerRecentTranscript)
 │
 ├── 【短路分支 A】chatMode == OPEN_CHAT（开放式提问）？
 │     └─ 是 → 直接返回 mode = REACT_AGENT 的执行计划（跳过第 2~4 步）
 │             顺带用 TimeSensitiveQueryHelper 判断是否需要时间锚定/新鲜搜索
 │
 ├── （校验：RAG 编排开关 properties.isEnabled()；DOCUMENT 模式必须带 selectedDocumentId/selectedTaskId）
 │
 ├── 第2步 问题改写与拆分
 │     chatQueryRewriteService.rewrite(question, historySummary, traceRecorder)
 │
 ├── 第3步 知识路由（三层漏斗） —— 仅 AUTO_DOCUMENT（自动文档）模式执行
 │     knowledgeRouteService.route(question, rewriteQuestion)
 │     knowledgeRouteService.recordAutoRoute(...)                 路由痕迹落库（auto 模式）
 │     （DOCUMENT 指定文档模式则改为 recordShadowRoute(...)，影子记录用于离线评估）
 │     selectAutoCandidates(routeDecision, question, rewriteQuestion)   生成候选文档列表
 │     shouldAskClarification(routeDecision, candidateDocuments)
 │     ├── 【短路分支 B】需要澄清？
 │     │     └─ 是 → 直接返回 mode = CLARIFICATION 的执行计划（不检索不生成，反问用户）
 │     └─ 否 → 用 top 候选覆盖 routedDocumentId/routedTaskId
 │
 ├── 第4步 文档问题路由
 │     documentQuestionRouter.route(routedDocumentId, question, rewriteResult)
 │     → 输出 ExecutionMode：GRAPH_ONLY / GRAPH_THEN_EVIDENCE / RETRIEVAL
 │
 └── 第5步 执行计划装配
       basePlan(...)  构建带全部公共字段的 builder
       .mode(executionMode).navigationDecision(...).rewriteQuestion(...).retrievalDocumentIds(...)...
       .build()  → ConversationExecutionPlan
```

### 2.3 后置链路：计划装配后的收尾与执行器分发（仍在 prepareExecutionPlan 中）

`BusinessChatService.prepareExecutionPlan(TaskInfo)` 是第 5 步"装配"的落点，它做三件事：

1. 调 `chatPreparationOrchestrator.prepare(taskInfo)` 拿到计划（前四步都在这次调用里完成）；
2. `buildAgentQuestion(executionPlan)` 设置最终给 Agent/执行器的问题文本；若知识路由改变了目标文档，还会 `conversationArchiveStore.refreshSessionScope(...)` 刷新会话文档范围，并把文档 ID/任务 ID 写入 `RunnableConfig` 上下文；
3. `initializeDebugTrace(executionPlan)` 初始化调试追踪，`taskInfo.setExecutionPlan(plan)` 挂回任务对象。

之后回到响应式链路：

```
plan.getMode() → conversationExecutorRegistry.get(mode) → executor.execute(taskInfo)
   RETRIEVAL           → RagChatExecutor            向量+关键词混合检索、RRF 融合、流式生成
   GRAPH_ONLY          → GraphOnlyExecutor           只查结构图直答
   GRAPH_THEN_EVIDENCE → GraphThenEvidenceExecutor   图定位后取证据
   REACT_AGENT         → ReactAgentExecutor          开放式 Agent 推理+工具调用
   CLARIFICATION       → ClarificationExecutor       直接输出澄清话术
```

### 2.4 每一步内部的调用细节

**第 1 步 `PersistentConversationMemoryService.loadMemoryContext`（记忆的双层结构）**
- 未开启摘要功能：只拉最近 N 轮原文（`conversationArchiveStore.listRecentExchanges`），渲染出 `recentTranscript` 与 `answerRecentTranscript`；
- 开启摘要功能：先 `refreshSummaryIfNecessary(...)` 按需刷新长期摘要（落库 `super_agent_chat_memory_summary`），再读取 `summaryPayload`（会话目标/已确认事实/待跟进问题/检索提示）+ 最近几轮原文，组装为 `ConversationMemoryContext`。
- 这就是"**摘要 + 近期窗口**"的记忆分层：老对话压成摘要省 token，近几轮保留原文保细节。

**第 2 步 `ChatQueryRewriteService.rewrite`（LLM 改写 + 三重兜底）**
1. `needsRewrite()`：无历史时问题 <8 字、有历史时 <18 字、或看起来是多问题（多个问号/分号/换行/编号/“分别”）才触发改写——**短问题才需要补上下文，长问题不动**，省一次 LLM 调用；
2. 触发则渲染 `CHAT_QUERY_REWRITE` prompt（带历史），经 `observedChatModelService.callText("rewrite", ...)` 调 LLM；
3. `parse()` 解析 JSON `{rewrite, should_split, sub_questions}`；
4. `normalizeRewriteResult()` 做保守结构校验：LLM 说要拆、但原文没有明确多问结构 → 强制收敛回单问题（防 LLM 过度拆分）；
5. LLM 失败/结果不可用 → `fallback()` → `ruleBasedSplit()` 按 `?？；;\n` 规则切分。**任何情况下都有确定性的 RagRewriteResult 返回**。
6. 子问题数超过 `maxSubQuestions` 配置时截断。

**第 3 步 `KnowledgeRouteServiceImpl.route`（Scope→Topic→Document 三层漏斗）**
1. `buildQueryContext()`：拼接原问题+改写问题 → `tokenize()` 分词（含中文 n-gram 扩展，最多 40 词）→ `embedSingle()` 向量化 → `RouteQueryContext`；
2. `rankScopes()`：第一层，对知识域节点打分（**语义余弦分为主分** + ES 词法辅助分 + 实体关键词加分），取 Top5；无域节点时从文档元数据推导；
3. `rankTopics()`：第二层，对话题节点打分，命中候选域的话题 +8 分，取 Top8；无话题节点时从文档画像的 coreTopics 推导；
4. `rankDocuments()`：第三层，对可检索文档打分，属于 top 域 +15 分、与 top 话题有关系表加权（relationScore×20），取 Top5；
5. `resolveConfidence()`：`top / max(10, top+second+5)` 归一化成 `BigDecimal` 置信度；
6. 状态判定：无候选 → `FAILED`；置信度 <0.55 → `LOW_CONFIDENCE`；否则 `SUCCESS`。
- 每层打分公式统一为：`semanticMainScore(语义) + lexicalAssist(词法) + keywordEntityAssist(实体词)`，语义分要经过 `≤0.20 归零、(s-0.20)×50` 的非线性放大。

**第 4 步 `DocumentQuestionRouter.route`（规则优先、LLM 兜底的三分类）**
1. `detectQuestionIntent()`：一次本地规则判断出 5 个意图维度（是否找编号项 / 是否分析型 / 是否问目录 / 是否问正文内容 / 是否有结构线索），其中结构直答意图走 `detectGraphOnlyIntentByRules()`（相邻章节、章节编号+方向词、引号标题+方向词、目录展开等规则）；
2. 本地规则置信不足且存在"结构导航线索"时，`classifyQuestionIntentWithModel()` 调 LLM 兜底分类，**置信度 ≥0.75 才接受 GRAPH_ONLY，否则一律回退 RETRIEVAL**；
3. 决策优先级：
   - 单问题 + 命中结构直答 → `GRAPH_ONLY`（只查结构图，不检索不生成长答案）；
   - 命中"第几步/第几条"编号项且非分析型 → `GRAPH_THEN_EVIDENCE`（图定位后取证）；
   - 其余 → `RETRIEVAL`（混合检索；若有结构线索，先 `resolveSection()` 定位章节作为**软提示**辅助检索）；
4. `resolveSection()` 的章节定位四级降级：章节编号正则（`3.2`、`第三章`）→ 导航索引检索 → 本地标题短语打分（路径 100+/标题 90+/锚点 80+）→ `graphService.findBestSection()` 兜底。

**执行顺序总结成一句话（面试可直接用）：**
> prepare() 串行执行：先装载"摘要+近期窗口"的会话记忆（第1步），开放式提问直接短路到 REACT_AGENT；否则用记忆改写问题（第2步），再用三层漏斗把问题路由到具体文档（第3步，AUTO_DOCUMENT 模式；歧义时短路到 CLARIFICATION），然后在选定文档内判断走图直答/图定位取证/混合检索（第4步），最后把所有决策结果装配成 ConversationExecutionPlan（第5步），由执行器注册表按 mode 分发执行。

## 五、面试讲述指南

### 5.1 30 秒电梯版

> "我们的 AI 问答请求不是直接丢给大模型的。入口是 `ChatPreparationOrchestrator.prepare()`，它串一条五步决策链：**先装会话记忆**（长期摘要+最近几轮原文），**再改写问题**（把指代补全、拆成适合检索的子问题），**然后知识路由**（Scope→Topic→Document 三层漏斗定位到具体文档），**再做文档问题路由**（判断走结构图直答、图定位取证还是混合检索），最后**把所有决策装配成一份 ConversationExecutionPlan**，由执行器注册表按 ExecutionMode 分发到五种执行器。其中开放式提问和路由歧义各有一个短路分支，分别直接走 ReAct Agent 和反问澄清。"

### 5.2 2~3 分钟标准版（按时间顺序讲）

1. **为什么要有这条链**（先讲动机）：用户问题路径差异极大——闲聊、问目录结构、问具体步骤、分析型提问、模糊提问，如果全部无脑走向量检索+大模型，会检索浪费、答非所问。所以我们在执行前用一条决策链决定"该怎么答"。
2. **入口与并发控制**：`BusinessChatService.openConversationStream` 是 SSE 入口，先 Redis 租约+内存注册表两层防同会话并发；决策链是同步阻塞代码，用 `Mono.fromCallable + boundedElastic` 隔离进弹性线程池，不阻塞 Reactor 事件循环。
3. **第 1 步 记忆**：`loadMemoryContext` 返回"长期摘要 + 最近 N 轮原文"双层结构——老对话被异步压缩成结构化摘要（会话目标/已确认事实/待跟进问题/检索提示），近几轮保留原文。同一份记忆还按用途裁出三个视图：给改写用的 historySummary（带字符预算裁剪）、给最终回答用的 answerRecentTranscript、结构化的 HistoryPlanningContext。
4. **第 2 步 改写**：不是每次都调 LLM——只有短问题（有历史 <18 字、无历史 <8 字）或明确多问题才改写；LLM 输出 JSON `{rewrite, should_split, sub_questions}`，代码层做保守校验：LLM 说要拆但原文没有多问结构就强制收敛，LLM 挂了就回退正则切分，**保证任何情况都有确定性结果**。
5. **第 3 步 知识路由**：AUTO_DOCUMENT 模式（用户不指定文档）才走。三层漏斗逐层收窄：域 Top5 → 话题 Top8 → 文档 Top5。每层打分 = 语义余弦主分（非线性放大）+ ES 词法辅助分 + 实体词加分，上层结果给下层加权（top 域 +15 分，top 话题关系分 ×20）。置信度用 `top/max(10, top+second+5)` 归一化：<0.55 标记 LOW_CONFIDENCE 并保守扩范围；候选分差 ≤3 且跨域就短路成 CLARIFICATION 反问用户，**宁可多问一句也不猜错文档**。指定文档的 DOCUMENT 模式则跑"影子路由"（recordShadowRoute）只记日志不生效，用于离线对比评估路由准确率。
6. **第 4 步 文档问题路由**：在选定文档内做三分类。本地规则优先（相邻章节词、章节编号、目录展开、'第几步'编号项），规则不够再 LLM 兜底且**置信度 ≥0.75 才允许 GRAPH_ONLY，否则一律回退 RETRIEVAL**——图直答虽省 token 但答错很伤体验，所以入口收紧。结构定位有四级降级：编号正则→导航索引→本地标题打分→图服务兜底。
7. **第 5 步 装配**：`basePlan()` 把记忆、改写结果、路由候选、执行模式、无证据兜底话术等 30 多个字段装进 `ConversationExecutionPlan`；`prepareExecutionPlan()` 再补 agentQuestion、刷新会话文档范围、初始化调试追踪。最后 `executorRegistry.get(plan.getMode())` 分发到五种执行器真正干活。

### 5.3 高频深挖问题与答法

**Q1：为什么改写要在记忆之后？（步骤顺序能否调换？）**
> 不能。改写 prompt 里必须注入 historySummary，否则"那它的第3步是什么"这种指代型问题改不出来——正是先加载记忆才知道"它"指什么。同理知识路由用的是"原问题+改写问题"双文本，改写质量直接影响路由命中率。

**Q2：为什么有两条路由？知识路由和文档问题路由的区别？**
> 正交的两件事。知识路由（第3步）回答"**查哪份文档**"——跨文档的范围决策；文档问题路由（第4步）回答"**在这份文档里怎么查**"——执行模式决策（结构图/图+证据/混合检索）。一个管 horizontal 定位，一个管 vertical 策略。

**Q3：CLARIFICATION 短路的触发条件是什么？**
> `shouldAskClarification()`：候选为空、路由无文档结果、置信度 <0.55，或**前两名分差 ≤3 分且分属不同知识域**——最后一条是关键：分数接近还跨域说明模型在两个答案间"摇摆"，此时反问用户的成本远低于答错的成本。

**Q4：LLM 调用失败会不会让整条链挂掉？**
> 不会，两处 LLM 调用（改写、路由意图兜底）都有降级：改写失败回退正则切分（原问题也能当 retrievalQuestion 用）；路由意图 LLM 失败回退本地规则结果。整条链只有在"参数非法、RAG 开关未开、DOCUMENT 模式缺文档"这类编程性错误时才抛异常。

**Q5：怎么观测这条链的运行情况？**
> 两个手段：① `ConversationTraceRecorder` 在 MEMORY/REWRITE/ROUTE 三个阶段 startStage/completeStage/failStage 埋点，每阶段带快照数据（改写前后问题、路由置信度、候选数等），前端可实时展示决策过程；② 知识路由每次都落库 `super_agent_knowledge_route_trace` 表，auto 模式记实际生效结果，DOCUMENT 模式记影子路由，可离线统计"用户指定文档 vs 路由推荐文档"的命中率来评估路由质量。

**Q6： EXECUTION_MODE 有哪些？分别谁在用？**
> GRAPH_ONLY（GraphOnlyExecutor，只查结构图直答，不生成长答案，最省 token）；GRAPH_THEN_EVIDENCE（GraphThenEvidenceExecutor，先图定位章节再取编号项/正文证据）；RETRIEVAL（RagChatExecutor，向量+关键词检索、RRF 融合、流式生成，最常用）；REACT_AGENT（ReactAgentExecutor，开放式问题，Agent 自主推理+调工具）；CLARIFICATION（ClarificationExecutor，不检索不生成直接反问）；RAG_CHAT 已废弃仅兼容旧数据。
> ⚠️ 注意纠偏：图片里说文档问题路由判断"RAG/图结构/开放问答"——精确说 **REACT_AGENT（开放问答）不是 DocumentQuestionRouter 决定的**，它是 chatMode==OPEN_CHAT 在 prepare() 开头短路决定的；DocumentQuestionRouter 只决定 GRAPH_ONLY / GRAPH_THEN_EVIDENCE / RETRIEVAL 三种。面试时说准这一点是加分项。

### 5.4 可复用的设计亮点句式

- "整条链是**决策与执行分离**的：prepare() 只产出数据不执行，ExecutionPlan 是纯数据载体，执行器是无状态分发的——好处是每一步可以独立测试、独立演进。"
- "**短路优先**：能不走的步骤绝不停留在链路上，OPEN_CHAT 和 CLARIFICATION 两个早返回让最常见/最危险的路径最快结束。"
- "**规则优先、LLM 兜底、再规则托底**的三明治结构：改写和路由都遵循'本地规则能判就不调 LLM，LLM 判不了就回退规则'，兼顾成本与确定性。"
- "**置信度驱动的保守策略**：0.55 是'敢不敢自己答'的门槛，0.75 是'敢不敢图直答'的门槛，0.80 是'候选收多窄'的门槛——所有阈值都有明确的业务语义。"
- "**全程可观测**：trace 埋点 + 路由痕迹落库 + 影子路由，任何一次回答都能回放'当时为什么这么决策'。"
