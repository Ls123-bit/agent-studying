# 知识路由（三层漏斗）

> 当系统中有多个知识库/多份文档时，怎么判断用户的问题该去哪个知识库找答案？这就是知识路由干的事。
> 本文基于源码分析：`KnowledgeRouteServiceImpl`、`ElasticsearchKnowledgeRouteIndexService`、`KnowledgeManageServiceImpl` 三个核心类。

---

## 一、一句话业务概述

用户提问后，系统**先不改写不检索**，而是先回答"这个问题应该去哪份文档/哪个知识域找答案"：
按 **知识域 Scope → 主题 Topic → 文档 Document** 三层逐级收窄候选（漏斗），最终选出 Top-N 候选文档，交给后续 RAG 检索去用。同时通过**影子路由**持续观测"自动路由 vs 用户手选文档"的命中率，用数据驱动路由质量优化。

| 功能 | 核心类 | 关键方法 | 一句话说明 |
|---|---|---|---|
| 三层路由决策 | `KnowledgeRouteServiceImpl` | `route()` | Scope→Topic→Document 逐层筛选 |
| 路由索引 | `ElasticsearchKnowledgeRouteIndexService` | `search()` 等 | 基于 ES 的路由候选词面索引 |
| 影子路由（质量观测） | `KnowledgeRouteServiceImpl` | `recordShadowRoute()` | 用户手动选文档时，后台静默跑一次路由做对比 |
| 知识域管理 | `KnowledgeManageServiceImpl` | CRUD 方法 | Scope 和 Topic 的增删改查 |

## 二、核心类与职责（先记住这张角色表）

| 类 | 层次 | 职责 |
|---|---|---|
| `ChatPreparationOrchestrator` | 聊天编排层 | 聊天准备阶段的编排器，**是 route() 的唯一业务调用方**，根据路由结果决定"直接锁定文档 / 反问澄清" |
| `KnowledgeRouteService` → `KnowledgeRouteServiceImpl` | 路由决策层 | 三层漏斗打分排序 + 路由轨迹落库（auto/shadow 两种模式） |
| `KnowledgeRouteIndexService` → `ElasticsearchKnowledgeRouteIndexService` | 路由索引层 | 把 Scope/Topic/Document 三类实体刷成 ES 快照文档，提供词面（lexical）候选检索 |
| `KnowledgeRouteElasticsearchIndexInitializer` | 索引初始化 | 应用启动时 `@PostConstruct` 创建 ES 路由索引（IK 分词，失败回退 standard） |
| `KnowledgeManageService` → `KnowledgeManageServiceImpl` | 知识域管理层 | Scope/Topic/主题-文档关系/文档画像/路由轨迹的 CRUD，Controller 直接对接 |
| `DocumentManageServiceImpl` | 文档管理层 | 删除文档时联动清理 ES 路由索引（调 `deleteDocumentRoute`） |

**数据模型三要素（三层漏斗的三层各对应一类数据）：**

- `SuperAgentKnowledgeScopeNode`（知识域节点：scopeCode/scopeName/描述/别名/示例）
- `SuperAgentKnowledgeTopicNode`（主题节点：topicCode/topicName/**scopeCode 归属**/回答形态/执行偏好）
- `SuperAgentDocument` + `SuperAgentDocumentProfile`（文档及其 LLM 画像：摘要/核心主题/示例问题）
- 关联表 `SuperAgentTopicDocumentRelation`（topic ↔ document，带 relationScore）
- 轨迹表 `SuperAgentKnowledgeRouteTrace`（路由过程全量留痕，表 `nexus_agent_knowledge_route_trace`）

**输出模型（都是简单 POJO，字段见第四节）：**
`KnowledgeRouteDecision`（决策总出口） ⊃ `ScopeRouteCandidate` / `TopicRouteCandidate` / `DocumentRouteCandidate` 三种候选。

## 三、方法调用关系与执行顺序

### 3.1 主链路：聊天自动路由（chatMode = AUTO_DOCUMENT）

触发入口在 `ChatPreparationOrchestrator.prepare(TaskInfo)`，执行顺序：

1. **装载会话记忆**（`summarizeHistory`）→ **问题改写**（`chatQueryRewriteService.rewrite`）得到 `rewriteQuestion`。
2. 判断 `chatMode == AUTO_DOCUMENT`（用户没指定文档，让系统自动挑）时：
   - 调 `knowledgeRouteService.route(question, rewriteQuestion)` → 得到 `KnowledgeRouteDecision`；
   - 紧接着调 `knowledgeRouteService.recordAutoRoute(...)` 把本次自动路由结果写入轨迹表（mode=`auto`）；
   - `selectAutoCandidates()` 挑候选（置信度 ≥0.80 取 3 个，否则取 5 个；低置信度会合并文档元数据兜底候选）；
   - `shouldAskClarification()` 判断是否反问澄清：**无候选 / 决策为空 / 置信度 <0.55 / Top2 分差 ≤3 且分属不同知识域** → 返回 `CLARIFICATION` 执行计划，把候选文档作为选项让用户选；
   - 否则置信度 ≥0.55 时锁定 Top1 文档（documentId + lastIndexTaskId），交给后续 `documentQuestionRouter.route()` 判定图查询还是混合检索。
3. 若 `chatMode == DOCUMENT`（用户手动选了文档）：**不走 route() 参与决策**，只调 `recordShadowRoute()` —— 后台静默跑一次完整路由并与用户手选文档对比落库（mode=`shadow`，并记录手选文档是否落在自动路由 Top3 内，即 `hitSelectedDocument`）。

### 3.2 route() 内部：三层漏斗执行顺序（面试重点）

```
route(question, rewriteQuestion)
 ① buildQueryContext()          —— 准备查询上下文（一次向量 + 一次分词）
 ② rankScopes()                 —— 第 1 层：知识域候选 Top5
 ③ rankTopics(ctx, scopes)      —— 第 2 层：主题候选 Top8（吃第 1 层结果加权）
 ④ rankDocuments(ctx,scopes,topics) —— 第 3 层：文档候选 Top5（吃第 1/2 层结果加权）
 ⑤ resolveConfidence()          —— 由 Top1/Top2 文档分差算置信度
 ⑥ 判定 routeStatus             —— FAILED / LOW_CONFIDENCE(<0.55) / SUCCESS
 ⑦ resolveDecisionReason()      —— 生成可解释的决策理由
```

**① 查询上下文准备 `buildQueryContext(question, rewriteQuestion)`**

- `buildRoutingText()`：原始问题 + 改写问题拼接（有一方为空取另一方，相同则去重）；
- `tokenize()`：按标点/连接词切词，长度 ≥2 的词保留，并对 ≥4 字的词做 **2~6 元中文 n-gram 扩展**，最多保留 40 个词元；
- `embedSingle()`：把整句路由文本喂给 `EmbeddingModel` 生成 `float[]` 查询向量。**拿不到模型或向量失败时返回 null —— 全链路自动降级为纯词面匹配**（内部用 `semanticEnabled()` 判断）。
- 若词元为空（问题为空），直接返回 `routeStatus=FAILED` 的决策。

**② 第 1 层 Scope：`rankScopes(queryContext)` → Top5 知识域候选**

- 查 `SuperAgentKnowledgeScopeNode` 全量有效节点；**表为空时兜底 `deriveScopesFromDocuments()`**，直接从文档元数据反推出知识域；
- 三路打分（所有层共用同一打分骨架）：
  - **语义主分** `semanticMainScore`：候选文本批量 embed（`computeSemanticScores`，批大小 10）后与查询向量算余弦相似度，`>0.20 才计分 = (cos-0.20)*50`；
  - **词面辅助** `lexicalAssist`：ES 索引检索分 `×1.6`，**封顶 10 分**（辅助信号不许喧宾夺主）；
  - **实体词辅助** `keywordEntityAssist`：查询中的英文/数字/短词（≤4字）命中候选文本，每个 +6；
- `buildScopeCandidates()` 汇总三路分数 → 按分排序取 Top5。

**③ 第 2 层 Topic：`rankTopics(queryContext, scopeCandidates)` → Top8 主题候选**

- 查 `SuperAgentKnowledgeTopicNode`；空表兜底 `deriveTopicsFromProfiles()`（从文档画像 coreTopics 反推主题）；
- 同样三路打分；**若主题所属 scopeCode 命中第 1 层的候选集合，直接 +8 分** —— 这就是"漏斗"的含义：上层结果为下层加权，而非硬过滤（硬过滤会因上游误杀而全盘皆输）。

**④ 第 3 层 Document：`rankDocuments(queryContext, scopeCandidates, topicCandidates)` → Top5 文档候选**

- `listRetrievableDocuments()`：只取 `status=有效 且 indexStatus=索引构建成功 且 lastIndexTaskId 非空` 的文档（没建好索引的文档没有资格被路由到）；
- `buildDocumentRouteMaterial()`：把文档名/知识域/业务分类/标签/画像摘要/核心主题/示例问题拼成路由文本参与语义打分；
- 加权规则：
  - 文档的 knowledgeScopeCode == 第 1 层 Top1 scope → **+15 分**；
  - 文档在 `SuperAgentTopicDocumentRelation` 中关联第 2 层 Top1 topic → **+relationScore×20 分**；
  - 分数 ≤0 且语义不可用时输出 0 分候选（reason="未命中路由关键词"），保证候选可解释。

**⑤⑥⑦ 收口**

- `resolveConfidence(documents)`：`Top1分 / max(10, Top1分+Top2分+5)` —— Top1 断层领先时趋近 1，Top2 咬得紧时显著下降，是一个"头部集中度"归一化指标；
- 状态机：候选为空→`FAILED`；置信度 <0.55→`LOW_CONFIDENCE`；否则 `SUCCESS`。

### 3.3 词面索引链路（ES，路由的第二信号源）

- 启动时：`KnowledgeRouteElasticsearchIndexInitializer.initIndex()`（`@PostConstruct`）建索引，IK 分词失败回退 standard；
- 每次检索：`KnowledgeRouteServiceImpl.searchLexicalScores()` 通过 `ObjectProvider` 拿到 `ElasticsearchKnowledgeRouteIndexService`（**ES 未启用时拿不到 Bean，返回空列表，路由照常工作**）→ `search(routingText, entityType, size)`：
  1. `refreshIfNeeded()`：**5 秒节流 + AtomicLong CAS**，只让一个线程触发 `refreshAll()` 全量重建（deleteByQuery 清空 → buildIndexRecords() 从 5 张表拼快照 → bulk 写入并 `Refresh.WaitFor`）；
  2. `extractEntityTerms()` 抽取英文/数字实体词；
  3. bool 查询：`filter(entityType=scope/topic/document)` + should（`matchPhrase(displayName, boost=12)`、`multiMatch(displayName^10, aliases^8, examples^6, summary^5, routeText^4, description^3)`、逐个实体词 `term(entityTerms, boost=9)`），`minimumShouldMatch=1`，size 截断到 [1,10]；
  4. ES 异常时 catch 住返回空列表并打 warn —— **词面信号缺失，退回语义+关键词打分，不阻断路由**。
- 文档删除时：`DocumentManageServiceImpl` → `deleteDocumentRoute(documentId)` 精准删除该文档的快照（entityType=document 且 documentId 匹配）。

### 3.4 轨迹落库链路

`recordShadowRoute()` / `recordAutoRoute()` → 都走私有 `saveTrace()`：
- shadow 模式会**先真正执行一次 `route()`** 再存；auto 模式直接存已算好的 decision；
- `resolveHitSelectedDocument()`：手选文档是否出现在自动路由 **Top3** 中（1/0/null），这是影子路由的核心观测指标；
- `resolveRouteStatus()`：SUCCESS/LOW_CONFIDENCE/FAILED → 数字 1/2/3；
- 插入 `SuperAgentKnowledgeRouteTrace`（id 用 UidGenerator 雪花 id）。**两处均整体 try-catch，轨迹失败只打 warn，绝不影响主流程**。
- 查询侧：`KnowledgeManageServiceImpl.queryRouteTracePage()` 分页暴露给前端（Controller `/manage/knowledge/route/trace/page/query`），支持按 conversationId / mode / routeStatus 过滤。

### 3.5 管理链路（知识域 CRUD）

前端 → `KnowledgeManageController`（`/manage/knowledge/*`）→ `KnowledgeManageServiceImpl`：
- Scope：`saveScope`（按 scopeCode 查存在则 update 否则 insert）、`deleteScope`（**逻辑删除** status 置 NO）、`listScopes`；
- Topic：`saveTopic` / `deleteTopic` / `listTopics`（可按 scopeCode 过滤）；
- 主题-文档关系：`listTopicDocuments` / `saveTopicDocumentRelation` / `removeTopicDocumentRelation`（维护 relationScore，直接影响第 3 层加分）；
- 文档画像：`queryProfile` / `regenerateProfile` / `batchRegenerateProfiles`（画像质量决定第 2/3 层语义召回质量）；
- 轨迹查询：`queryRouteTracePage`。

> 注意：**CRUD 改完数据后路由索引不会立刻生效**——ES 索引靠 5 秒节流的全量重建（refreshIfNeeded）最终一致。

## 五、ASCII 函数调用关系图

### 5.1 主链路全景图（聊天 → 路由 → 检索计划）

```
用户提问
   │
   ▼
ChatPreparationOrchestrator.prepare(TaskInfo) : ConversationExecutionPlan
   │
   ├─[0] summarizeHistory() ─────────── 会话记忆（ROUTE 阶段之前）
   ├─[1] chatQueryRewriteService.rewrite(question, history) : RagRewriteResult
   │        │  得到 rewriteQuestion（改写问题）
   ▼        ▼
   ├─[2] chatMode == AUTO_DOCUMENT ? ── 是 → 走【自动路由】；否且为 DOCUMENT → 走【影子路由】
   │
   │  ┌───────────────────────【自动路由 AUTO_DOCUMENT】───────────────────────┐
   │  │                                                                        │
   │  │  KnowledgeRouteServiceImpl.route(question, rewriteQuestion)            │
   │  │      : KnowledgeRouteDecision                                          │
   │  │    │                                                                   │
   │  │    ├─① buildQueryContext(q, rq) : RouteQueryContext                    │
   │  │    │     ├─ buildRoutingText(q, rq) : String      原问题+改写问题拼接    │
   │  │    │     ├─ tokenize(text) : List<String>         分词+中文n-gram(≤40)  │
   │  │    │     └─ embedSingle(text) : float[]           问题向量(可null→降级) │
   │  │    │                                                                   │
   │  │    ├─② rankScopes(ctx) : List<ScopeRouteCandidate>   ← 第1层 Top5      │
   │  │    │     ├─ scopeNodeMapper.selectList()          查知识域节点          │
   │  │    │     ├─ [空表] deriveScopesFromDocuments(ctx)  文档元数据兜底        │
   │  │    │     ├─ computeSemanticScores(ctx, texts) : List<Double>           │
   │  │    │     │     └─ embeddingModel.embed(batch≤10) + cosineSimilarity()  │
   │  │    │     ├─ searchLexicalScores(text,"scope",5) ────┐                   │
```

## 六、打分公式与关键阈值（面试被追问时直接背）

| 信号 | 公式 | 定位 |
|---|---|---|
| 语义主分 | `cos > 0.20 ? (cos - 0.20) × 50 : 0` | **主分**，上限约 40 |
| ES 词面辅助 | `min(10, esScore × 1.6)` | 辅助，**硬封顶 10 分** |
| 实体词辅助 | 每个命中 +6（仅英文/数字/≤4字短词） | 辅助，抓型号/产品名等硬词 |
| Topic 层继承 | topic.scopeCode ∈ 第1层候选 → +8 | 漏斗软传递（非硬过滤） |
| Document 层继承 | doc.scope == 第1层Top1 → +15；doc 关联第2层Top1 → relationScore×20 | 漏斗软传递 |
| 置信度 | `Top1分 / max(10, Top1分+Top2分+5)` | 头部集中度，∈(0,1] |
| 低置信阈值 | `< 0.55 → LOW_CONFIDENCE`：候选扩容合并兜底；若 AUTO 模式且歧义 → 反问澄清 | 兜底策略 |
| 高置信 | `≥ 0.80`：候选从 5 个收紧到 3 个 | 精准收敛 |
| 影子命中 | 手选文档 ∈ 自动路由 Top3 → hit=1 | 质量观测指标（hit@3） |

**三层容错设计（重要亮点，面试必讲）：**
1. 向量模型不可用 → `queryEmbedding=null`，`semanticEnabled()=false`，退化为纯词面+关键词打分；
2. ES 不可用/未启用 → `ObjectProvider.getIfAvailable()` 返回 null，词面信号记 0，语义+关键词继续；
3. Scope/Topic 表为空（冷启动，运营还没配置）→ `deriveScopesFromDocuments` / `deriveTopicsFromProfiles` 从文档元数据和 LLM 画像反推候选，**路由功能开箱即用**；
4. 轨迹落库失败 → try-catch 吞掉只打 warn，不影响问答主链路。

## 七、面试讲述脚本

### 7.1 30 秒电梯版

> "我们系统支持多知识库问答，用户提问时先要解决'去哪个知识库找答案'的问题。我设计了一个三层漏斗式知识路由：第一层在知识域 Scope 里选，第二层在主题 Topic 里选，第三层落到具体文档。每一层都用三路信号打分——向量语义相似度做主分、ES 词面检索做辅助分、实体词命中做补充分，上层结果会给下层加权但**不做硬过滤**，避免上游误杀。最后根据 Top1/Top2 分差算置信度：高置信直接锁定文档进 RAG，低置信就把候选作为选项反问用户澄清。另外做了影子路由——用户手选文档时后台静默跑一次自动路由，用 hit@3 持续观测路由质量。"

### 7.2 两分钟详细版（按"问题→方案→细节→效果"讲）

> **问题**：多个知识库场景下，直接全库向量检索会互相干扰、召回噪声大、成本高。
>
> **方案**：路由前置。用户问题先经过改写（结合会话历史），然后进入三层漏斗：
> - 第一层 Scope，从运营配置的知识域节点表里选 Top5；
> - 第二层 Topic，主题表里选 Top8，主题归属第一层的知识域就加 8 分；
> - 第三层 Document，只看"索引构建成功"的文档，第一层 Top1 域加 15 分、第二层 Top1 主题的关系分乘 20 加权，取 Top5。
>
> **打分细节**：每层候选文本由"名称+描述+别名+示例"拼成；语义分=(cosine−0.20)×50 是主分，ES 的 matchPhrase/multiMatch 得分 ×1.6 且封顶 10 分做辅助，英文数字实体词每个 +6。这样保证语义是主导、词面是纠偏。
>
> **置信度与兜底**：置信度 = Top1/(Top1+Top2+5 与 10 取大)，是头部集中度指标。<0.55 时：自动模式会把路由候选和文档元数据兜底候选合并扩范围，如果 Top2 分差还小于 3 且跨知识域，就干脆反问用户"你想问哪份文档"，把候选做成选项；≥0.55 直接锁定 Top1。≥0.80 时候选从 5 个收到 3 个。
>
> **质量闭环**：这是我觉得最有意思的设计——即使用户手动选了文档，后台也会静默跑一次自动路由，记录手选文档是否落在自动路由 Top3 内（hit@3），全量轨迹落库，管理端可以分页查询。这样不用打扰用户就能量化路由准确率，为后续调权重、补别名提供数据依据。

### 7.3 高频追问 Q&A

**Q1：为什么三层？一层直接对文档打分不行吗？**
> 文档多时全量文档两两算 embedding 成本高且区分度低。Scope/Topic 是运营配置的少量节点，先在小集合里粗筛，语义信号更干净；同时上层信息（域、主题）作为强先验加权给文档层，等价于把层级知识注入打分。漏斗还控制了 embedding 批量调用的规模。

**Q2：为什么加权而不是硬过滤（只在上层命中的域里找文档）？**
> 硬过滤会被上游单点错误放大——第一层选错域，第三层必然错。软加权让正确文档即使域没排到第一也保有竞争力，本质是排序融合而非级联裁剪。

**Q3：embedding 调用性能怎么控制？**
> 候选文本按批（batch=10）批量 embed，一次 route() 只对查询做 1 次 embed + 候选按层分批 embed；ES 词面信号把不需要向量的命中也能拉进来，语义不可用时整体可降级。

**Q4：ES 索引数据怎么保持新鲜？**
> 不做增量同步，`refreshIfNeeded()` 用 5 秒节流 + AtomicLong CAS 保证并发下只有一个线程触发全量重建（deleteByQuery + bulk + Refresh.WaitFor），5 张表拼快照，最终一致。删除文档则单独精准删。全量重建的理由是路由索引只是元数据快照，量级小（域/主题/文档数），全量比增量同步逻辑简单可靠。

**Q5：怎么评估路由好不好？**
> 影子路由 + hit@3。用户手选文档是"金标准"标签，auto 与 shadow 两种 mode 的轨迹都落 `nexus_agent_knowledge_route_trace` 表，包含三层候选 JSON、置信度、状态、错误信息，管理端分页可查，还能按会话回放。

**Q6：冷启动怎么办（还没配置知识域/主题）？**
> 兜底推导：Scope 空表时直接从文档元数据（scopeCode/Name/分类/标签）聚合反推候选域；Topic 空表时从文档画像（LLM 生成的 coreTopics/示例问题）反推主题。路由功能不依赖运营先配好数据。

**Q7：如果让你继续优化？**
> ① 轨迹数据积累后用轻量分类模型（或 LLM few-shot）替代线性打分；② 影子路由命中率分域统计，定位弱域补别名/示例；③ 上层硬过滤改成"Top-K 域白名单 + 软加权"折中，降低全量文档打分开销；④ 置信度阈值按域自适应；⑤ 手拼 JSON 换 ObjectMapper 防注入转义不全的问题。
