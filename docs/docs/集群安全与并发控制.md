# 集群安全与并发控制（Redis 分布式租约）

> 对应文档描述：生产环境下多实例部署时，怎么保证同一个会话不会被多个节点同时处理。
> 核心类：`RedisLeaseManager`（redisson 模块，`acquire() / renew() / release()`）、`BusinessChatService`（`startLeaseRenewal()` 10 秒续期一次、30 秒 TTL；`cleanup()` 在 finally 块中释放所有资源）。

---

## 一、模块定位（一句话说清这个业务）

SSE 对话是长任务：一次提问从开始生成到流式输出完毕可能持续几十秒甚至几分钟。项目部署多实例（负载均衡后面挂多台）时，同一个用户可能连到不同节点重复发同一个会话请求，如果不加控制，**同一个 conversationId 会被两个节点同时执行**——AI 回答串台、数据库记录互相覆盖、checkpoint 状态错乱。

解决方案是**Redis 分布式租约（Lease）**：

- 请求进来先拿"租约"（带过期时间的分布式锁），拿不到直接拒绝："该会话当前正在执行中，请稍后再试"；
- 拿到后**每 10 秒自动续期**一次（TTL 30 秒），保证长任务执行期间租约不过期；
- 任务正常完成 / 失败 / 用户停止 / 租约续期失败，统一走 `cleanup()` 在 **finally 块中释放所有资源**（停续期任务、停主流程、释放租约、摘除运行时注册表）；
- 节点突然宕机也不怕：租约 30 秒后自动过期，其他节点可以接管。

### 三道防线（纵深防御）

| 层级 | 机制 | 防护范围 | 代码位置 |
|---|---|---|---|
| 第 1 道 | **Redis 分布式租约** `RedisLeaseManager.acquire()` | **跨实例/跨节点**（集群级互斥） | `claimConversationLease()` |
| 第 2 道 | **进程内注册表** `ChatRuntimeRegistry.register()`（`ConcurrentHashMap.putIfAbsent`） | 同一 JVM 内并发 | `bootstrapConversation()` |
| 第 3 道 | **任务级 CAS** `TaskInfo.finalized`（`AtomicBoolean.compareAndSet`） | 同一次任务的收尾只执行一次 | `stopTask()` / `finishSuccessfully()` / `finishWithFailure()` |

> 面试要点：**为什么本地锁不够**——`synchronized` / `ReentrantLock` 只在单个 JVM 进程内有效，多实例部署时实例 A 和实例 B 是两块独立内存，本地锁互相看不见，必须用所有节点共享的外部存储（Redis）做互斥。

## 三、`RedisLeaseManager` 方法签名与参数/返回值类型

### 3.1 三条 Lua 脚本（原子性的根源）

| 脚本 | Redis 逻辑 | 保证的原子语义 |
|---|---|---|
| `ACQUIRE_SCRIPT` | `exists(KEYS[1]) == 0` → `psetex(KEYS[1], ARGV[2], ARGV[1])`，返回 1；否则返回 0 | "检查不存在 + 写入 + 设置过期时间" 三步合一，不存在竞态窗口 |
| `RENEW_SCRIPT` | `get(KEYS[1]) == ARGV[1]` → `pexpire(KEYS[1], ARGV[2])`，返回 1；否则返回 0 | 只有**持有人本人**才能续期 |
| `RELEASE_SCRIPT` | `get(KEYS[1]) == ARGV[1]` → `del(KEYS[1])` 返回 1；否则返回 0 | 只有**持有人本人**才能删除，防止误解别人的锁 |

参数映射（三个脚本共用）：`KEYS[1]` = 租约 key（`chat:running:{conversationId}`），`ARGV[1]` = `ownerToken`（UUID 字符串，锁的"持有人身份"），`ARGV[2]` = `ttl.toMillis()`（毫秒字符串）。

> 面试要点：**为什么必须用 Lua 脚本**——Redis 单线程执行 Lua，整个脚本是一个原子操作。如果用 Java 先 `GET` 再 `SETEX`，两步之间可能被其他节点的请求插入（check-then-act 竞态）。`ownerToken` 校验则解决了"张三的锁被李四释放"的经典问题（比如李四的请求在张三的锁过期后才到，若无条件 `DEL` 会把李四刚抢到的锁删掉）。

### 3.2 方法签名总表

| 方法 | 参数类型 | 返回值类型 | 说明 |
|---|---|---|---|
| 构造器 `RedisLeaseManager` | `(RedissonClient redissonClient)` | — | 由自动配置类注入 Redisson 客户端 |
| `acquire` | `(String key, String ownerToken, Duration ttl)` | `boolean` | 抢租约：key 不存在则写入 `ownerToken` 并设 TTL，返回 true；已存在返回 false |
| `renew` | `(String key, String ownerToken, Duration ttl)` | `boolean` | 续租：key 存在**且 value 等于自己的 token** 时重置 TTL，返回 true；否则 false |
| `release` | `(String key, String ownerToken)` | `boolean` | 释放：key 存在且 value 等于自己的 token 时 `DEL`，返回 true；否则 false |
| `executeInteger`（private） | `(String script, String key, String ownerToken, Duration ttl)` | `long` | acquire/renew 的公共执行器：参数校验（`Assert`）→ Redisson `getScript(StringCodec.INSTANCE).eval(Mode.READ_WRITE, script, ReturnType.INTEGER, List.of(key), ownerToken, ttlMillis)`，null 兜底返回 0 |

注意差异：`acquire` 和 `renew` 走 `executeInteger()`（内含 TTL 参数与校验），`release` 不需要 TTL，单独调用 `eval`，只做了 key/token 的非空校验。

## 四、`BusinessChatService` 中租约相关方法签名与参数/返回值类型

| 方法 | 可见性 | 参数类型 | 返回值类型 | 职责 |
|---|---|---|---|---|
| `openConversationStream` | public | `(ChatRequestDto request)` | `Flux<String>` | 对外入口，`Flux.defer` 惰性包装启动逻辑 |
| `openDeferredConversationStream` | private | `(ChatRequestDto request)` | `Flux<String>` | 启动编排：建计划 → 抢租约 → 引导启动；catch 中兜底释放租约 |
| `buildLaunchPlan` | private | `(ChatRequestDto request)` | `StreamLaunchPlan` | 归一化问题/会话 ID，**生成 leaseKey 和 leaseOwnerToken(UUID)** |
| `claimConversationLease` | private | `(StreamLaunchPlan launchPlan)` | `boolean` | 调 `redisLeaseManager.acquire(key, token, 30s)` 抢租约 |
| `bootstrapConversation` | private | `(StreamLaunchPlan launchPlan)` | `BootstrapResult` | 落库轮次 → 构建 TaskInfo → 注册本地注册表（失败则回滚：释放租约+标记失败）→ 绑定客户端通道 |
| `createTaskInfo` | private | `(StreamLaunchPlan, ConversationExchangeView)` | `TaskInfo` | 构建运行时上下文（sink、trace、config，携带 leaseKey/token） |
| `bindClientChannel` | private | `(TaskInfo taskInfo)` | `Flux<String>` | `sink.asFlux().doOnSubscribe(激活).doOnCancel(停止)` |
| `activateGeneration` | private | `(TaskInfo taskInfo)` | `void` | 客户端订阅时触发：**启动续期任务 + 订阅主执行流**，双重检查 finalized |
| `startLeaseRenewal` | private | `(TaskInfo taskInfo)` | `reactor.core.Disposable` | `Flux.interval(10s, 10s).subscribe(→ renewLeaseOrStop)`，返回可取消句柄 |
| `renewLeaseOrStop` | private | `(TaskInfo taskInfo)` | `void` | 调 `redisLeaseManager.renew(key, token, 30s)`；**续期失败 → 自愈：停掉续期任务并 stopTask** |
| `releaseLeaseQuietly` | private | `(String leaseKey, String leaseOwnerToken)` | `void` | try-catch 包装 `release()`，释放失败只告警不抛异常 |
| `stopTask` | private | `(TaskInfo taskInfo, String reason)` | `ConversationStopVo` | 停止任务：finalized CAS 抢占 → 中断 Agent → dispose → 收尾落库 → finally 中 cleanup |
| `stopConversation` | public | `(String conversationId)` / `(String, String reason)` | `ConversationStopVo` | 对外停止接口，从注册表找到 TaskInfo 后转 `stopTask` |
| `finishSuccessfully` | private | `(TaskInfo taskInfo)` | `void` | 正常完成收尾，finally 中 cleanup |
| `finishWithFailure` | private | `(TaskInfo taskInfo, Throwable error)` | `void` | 异常收尾，finally 中 cleanup |
| `cleanup` | private | `(TaskInfo taskInfo)` | `void` | **统一清理出口**：dispose 续期任务 → dispose 主流程 → `releaseLeaseQuietly` → `chatRuntimeRegistry.remove(conversationId, taskInfo)` |
| `buildChatLeaseKey` | private | `(String conversationId)` | `String` | `"chat:running:" + conversationId` |

### 支撑类型

- `ChatRuntimeRegistry.register(TaskInfo) : boolean`（`putIfAbsent`，返回 false 表示已被占用）；`get(String) : Optional<TaskInfo>`；`remove(String, TaskInfo) : void`（条件删除，只删自己的）。
- `TaskInfo` 关键字段：`leaseKey: String`、`leaseOwnerToken: String`、`leaseRenewalDisposable: volatile Disposable`、`disposable: volatile Disposable`、`finalized: AtomicBoolean`。

## 五、调用关系与执行顺序（重点）

整个生命周期分四个阶段，租约贯穿始终：

### 阶段 A：请求受理（HTTP 线程，同步执行）

1. `BusinessChatController.stream(ChatRequestDto)` → `openConversationStream(request)`，用 `Flux.defer` 把启动逻辑包成惰性流返回给 WebFlux。
2. 订阅发生时进入 `openDeferredConversationStream(request)`：
3. **`buildLaunchPlan`**：归一化 question / conversationId，生成 `leaseKey = "chat:running:" + conversationId`、`leaseOwnerToken = UUID`。
4. **`claimConversationLease`** → `RedisLeaseManager.acquire(key, token, 30s)`（Lua 原子抢锁）。
   - 返回 false（其他节点正在执行）→ `rejectionFlux("该会话当前正在执行中，请稍后再试")`，**到此为止，不碰任何业务**。
5. **`bootstrapConversation`**：
   - `conversationArchiveStore.startExchange(...)` 落库一轮对话记录；
   - `createTaskInfo` 构建 TaskInfo（leaseKey/token 随任务携带）；
   - `chatRuntimeRegistry.register(taskInfo)`——实例内第二道防线，失败则 `failBootstrappedExchange`（落库失败状态）+ `releaseLeaseQuietly`（归还租约）后拒绝；
   - `bindClientChannel(taskInfo)`：`sink.asFlux()` 挂上 `doOnSubscribe` / `doOnCancel` 钩子。
6. 若上述任何一步抛 RuntimeException：catch 中 `releaseLeaseQuietly`（只在前置条件 `leaseClaimed == true` 时才释放，避免误释放），返回错误事件流。

### 阶段 B：客户端订阅激活（doOnSubscribe 回调，异步）

7. `activateGeneration(taskInfo)`：
   - 先查 `taskInfo.finalized()`，已结束直接返回（防止取消竞态）；
   - **`startLeaseRenewal`**：`Flux.interval(10s, 10s).subscribe(...)` 启动**每 10 秒一次**的续期定时任务，句柄存入 `taskInfo.leaseRenewalDisposable`；
   - 再查一次 `finalized`（double-check，启动瞬间被停止则立刻 dispose 续期任务）；
   - `buildConversationExecution(taskInfo).subscribe()`：在 boundedElastic 上 `prepareExecutionPlan` → 拿到 `ConversationExecutor` 执行真正的 AI 生成，句柄存入 `taskInfo.disposable`。

### 阶段 C：执行中（每 10 秒一次，周期性）

8. 定时器触发 **`renewLeaseOrStop(taskInfo)`** → `RedisLeaseManager.renew(key, token, 30s)`：
   - 返回 true：租约续上（TTL 重置回 30 秒），任务继续；
   - 返回 false（比如节点长时间 GC 停顿导致租约过期且被别的节点拿走）：**自愈逻辑**——dispose 自己的续期任务 → `stopTask(taskInfo, "会话租约已失效，已停止生成")`。宁可主动停，也不能两个节点同时写一个会话。

### 阶段 D：终止收尾（四个出口汇聚到 `cleanup`）

终止只有四个触发源：① 生成正常完成 `doOnComplete → finishSuccessfully`；② 执行异常 `doOnError → finishWithFailure`；③ 用户停止（`POST /session/stop` → `stopConversation`，或客户端断开 `doOnCancel` → `stopTask`）；④ 续期失败自愈 → `stopTask`。

三个收尾方法内部结构一致：

9. `taskInfo.finalized.compareAndSet(false, true)`——CAS 抢占，保证**收尾逻辑全局只执行一次**（完成/失败/停止三边并发时只有一个赢家）；
10. 发终止事件 → `safeComplete(sink)` 关闭 SSE 流 → `conversationArchiveStore.completeExchange(...)` 落库最终状态（COMPLETED / FAILED / STOPPED）；
11. **finally 块中调用 `cleanup(taskInfo)`**，顺序固定：
    - `leaseRenewalDisposable.dispose()`——先停续期（不再给租约续命）；
    - `disposable.dispose()`——再停主执行流；
    - `releaseLeaseQuietly(leaseKey, leaseOwnerToken)` → `RedisLeaseManager.release`（Lua 校验 token 后 DEL，只删自己的锁）；
    - `chatRuntimeRegistry.remove(conversationId, taskInfo)`——条件删除，从进程内注册表摘除。

> 面试要点：为什么 finally？——收尾前置步骤（发事件、落库）任何一步抛异常，租约和注册表**都必须**被释放，否则这个会话要等 30 秒 TTL 过期才能再次使用；`releaseLeaseQuietly` 的"quietly"同理：清理链路中任何一环失败都不阻断后面的清理步骤。

```text
openConversationStream(request)

     ├─ buildLaunchPlan(request)                      → leaseKey + ownerToken(UUID)
     ├─ claimConversationLease(plan) ── acquire() ── [Redis Lua: exists→psetex]
     │       └─ false ⇒ rejectionFlux("会话正在执行中")
     ├─ bootstrapConversation(plan)
     │       ├─ register(taskInfo)                    [本地 putIfAbsent 二道防线]
     │       │       └─ false ⇒ 释放租约 + 拒绝
     │       └─ bindClientChannel(taskInfo) ─ doOnSubscribe
     │                └─ activateGeneration(taskInfo)
     │                     ├─ startLeaseRenewal(taskInfo) ─ interval(10s)
     │                     │      └─ renewLeaseOrStop(taskInfo) ── renew() ── [Lua: get==token→pexpire]
     │                     │             └─ 失败 ⇒ stopTask("租约已失效")
     │                     └─ buildConversationExecution(taskInfo).subscribe()
     │                            └─ 完成/异常 ⇒ finishSuccessfully / finishWithFailure
     └─ cleanup(taskInfo)   ← 所有出口的 finally
          ├─ dispose 续期任务 + dispose 主流程
          ├─ releaseLeaseQuietly ── release() ── [Lua: get==token→del]
          └─ chatRuntimeRegistry.remove(conversationId, taskInfo)
```

## 七、设计细节与边界情况（面试深挖点）

### 7.1 为什么 TTL 是 30 秒、续期间隔是 10 秒？

- **30 秒 TTL** 给"任务活着"提供证明：续期成功 → TTL 重置回 30 秒；节点宕机 → 最多 30 秒后 Redis 自动删除 key，其他节点可接管，**不会死锁**。
- **10 秒间隔**意味着一个续期周期内有 2 次重试机会（10s、20s 时还能续），Redis 抖一下不至于租约丢失；同时执行结束时租约最多残留 30 秒，等待方重试的延迟可控。
- 这实际上是自己实现了一个**简化版 Redisson 看门狗（watchdog）**：Redisson 默认 lockWatchdogTimeout=30s、每 10s（1/3）续期一次，本项目用 `Flux.interval` + Lua 显式实现，节奏完全一致但更可控、不依赖 RLock 的可重入语义。

### 7.2 各异常场景下会发生什么

| 场景 | 行为 | 依赖的机制 |
|---|---|---|
| 另一节点正在执行同一会话 | `acquire` 返回 0 → 直接返回错误事件流，不落库、不启动任务 | Lua `exists` 检查 |
| 同一实例重复请求（租约已过期但旧任务还在注册表里） | `acquire` 可能成功但 `chatRuntimeRegistry.register` 失败 → 回滚：`failBootstrappedExchange` + `releaseLeaseQuietly` + 拒绝 | 进程内 putIfAbsent |
| 执行中 Redis 短暂抖动导致续期失败（返回 false） | `renewLeaseOrStop` → 主动 `stopTask("会话租约已失效，已停止生成")` → cleanup 释放全部资源 | 自愈优先于继续执行 |
| 节点宕机 / 进程被 kill | 没有续期，30 秒后租约自动过期，其他节点可接管该会话 | Redis key TTL 兜底 |
| 任务结束但 `release` 前进程崩溃 | 租约最多残留 30 秒，由 TTL 过期兜底 | 同上 |
| 收尾落库本身抛异常 | 落库在 try 中，cleanup 在 finally 中，**租约照样释放**；且 `releaseLeaseQuietly` 内部 try-catch，释放失败不阻断注册表摘除 | finally + quietly |
| 完成事件与用户停止并发（三边收尾） | `finalized.compareAndSet(false, true)` 只有一个赢家，其余直接 return | AtomicBoolean CAS |

### 7.3 为什么 `stopTask` 里要校验"会话已由新的执行接管"

`stopTask` 拿到 TaskInfo 后会再查一次注册表：`chatRuntimeRegistry.get(conversationId)` 返回的如果不是当前这个 TaskInfo，说明已有新任务接管了该会话，此时停止操作不能动新任务的资源，直接返回"会话已由新的执行接管"。对应的，`cleanup` 里注册表用的是 `remove(key, expectedValue)` **条件删除**——只有 map 里还是自己时才删，防止误删新任务的注册信息。这是"并发环境下检查-再操作"在本地注册表上的又一次落地。

### 7.4 值得注意的边界（可作为"还能怎么改进"的谈资）

`startLeaseRenewal` 订阅时第二个参数是错误回调：若 `renewLeaseOrStop` 内部抛出异常（例如 Redis 连接失败导致 `renew` 抛 RuntimeException 而非返回 false），interval 流会**直接终止**，当前代码只打了 warn 日志——续期从此停止，租约将在 30 秒后过期，而主任务仍在生成。改进方向：把错误也路由到"停止任务"的自愈逻辑，或在 interval 外再包一层重试。这体现"续期失败要 fail-stop"的设计意图在异常分支上还可以加固。

## 八、面试讲述模板

### 8.1 三十秒版本（电梯陈述）

> 我们项目是 AI 对话系统，一次 SSE 生成是几十秒的长任务，多实例部署时必须防止同一个会话被两个节点同时执行。我设计了一个基于 Redis 的分布式租约：请求进来先用一段 Lua 脚本原子地"检查不存在 + 写入 ownerToken + 设置 30 秒 TTL"抢租约，抢不到直接拒绝；拿到后由 Reactor 的 `Flux.interval` 每 10 秒用 Lua 续期一次——Lua 里先比对 value 是不是自己的 token 再 pexpire，保证只能续自己的锁；正常完成、异常、用户停止、续期失败这四个出口全部汇聚到 finally 里的 `cleanup()`：先停续期任务、再停主流程、然后用 Lua 校验 token 后 DEL 释放租约、最后从本地注册表摘除。节点宕机也不怕，租约 30 秒自动过期，不会死锁。

### 8.2 三分钟版本（按"问题→方案→细节→兜底"展开）

1. **问题**：对话生成是长任务，Nginx 负载均衡下同一用户两次请求可能落到不同实例，本地锁（synchronized/ReentrantLock）只对单 JVM 有效，必须用跨节点的共享存储做互斥。
2. **方案**：抽了一个独立的 redisson 租约框架模块（`RedisLeaseManager` + 自动配置），业务侧 `BusinessChatService` 在会话启动链路里先抢租约，key 是 `chat:running:{conversationId}`，value 是随机 UUID 作为持有者身份。
3. **原子性细节**：三个操作（抢/续/放）各对应一段 Lua 脚本。抢：`exists==0` 才 `psetex`，把"检查、写入、设 TTL"合成一个原子操作；续和放都先 `get` 比对 token——这是为了解决"锁过期后别人抢到、自己回来误删别人的锁"的经典问题。
4. **生命周期**：租约不能只靠初始 TTL（长任务会超时），所以客户端订阅 SSE 时启动每 10 秒一次的续期定时任务，把 TTL 重置回 30 秒——相当于自己实现了 Redisson 的看门狗。续期失败（返回 false）说明租约已丢、可能被其他节点接管，此时主动停止当前生成，宁可失败也不能双写。
5. **优雅清理**：所有终止路径（完成/异常/停止/续期失败自愈）用 `AtomicBoolean` CAS 保证收尾只执行一次，并在 finally 中 `cleanup`：dispose 续期任务 → dispose 主流程 → 释放租约（quietly，异常不阻断）→ 注册表条件删除。配合进程内的 `ChatRuntimeRegistry.putIfAbsent` 做第二道防线。
6. **兜底**：任何原因导致租约没被显式释放（进程崩溃、release 前宕机），30 秒 TTL 自动过期，系统自愈，不会死锁。

### 8.3 高频追问 Q&A

**Q1：为什么不用 Redisson 自带的 `RLock`？**
> RLock 完全可行，但它提供的是"可重入、可阻塞等待"的互斥锁语义，还自带看门狗黑盒。本场景需要的是"租约"语义：抢不到就立刻拒绝（不排队等待）、TTL 与续期节奏要业务可控、无需可重入。十几行 Lua 就能表达清楚，不引入 `tryLock` 超时参数、park/unpark 等额外复杂度，也便于排查（Redis 里直接能看懂 key 和 value）。两者是取舍不是优劣。

**Q2：`acquire` 时 `psetex` 的 value 为什么放 UUID 而不是节点 ID？**
> 粒度是"会话 × 某一次执行"而不是"会话 × 节点"。同一节点上同一会话旧任务还没结束、新请求又进来（比如注册表回滚后重试），用 UUID 区分的是这一次执行，释放时只释放自己这一次的锁。

**Q3：续期任务和主任务谁先停？为什么这个顺序？**
> cleanup 里先 `dispose` 续期任务、再 dispose 主流程、再释放租约。先停续期是防止主流程已死而续期还活着，把一个"死任务"的租约一直续着不释放（僵尸租约）；释放租约放在注册表摘除之前，是让其他节点尽早能抢到会话，而本节点残留的注册表条目由 `remove(key, value)` 条件删除 + `register` 失败回滚兜底。

**Q4：Redis 挂了整个机制不就失效了吗？**
> 请求入口 `acquire` 抛异常会被 `openDeferredConversationStream` 的 catch 捕获，快速失败返回错误流——Redis 不可用时系统表现为"拒绝新会话"，而不是"无保护地并发执行"，这是 fail-fast 的取舍。已有任务则靠续期失败触发停止（见 7.4 的加固点）。

**Q5：为什么拒绝消息在多个地方出现（抢租约失败、注册表失败）？**
> 第一处是集群级互斥失败（别的实例占着），第二处是实例内互斥失败（本实例旧任务还在）。两道防线返回同样的用户话术，但日志和回滚路径不同：前者什么都不用回滚，后者要落库失败状态并归还刚抢到的租约。

### 8.4 一图记忆口诀

> **一把锁（Redis 租约）、两道防线（Redis + 本地注册表）、三个 Lua（抢/续/放，token 校验）、四个出口（完成/异常/停止/自愈）、finally 一个 cleanup（停续期→停主流程→还锁→摘注册表）。**
