# 会话记忆（Conversation Memory）业务全解 —— 面试讲述版

> 对应项目：superagent-understanding / `nexus-agent-business-chat` 模块
> 核心类：`PersistentConversationMemoryService`（实现接口 `ConversationMemoryService`）
> 源码位置：`nexus-agent-business/nexus-agent-business-chat/src/main/java/org/javaup/ai/chatagent/service/PersistentConversationMemoryService.java`

---

## 0. 一句话总览（面试开场白）

> "这个项目的会话记忆是一套**分层记忆 + 水位线增量压缩**的方案：短期记忆是最近 N 轮对话原文窗口，长期记忆是一份由 LLM 增量维护的**结构化 JSON 摘要**（存在 MySQL 表 `nexus_agent_chat_memory_summary` 里）。每轮问答结束后异步判断'溢出轮次'，超出窗口保留数的历史对话按批次交给 LLM 合并进已有摘要，并用 `coveredExchangeId` 水位线记录压缩进度；下一轮提问时把'长期摘要 + 最近几轮原文'拼装成 `ConversationMemoryContext` 一次性交给编排层。"

三大能力（与文档表格一一对应）：

| 功能 | 核心类 | 关键方法 | 一句话说明 |
| --- | --- | --- | --- |
| 记忆加载 | `PersistentConversationMemoryService` | `loadMemoryContext()` | 加载长期摘要 + 最近几轮原文 |
| 摘要压缩 | `PersistentConversationMemoryService` | `refreshConversationSummaryAsync()` | 用 LLM 把历史对话压缩成结构化摘要 |
| 摘要合并 | `PersistentConversationMemoryService` | `mergeSummaryPayload()` | 增量合并新对话到已有摘要 |

### 1.2 关键数据结构

**摘要持久化实体 `SuperAgentChatMemorySummary`（表 `nexus_agent_chat_memory_summary`）**

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | `Long` | 雪花 ID（`IdType.INPUT`，由 `UidGenerator` 生成） |

| `coveredExchangeId` | `Long` | **水位线**：摘要已覆盖到的最大 `exchangeId` |

| `compressionCount` | `Integer` | 累计执行压缩次数 |
| `summaryVersion` | `Integer` | 摘要版本号（每次更新 +1） |
| `summaryText` | `String` | 渲染后的中文纯文本摘要（给 LLM 当上下文用） |
| `summaryJson` | `String` | 结构化 JSON 摘要（程序解析用） |
| `lastSourceEditTime` | `Date` | 摘要覆盖的最后一轮原文的编辑时间 |

**结构化摘要载体 `ConversationSummaryPayload`（内存模型，`model/memory` 包）**

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `summary` | `String` | 180~260 字中文总摘要 |
| `conversationGoal` | `String` | 用户长期目标（一句话） |
| `stableFacts` | `List<String>` | 已确认事实 |
| `userPreferences` | `List<String>` | 用户偏好与约束 |
| `resolvedPoints` | `List<String>` | 已解决的问题 |
| `pendingQuestions` | `List<String>` | 待跟进问题 |
| `retrievalHints` | `List<String>` | 检索提示关键词（供 RAG 用） |

**单轮对话视图 `ConversationExchangeView`**：`long exchangeId`、`String question/answer`、`ChatTurnStatus status`（RUNNING/COMPLETED/STOPPED/FAILED）、`Date createTime/editTime` 等。

**记忆上下文 `ConversationMemoryContext`（`loadMemoryContext` 的返回值）**

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `assembledHistory` | `String` | 最终拼装结果 = 长期摘要 + `\n\n` + 最近原文 |
| `longTermSummary` | `String` | 长期摘要纯文本 |
| `recentTranscript` | `String` | 最近 N 轮"用户+助手"原文（用于问题改写） |
| `answerRecentTranscript` | `String` | 最近 N 轮"仅用户问题"（用于回答阶段历史） |
| `summaryPayload` | `ConversationSummaryPayload` | 结构化摘要 |
| `coveredExchangeId` | `Long` | 水位线快照 |
| `coveredExchangeCount` | `Integer` | 已压缩轮数快照 |
| `compressionCount` | `Integer` | 压缩次数快照 |
| `compressionApplied` | `boolean` | 是否已应用过压缩（= 长期摘要非空） |

**相关配置 `ChatRagProperties.HistorySummaryProperties`（前缀 `app.chat.rag.history-summary`）**：`enabled=true`、`keepRecentTurns=4`（窗口保留轮数）、`compressionBatchTurns=6`（每批压缩轮数）、`recentTranscriptMaxChars=2200`、`summaryMaxChars=1400`。

## 2. 方法之间的调用关系与执行顺序

整个会话记忆有两条主线：**读取侧（下一轮提问时装载记忆）** 和 **写入侧（本轮回答结束后异步压缩摘要）**，两侧共用同一个核心私有方法 `refreshSummaryIfNecessary`。

### 2.1 执行顺序总述（时间线）

```
用户第 k 轮提问
  │
  ├─ ① BusinessChatService.openConversationStream(ChatRequestDto)
  │     └─ bootstrapConversation → conversationArchiveStore.startExchange(...)
  │         （先落库一轮 RUNNING 状态的对话，拿到 exchangeId）
  │
  ├─ ② prepareExecutionPlan → ChatPreparationOrchestrator.prepare(TaskInfo)
  │     └─ summarizeHistory → loadMemoryContext(conversationId, traceRecorder)   ←【记忆加载】
  │         内部可能触发一次"同步懒压缩"（refreshSummaryIfNecessary）
  │         返回 ConversationMemoryContext → 供改写/路由/回答各阶段使用
  │
  ├─ ③ 本轮回答流式输出……
  │
  └─ ④ 回答终态收尾（三种：完成 finishSuccess / 失败 finishWithFailure / 用户停止 stop）
        ├─ conversationArchiveStore.completeExchange(...)  （本轮状态置 COMPLETED/FAILED/STOPPED）
        └─ finally: safeRefreshConversationSummary(conversationId)
              └─ refreshConversationSummaryAsync(conversationId)                    ←【摘要压缩·异步入口】
                    └─ 异步线程: refreshSummaryIfNecessary
                          └─ 每个溢出批次: mergeSummaryPayload(...)                 ←【摘要合并·LLM】
                                └─ saveSummarySnapshot(...)  （水位线推进 + insert/update）
```

**记忆加载发生在"本轮问题开始时"，摘要压缩发生在"上一轮回答结束后"**——二者通过数据库里的摘要表解耦，压缩是异步的，不阻塞用户请求。

### 2.2 读取侧：`loadMemoryContext` 内部顺序

```
loadMemoryContext(String, ConversationTraceRecorder)
  1. conversationId 为空                    → emptyContext() 直接返回空上下文
  2. historySummary.enabled == false（降级）→ 只调 listRecentExchanges + renderRecentTranscript
     + renderAnswerRecentTranscript，longTermSummary 为空串（无长期记忆的"无状态"模式）
  3. 正常路径（按序执行）：
     3.1 findSummary(conversationId)                     查摘要表最新一行
     3.2 refreshSummaryIfNecessary(...)                  ★ 读时懒压缩（同步，保证读到最新水位）
     3.3 readSummaryPayload(summaryState)                解析 summaryJson → ConversationSummaryPayload
     3.4 listRecentExchanges(conversationId, recentFetchLimit(keepRecentTurns))
         —— recentFetchLimit = max(keep*3, keep+4)，多取一些再过滤 RUNNING 轮
     3.5 renderRecentTranscript(...)                     最近 keepRecentTurns 轮"用户+助手"原文（尾部截断）
     3.6 renderAnswerRecentTranscript(...)               最近 keepRecentTurns 轮"仅用户问题"
     3.7 assembleHistory(longTermSummary, recentTranscript)  拼接：摘要在前、原文在后
     3.8 Builder 组装 ConversationMemoryContext 返回
```

> 面试点：`loadMemoryContext(conversationId)` 是接口 default 方法的重载，无 trace 时转调 `loadMemoryContext(conversationId, null)`。记忆装载在 `ChatPreparationOrchestrator.prepare` 里是**第一个阶段（MEMORY 阶段）**，早于问题改写（REWRITE）和路由（ROUTE）。

### 2.3 写入侧：`refreshConversationSummaryAsync` → `refreshSummaryIfNecessary` → `mergeSummaryPayload` → `saveSummarySnapshot`

```
refreshConversationSummaryAsync(String conversationId)          【异步入口，立即返回】
  1. conversationId 为空 或 摘要开关关闭 → 直接 return
  2. refreshingConversationIds.add(conversationId) 失败（已在刷新中）→ 直接 return（同会话去重）
  3. CompletableFuture.runAsync(task, chatMemorySummaryExecutorService) 提交后台线程池
     └─ 任务体: refreshSummaryIfNecessary(conversationId, findSummary().orElse(null), null)
        finally: refreshingConversationIds.remove(conversationId)

refreshSummaryIfNecessary(String, SuperAgentChatMemorySummary, ConversationTraceRecorder)  【核心调度】
  1. listExchangesAfter(conversationId, coveredExchangeId)      查水位线之后的全部增量轮
  2. filter(isStableSummaryExchange)                            只保留 COMPLETED 且 question 非空的轮
  3. overflowCount = stable.size() - keepRecentTurns
     overflowCount <= 0 → 无溢出，原样返回 currentState（不调 LLM，零成本）
  4. overflowExchanges = stable.subList(0, overflowCount)       取最早的溢出部分（最新的留给短期窗口）
  5. for (start = 0; start < overflow; start += compressionBatchTurns)   按 6 轮一批循环：
     5.1 readSummaryPayload(workingState)                       读当前摘要 JSON
     5.2 mergeSummaryPayload(existingPayload, batch, traceRecorder)     ←【LLM 合并】
     5.3 saveSummarySnapshot(conversationId, workingState, mergedPayload,
                             lastExchangeId, coveredCount+batch.size, resolveSourceTime(last))
         —— 每批立即落库，水位线推进，失败不影响下一批的起点正确性
  6. return workingState

mergeSummaryPayload(ConversationSummaryPayload, List<ConversationExchangeView>, ConversationTraceRecorder)
  1. render(CONVERSATION_SUMMARY_SYSTEM, {})                    系统 prompt：只压缩不回答、只留跨轮价值信息
  2. buildSummaryMergePrompt(existingPayload, batch)
     ├─ writePayloadJson(normalizePayload(copyPayload(existingPayload)))   已有摘要 JSON
     ├─ renderCompressionTranscript(batch)                      新批次对话原文（问题截 160 字/回答截 320 字）
     └─ render(CONVERSATION_SUMMARY_MERGE, Map)                 用户 prompt：规定 JSON 输出结构
  3. observedChatModelService.callText("summary", systemPrompt, userPrompt, traceRecorder)  → 调 LLM
  4. parseSummaryPayload(content)
     ├─ extractJsonObject(raw)  正则 \{.*} DOTALL 抽取 JSON（防 LLM 输出带解释文字）
     └─ objectMapper.readTree → 按 7 个字段构建 Payload → normalizePayload
  5. LLM 调用异常 或 JSON 解析失败 → fallbackMerge(existingPayload, batch)   【规则兜底】
     ├─ renderFallbackBatchHighlight(batch)                     生成"用户关注/已有结论"要点串
     ├─ 拼接进 summary（截 summaryMaxChars）
     ├─ 首次压缩时把最后一轮 question 设为 conversationGoal
     ├─ 累加 pendingQuestions（clip 80 字 + 去重限 6 条）
     └─ extractRetrievalHints(lastQuestion) 提取检索关键词（过滤"请问/帮我"等噪声词）

saveSummarySnapshot(String, SuperAgentChatMemorySummary, ConversationSummaryPayload, long, int, Date)
  1. findSummary(conversationId) 再查一次 DB 最新状态           ★ 二次校验（并发写保护）
  2. DB.coveredExchangeId > 本次 coveredExchangeId → 别的线程已推进 → 放弃本次，返回 DB 最新
  3. DB.coveredExchangeId == 本次 且 summaryText 非空 → 已写过同一水位 → 返回 DB 最新
  4. buildLongTermSummaryText(payload)                          结构化 JSON → 中文分段纯文本（【长期会话摘要】【会话目标】【已确认事实】…）
  5. latestState == null → summaryMapper.insert（新行：compressionCount=1, summaryVersion=1, id=uidGenerator）
     否则     → summaryMapper.updateById（compressionCount+1, summaryVersion+1）
```

### 2.4 管理侧（查询/重建/删除）

```
getConversationSummary(String)       → findSummary → toSummaryView        （前端查看摘要状态，只读）
rebuildConversationSummary(String)   → 去重加锁 → summaryMapper.delete 全删
                                     → refreshSummaryIfNecessary(currentState=null) 全量重压（同步）
                                     → toSummaryView                      （HTTP 入口：BusinessChatController）
deleteConversationSummary(String)    → summaryMapper.delete               （删会话时清理摘要）
```

这三个方法的调用入口都在 `BusinessChatService`（`rebuildConversationSummary`/`deleteConversationSummary`/会话视图里的 `getConversationSummary`），最终由 `BusinessChatController` 暴露 HTTP 接口。

## 5. 面试讲述脚本（背这段）

### 5.1 30 秒版本

> "我们 Chat Agent 的会话记忆分两层：**短期记忆**是最近 4 轮对话原文，直接从对话归档表查；**长期记忆**是一份结构化 JSON 摘要，由 LLM 增量维护，存 MySQL。核心类是 `PersistentConversationMemoryService`，对外三个能力：`loadMemoryContext` 装载记忆、`refreshConversationSummaryAsync` 异步压缩、`mergeSummaryPayload` 增量合并。摘要里存了会话目标、已确认事实、用户偏好、待跟进问题、检索提示七个字段，既能拼 prompt 又能反哺 RAG 检索。"

### 5.2 2 分钟完整版（按"写入→存储→读取"讲）

**① 为什么这么做（痛点）：**
> "LLM 上下文有限，多轮对话全量塞 prompt 会爆 token、也会让模型跑偏。所以不能把所有历史都给模型，但只给最近几轮又会丢失长期意图，比如用户十几轮前说过的一个约束。我们用'**摘要 + 滑动窗口**'解决：重要的沉淀成摘要，细节保留最近 4 轮原文。"

**② 写入侧（摘要是怎么长出来的）：**
> "每轮问答结束时——不管是正常完成、失败还是被用户停止——收尾落库后都会在 `finally` 里调 `refreshConversationSummaryAsync`，把压缩任务扔进**专用线程池**（2 线程、队列 32、CallerRunsPolicy），所以用户请求零等待。异步任务里核心是 `refreshSummaryIfNecessary`：先按水位线 `coveredExchangeId` 查增量对话，只保留 COMPLETED 的稳定轮；增量减去窗口保留数 4 轮，没有'溢出'就直接返回，**不花一分钱 token**；有溢出就取最早的溢出段，按 6 轮一批循环：把'已有摘要 JSON + 新批次对话原文'填进 `conversation-summary-merge` 提示词模板调 LLM，产出新的七字段结构化摘要；每批立即 `saveSummarySnapshot` 落库并推进水位线——这样即使中途挂了，进度也是持久化的，下次从断点继续。"

**③ 可靠性设计（面试加分项）：**
> "这里有四个防御性设计：
> 1. **同会话去重**——`ConcurrentHashMap.newKeySet()` 维护刷新中的会话 ID，重复触发直接跳过；
> 2. **并发水位保护**——落库前重查一遍 DB，如果发现水位线已被别的线程推进得更远，就放弃本次写入，避免旧摘要覆盖新摘要；
> 3. **LLM 失败兜底**——`mergeSummaryPayload` 里 LLM 调用或 JSON 解析失败时不抛异常，走 `fallbackMerge` 规则合并（截取要点串、补待跟进问题、正则抽取检索关键词），保证摘要链路永远向前推进；
> 4. **解析容错**——LLM 输出可能带解释文字，先用正则 `\{.*}` DOTALL 抽出 JSON 再解析。"

**④ 读取侧（下一轮提问怎么用记忆）：**
> "用户下一轮提问时，编排器 `ChatPreparationOrchestrator.prepare` 的**第一个阶段**就是调 `loadMemoryContext` 装载记忆。它先查摘要表，这里有个细节：读取路径也调了 `refreshSummaryIfNecessary`，相当于**读时懒压缩**，即使异步刷新没跑完也能保证读到最新水位。然后把'长期摘要文本'和'最近 4 轮原文'用 `assembleHistory` 拼成 `assembledHistory`；另外产出一份只含用户问题的 `answerRecentTranscript`。这些统一装进 `ConversationMemoryContext`，供后面的**问题改写**（带历史理解指代）、**知识路由**和**回答生成**使用；结构化 payload 里的检索提示还会转成 `HistoryPlanningContext` 反哺 RAG 检索。如果摘要开关关掉，就自动降级成只拼最近原文的'无状态'模式。"

### 5.3 高频追问 & 参考回答

| 可能的追问 | 参考回答要点 |
| --- | --- |
| 为什么用 `coveredExchangeId` 做水位线，而不是按条数/时间？ | exchangeId 是雪花 ID 单调递增，天然可比较；按 ID 增量查询（`gt` 条件）对索引友好；幂等——同水位重复压缩会被 `saveSummarySnapshot` 的二次校验挡掉 |
| 为什么压缩放在"回答结束后"而不是"下次提问前"？ | 压缩要调 LLM，耗时不可控；放提问前会把成本加在用户等待路径上。放结束后异步做，提问时只需读表，最多读时懒压缩兜底一次 |
| 为什么单独建线程池而不用公共池？ | 隔离：摘要压缩慢且可失败，不能挤占改写/回答等主链路线程。`chatMemorySummaryExecutorService`：2 核心、32 队列、守护线程、`CallerRunsPolicy`（打满时回退到提交线程执行，起到天然限流作用，不丢任务） |
| `isStableSummaryExchange` 为什么只认 COMPLETED？ | STOPPED/FAILED 轮的答案不完整，压缩进去会污染摘要（把失败猜测写成事实）；但用户的问题文本仍可通过 `renderRecentTranscript` 的窗口进入短期记忆 |
| JSON 摘要和 summary_text 为什么要双份？ | `summary_json` 给程序解析（结构化字段反哺检索与规划），`summary_text` 是渲染好的中文分段文本，直接拼 prompt 给 LLM 读，避免每次读取都重新渲染 |
| 摘要会不会无限膨胀？ | 不会。`normalizePayload` 统一裁剪：summary 上限 1400 字、conversationGoal 120 字、每个数组去重后最多 6 条、每条 80 字；批次合并时旧的低价值信息由 LLM 按提示词淘汰 |
| 重建（rebuild）和刷新（refresh）的区别？ | refresh 是水位线增量合并；rebuild 先 `delete` 全部摘要、再从零全量重压（同步执行），用于提示词升级或摘要污染后的修复，期间同样用去重集合防并发 |

### 5.4 讲述时的数字速记卡

- 窗口保留 **4** 轮（`keepRecentTurns`）｜每批压缩 **6** 轮（`compressionBatchTurns`）
- 最近原文截 **2200** 字｜摘要上限 **1400** 字｜数组每项限 **6** 条、单条 **80** 字
- 最近查询条数 = max(keep×3, keep+4)｜线程池 **2** 线程 / 队列 **32**
- 摘要表 `nexus_agent_chat_memory_summary`，七字段 JSON：summary / conversation_goal / stable_facts / user_preferences / resolved_points / pending_questions / retrieval_hints
